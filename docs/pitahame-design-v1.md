# ピタハメ 設計書 v1

作成: 2026-07-18 ／ 更新: 2026-07-19 ステータス: **フェーズ1〜4 実装完了（未コミット）・フェーズ2.5 メンター実機ゲート待ち**。実装との既知差分は [apps/pita-hame/AGENTS.md](../apps/pita-hame/AGENTS.md)「既知の注意点」を参照

ボードゲーム「ウボンゴ」着想のポリオミノ・スピードパズル。ピースをドラッグして型（シルエット）をぴったり埋め、完成の速さを競う。

> 名称の経緯: 当初案「ウホンゴ」は原作名と一音違いで、商標・不正競争防止法上の混同リスクがあるため「ピタハメ」（ぴたっとはめる）に決定（2026-07-18）。着想元の明記は問題ない（ことばみっけの「コトバト着想」と同方式）。

---

## 1. 位置づけとねらい

- **利用シーン**: ボドゲクラブ（`bodoge`）＋ ひろばでのひとり練習（`hiroba`）
- **競争について**: roomK ツールは普段「評価しない・競わない」を原則とするが、本アプリは**意図的にスピード競争を残す**（キャパグラフが「数値化しない」原則を意図的に破ったのと同系の判断）。
  - v1 の競争は**ラウンドごとの完成順表示のみ**。通算得点・総合順位は付けない（ラウンドごとに勝負がリセットされ、負け体験が持ち越されない）
  - 宝石ドロー等の運要素による緩和は、実機で子どもの反応を見てから v2 で設計する
- **対象**: 小学校中学年〜中学生。空間パズルなので読み書きの負担が小さく、学年差が出にくい

## 2. あそびの概要

1. 画面に「型」（グレーのシルエット）と3〜4個のカラフルなピースが出る
2. ピースをドラッグと回転で型の中に置いていく
3. 型をぴったり埋めたら完成 →「ピタハメ！」
4. みんなでモードでは全員が同じ問題に同時挑戦し、完成した順番が表示される

## 3. モード

| モード | 通信 | 内容 |
|--------|------|------|
| みんなで | RTDB ルーム（6桁コード） | ホストがラウンド開始 → 全員同一問題 → 完成順を表示。ラウンド制 |
| ひとりで練習 | オフライン | 同じエンジンで1問ずつ挑戦。経過タイムのみ表示（記録の保存・ベスト比較はしない） |

## 4. パズル仕様

### ピースプール（v1 = 回転のみ、左右反転なし）

反転操作は入れない。鏡像関係のピース（S/Z、L/J など）は**別ピースとして両方収録**することで、反転なしでも多様な問題を作れる。

| サイズ | ピース | 種数 |
|--------|--------|------|
| 3マス | I3, L3 | 2 |
| 4マス | O4, I4, T4, L4, J4, S4, Z4 | 7 |
| 5マス | P5, L5, Y5, T5 | 4 |

- 計13種。5マスのキラルな鏡像違い（P5' 等）は v1 では収録しない
- 各ピースは**種類ごとに固定色**。色だけに頼らず、太い輪郭＋マス目の白い区切り線で形でも判別できるようにする（色覚対応）。隣接ピース間のコントラストを確保するパレットを実装時に確定

### 難易度

| 難易度 | ピース数 | 合計マス | バウンディングボックス |
|--------|---------|----------|------------------------|
| やさしい | 3 | 9〜12 | 5×4 以内 |
| むずかしい | 4 | 13〜17 | 6×5 以内 |

「以内」は回転して収まればよい（長辺≤5 かつ 短辺≤4 等）。カタログの `w,h` は生成時の向きのまま格納する。

- 複数解は**許容**（原作も複数解あり）。ただしヒント機能は複数解と矛盾するため v1 では持たない

## 5. 問題カタログと制作パイプライン

**実行時のランダム生成はしない。** 開発時に生成・選別した問題カタログ（quiz の問題パックと同方式）を同梱する。生成器はゲーム機能ではなく問題制作ツールと位置づける。

### パイプライン

1. **生成**: `scripts/pitahame-gen.mjs`（Node、リポジトリ内の開発ツール。デプロイ対象外）。ピースをランダムな向き・位置で連結に合成してシルエットを作る → 構成的に必ず解がある
2. **自動フィルタ**（Codex 相談で確定した基準）:
   - 完全な長方形は除外
   - 縦横比が極端（長辺÷短辺 > 2）は除外
   - 穴（外周に到達できない空き領域）がある形は除外。1マスに限らず全ての穴が対象（埋められない囲まれ空所は子どもを混乱させるため強い方を採用）
   - 周囲と1辺しか接しない突起マスが多い形を制限
   - 基準解で各ピースが他ピースと2辺以上接することを要求（1ピースだけ大きく露出する形を減点）
   - 「シルエット内に単独で置ける位置・向きが1通りしかないピース」が複数ある問題は除外（形を見ただけで配置が決まるため）
   - 正規化したシルエット＋ピース集合のハッシュで重複除外
   - 完全探索（6×5 以内なら軽量）で解数・全探索ノード数を算出
   - **難易度スコアの主軸は `effort`** = 最初の1解に到達するまでの探索ノード数（探索順をシャッフルした9トライアルの中央値、seed は問題ハッシュ由来で決定的）。全解探索コストは「解が多い問題ほど膨らむ＝1解を見つける難しさと逆転する」ため主軸にしない（Codex 指摘反映）
3. **選別**: スコア昇順プールから easy は 15〜75% 帯（下位15%の数秒で終わるチュートリアル級を廃棄）、hard は 40〜100% 帯を採用。帯内にアンカーを均等配置して難易度を散らし、同一ピース組合せは3問以内。**目標: 各難易度30問（最低20問）**。採用後の実プレイ確認はフェーズ2.5 実機ゲートで行う
4. **同梱**: 採用分を `index.html` にインラインの `PITAHAME_PUZZLES` として埋め込む（RTDB 単一ファイル規約を維持。60問程度なら容量問題なし、HTMLとデータの版ずれも防げる）。生成器が「index.html 内のマーカー区間を差し替える」出力モードを持つと再生成が楽

### 問題の巡回（枯渇処理）

- 同一ルーム内では未使用問題を優先し重複させない（`usedPuzzleIds` で管理）
- 全問使い切ったら `usedPuzzleIds` をクリアして再巡回。ただし直前の問題は再選択しない

### 問題データ形式（カタログ）

```js
const PITAHAME_PUZZLES = {
  formatVersion: 1,
  easy: [
    { id: 'E01', w: 5, h: 4,
      cells: [[0,0],[1,0], ...],            // シルエットのマス座標
      pieces: ['L4', 'S4', 'I3'],           // トレイ上の並び順もこの順で固定
      sol: [{ p: 0, x: 0, y: 1, r: 2 }, ...], // 基準解（答え表示用）。r = 90°回転回数
      metrics: { solutions: 1, nodes: 11, effort: 5, singlePlacements: [7,2,20], protrusion: 1, perimeter: 16 } // 制作時指標（アプリ動作には未使用）
    },
  ],
  hard: [ ... ],
};
```

### 座標規約（生成器・アプリ共通）

- シルエットは左上が `(0,0)` になるよう正規化
- ピース形状はセル座標の集合で定義し、回転後も `minX = minY = 0` へ正規化
- 基準解の `x, y` は正規化後ピースの左上（オフセット）座標
- **同一問題内で同種ピースの重複は禁止**（重複を許すと完全探索が入れ替えを別解として数える。v1 は禁止が単純）
- トレイの並び順・初期向き（r=0）はカタログで固定 → 全端末で同一条件（公平性）

### RTDB へ保存するパズルは自己完結 JSON にする

ホストはラウンド開始時にカタログエントリを**展開**し、種類名参照ではなく以下を含む自己完結 JSON を RTDB に保存する（デプロイ版ズレで旧クライアントが新種類名を解釈できない事故を防ぐ）。

- `formatVersion`／問題 `id`／`w`・`h`／シルエット座標
- 各ピース: インスタンス番号・**セル座標そのもの**・初期向き・トレイ順
- 基準解

ピース色は機能に影響しないためローカル定義でよい（種類名から引けない場合の既定色を持つ）。未知の `formatVersion` を受信したクライアントは「新しいバージョンがあります。再読み込みしてね」を表示する。

## 6. 操作仕様

### 基本操作

| 操作 | 挙動 |
|------|------|
| タップ／クリック | ピースを選択（太枠でハイライト） |
| ドラッグ | ピースを移動。ボード上ではグリッドスナップ候補を表示 |
| 「まわす」ボタン | 選択中ピースを90°回転 |
| 「もどす」ボタン | 選択中ピースをトレイへ戻す |
| 「ぜんぶもどす」ボタン | 全ピースをトレイへ戻す（確認なし・即時） |

- ピースのタップを回転に割り当てない（選択しようとして回転する誤操作を防ぐ）
- ボタンはピース未選択時は無効化

### 配置ルール

- ピースは**シルエット内・重なりなし**の位置にのみ置ける
- ドラッグ中: 有効位置ならスナップ候補をプレビュー、無効位置は赤系で明示
- 無効なまま離したら**直前の有効位置（またはトレイ）へ戻す**。無効配置をボードに残さない
- 配置済みピースを回転して重なる場合: 周囲1マスの「壁蹴り」探索で置ける位置へ補正、なければ回転を取り消す

### タッチ・表示

- パズル領域のみ `touch-action: none`。ページ全体のスクロールは殺さない
- **入力の堅牢化**（フェーズ2 Codex レビュー反映）: ドラッグは単一プライマリポインタのみ受理（pointerId 照合）。`pointercancel`（OSジェスチャー・通知等）では配置を確定せず必ず元へ戻す。ドラッグ中の回転は禁止。画面遷移・問題切替の前に `cancelDrag()` で進行中ドラッグを破棄する
- ドラッグ中のピースは指より少し上に表示
- セルは48px前後を確保（6×5 + トレイが縦MAX。600px以下はセル縮小で対応）
- 論理座標は常に整数グリッドで保持し、CSS の座標から状態を逆算しない
- `prefers-reduced-motion` では完成演出を縮小
- ラウンド中の配置状態は sessionStorage に保存し、リロード時に復元

### 完成判定

配置確定のたびに「シルエット全マスが充填されているか」を判定（配置ルール上、重なり・はみ出しは存在しない）。充填完了 → 自動で「ピタハメ！」演出 + 完成登録。

## 7. みんなでモード進行

### 画面フロー

```
TOP（つくる／入る／ひとりで練習）
 → waiting（参加者一覧・ホスト設定）
 → round（カウントダウン → プレイ）
 → results（完成順 + 答え表示）
 → …（ラウンド繰り返し）
 → finished（ふりかえり）
```

### status 遷移

```
waiting → round → results → round → results → … → finished
```

- カウントダウンは独立 status にしない。`startAt` 前ならカウントダウン表示、到達後に操作解禁、とクライアントで導出
- status 更新はホストのみ（UI制御）

### waiting（ホスト設定）

| 設定 | 選択肢 | 既定 |
|------|--------|------|
| なんいど | やさしい／むずかしい | やさしい |
| ラウンドすう | 1／3／5 | 3 |
| せいげんじかん | 2分／3分／5分 | 3分 |
| わたしもあそぶ | ON／OFF | ON |

- 「わたしもあそぶ」OFF = 進行専任（`isPlaying: false`）。ラウンド参加者に含めない
- **開始条件: `isPlaying` な参加者が2人以上**（1人では競争が成立しない。1人で遊びたい場合は「ひとりで練習」へ誘導）
- ニックネーム: 共通規約どおり（8文字・重複NG・空NG）

### round

- ラウンド開始 transaction（ルーム全体）で「参加者固定・自己完結パズルJSON・startAt・endsAt・ラウンド番号・attemptId・status」を同時確定。startAt = サーバー補正時刻 + 5秒
- **startAt までは盤面とピースをカバーで隠す**（先に配信された問題が見えないように）
- プレイ中: 経過表示は残り時間バー（数字の秒読みで煽らない）。誰かが完成したら「○○さん ピタハメ！」を控えめにフィード表示
- **完成登録もルーム全体 transaction** で行う。transaction 内で「status === round」「対象が currentRound・現 attemptId」「participants に含まれる」「未登録」を確認してから `finishes/{nick}` を書く（子ノード単独の transaction だと、results 移行後に遅れて完成が追加される競合が残るため）
- ラウンド終了条件: ①参加者全員完成 ②endsAt 到達 ③ホストの「ラウンドをおわる」
- **ラウンド終了もルーム全体 transaction** で、`status: results`・`closedAt`・完成スナップショットから算出した `resultOrder` を同時確定。endsAt 到達時はホストが endsAt + 2秒（送信中の完成を拾う猶予）で実行。終了 transaction 後に届いた完成は記録されない（仕様として許容）

### results

- **表示は確定済み `resultOrder` のみを使う**（変動する finishes を直接ソートしない）
- 完成順を丸数字で表示。同着の次順位は**密順位方式**（例: ①①② — 表示が分かりやすい）。ミリ秒は表示しない
- 未完成の参加者は**列挙しない**（「できなかった人リスト」を作らない）
- 基準解をアニメーションで表示。見出しは「こんな置きかたもあるよ」（完成者の解と違ってよい）
- ホスト操作: 「つぎのラウンドへ」／最終ラウンドなら「けっかを見る」

### finished

- 各ラウンドの完成順を並べて振り返り表示。**通算得点・総合順位は出さない**
- ホスト操作: 「もういちどあそぶ」（waiting に戻る・設定保持・**gameId を更新**）／「ルームをとじる」（即時ルーム削除）
- **自動削除（共通規約準拠）**: finished 移行時に `finishedAt` を保存し、30秒後に「status === finished かつ同じ gameId」なら削除。その間に「もういちどあそぶ」で gameId が変わっていたら削除しない

## 8. RTDB データ設計

```text
pitahame_rooms/{roomCode}/
├── schemaVersion: 1
├── createdAt
├── status                 # waiting | round | results | finished
├── hostConnected / hostDisconnectedAt   # 共通規約どおり
├── gameId                 # 「もういちどあそぶ」ごとに更新（sessionStorage 照合・自動削除ガード用）
├── settings/ { difficulty, totalRounds, roundTimeMs }
├── currentRound           # 1〜
├── finishedAt             # finished 移行時（自動削除判定用）
├── usedPuzzleIds/{puzzleId}: true   # 同一ルームでの問題重複防止（RTDB 向けにマップ形式）
├── players/{nick}/ { isHost, isPlaying, joinedAt }
└── rounds/{n}/
    ├── attemptId          # 「このラウンドをやりなおす」ごとに更新
    ├── puzzle             # 自己完結 JSON（§5。種類名参照ではなくセル座標を展開済み）
    ├── participants/{nick}: true   # 開始時に固定
    ├── startAt / endsAt / closedAt
    ├── finishes/{nick}/ { completedAt, receivedAt }
    └── resultOrder        # 終了 transaction で確定した順位スナップショット
```

- **結果は players ではなく rounds/{n}/finishes に置く**: ゲストは `onDisconnect().remove()` で players から消えるが、participants／finishes は残る
- ルーム作成・参加・ラウンド開始・**完成登録・ラウンド終了**は、いずれもルーム全体 transaction（§7 の条件確認を同一原子内で行う）

### 書き込み最小化（Spark 無料枠）

RTDB に書くのは「参加・退出／ラウンド開始／各人の完成1回／status 遷移／ルーム削除」のみ。**ピースの移動状態・ドラッグ座標・タイマーは絶対に同期しない**（各端末ローカル）。リスナーはルームルート1本ではなく、`status`・`players`・現在ラウンドの `finishes` 等に分けて購読する。

## 9. 公平性・時刻の扱い

- `completedAt` = 完成判定直後の `RoomkRTDB.now()`（サーバー補正済みローカル時刻）
- `receivedAt` = `ServerValue.TIMESTAMP`（サーバーに届いた時刻。回線が遅い端末ほど不利になるため順位の主役にしない）

### 順位確定アルゴリズム（実装で迷わないよう固定）

1. 採用時刻: `completedAt` が有限数かつ `startAt <= completedAt <= endsAt` なら採用。範囲外・欠損なら `receivedAt` へフォールバック
2. 採用時刻の昇順にソート
3. 同着判定: **同着グループ先頭との差が 1000ms 以内なら同着**（隣同士比較は推移律がなく連鎖するため、グループ先頭基準に固定）
4. 順位番号は密順位方式（①①②）
5. 順位・同着の計算はラウンド終了 transaction 内で行い、`resultOrder` として確定保存する

- 終了 transaction 後に届いた完成は記録されない（§7）。`completedAt <= endsAt` でも受理しない — 単純さを優先
- 性善説（DevTools での改ざんはスタッフ監視下で許容）は共通規約どおり

## 10. 切断・再接続

- 共通規約どおり: ホストは `onDisconnect().update({hostConnected:false, ...})`、ゲストは `players/{nick}` を `onDisconnect().remove()`。TTL 2分。sessionStorage 再接続
- **ラウンド中のホスト切断**: 全員に即オーバーレイ表示しラウンド中断。ホスト復帰後、**自動では finishes を消さない**（短い通信断で全員の完成が消える事故を防ぐ）。ホストがオーバーレイ上の「このラウンドをやりなおす」を押したときだけ、ルーム全体 transaction で attemptId 更新・finishes クリア・新 startAt を確定し、同じ問題を最初から再スタート。時計の途中補正はしない
- ラウンド中のゲスト切断: participants・finishes は保持。**通常参加は status === waiting のときのみ**。再接続は「既存の `participants/{nick}` に含まれる場合だけ」round 中でも players へ復帰できる（別フローとして実装）

### sessionStorage の盤面復元キー

保存キーに `roomCode / gameId / roundNo / attemptId / puzzleId` をすべて含め、**ひとつでも一致しなければ配置を破棄**する。これで「やりなおし後に古い配置が復元される」「もういちどあそぶ後に前ゲームの配置が出る」「同じ問題が再度選ばれたときに完成済み盤面が出る」を防ぐ。results 表示時・退出時・やりなおし時にも対象配置を消去する。

## 11. 文言・演出ガイド

- 完成: 「ピタハメ！」＋祝福演出（reduced-motion 対応）
- 時間切れ: 「ここまで！」→ 答え表示「こんな置きかたもあるよ」。**「ざんねん」「まけ」「できなかった」は使わない**
- 完成順は淡々と表示し、1位を過剰に称えない（競争は残すが煽らない）
- 全員完成したときだけ「ぜんいんピタハメ！」の全体祝福
- 絵文字禁止・Material Symbols・丸数字①②③・ボタンは素直な動詞（比喩なし）— いずれも共通規約どおり

## 12. ポータル・付帯物

## 15. 決定済み事項（旧・未決事項）

Codex 二重レビューを経て以下のとおり決定。

1. **問題データはインライン**: `puzzles.js` 分離は単一ファイル規約との直接衝突のため見送り。60問程度なら容量・版ずれの両面でインラインが優位
2. **収録問題数は各30問（最低20問）で十分**: 枯渇時は再巡回（§5）。数より全問検証済みを優先
3. **「ミックス」難易度は v2 送り**: 出題順・比率・制限時間の仕様決定が増えるため、実機確認後に検討
4. **ピース色パレット**: 13色の具体値（隣接コントラスト・色覚対応）のみ実装時確定として残す
