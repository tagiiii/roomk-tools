## 着手可能（Tier A・機械検証で閉じる・scripts/ のみ・変更禁止パス外）

### A1 — SEC-1 を複数行 innerHTML 補間に対応（旧 P1-1）
- **根拠**: `scripts/lint.sh:63`（SEC-1 は行単位 grep）。単一行 `.innerHTML…${…}`=7箇所しか見ず、複数行テンプレ=80箇所は機械保証ゼロ。
- **重要（Codex 較正）**: 「80件の脆弱性」ではない。**現状は全箇所が手動 `esc()` 済みで稼働脆弱性なし**。これは検査範囲の穴。すべての innerHTML が外部入力 sink でもない。
- **アクション**: SEC-1 を awk/python で複数行テンプレ内の各 `${…}` が `esc()`/`escapeHtml()` で包まれるか判定するよう拡張。`A-8 draft-lint.sh` が「SEC-1 と同型」を謳うため共通ロジック化で二重メンテ回避。
- **受入条件**: unsafe / safe / `esc()`済み の複数行 fixture で ①未エスケープを ERROR 検出 ②現行 apps/* 全体は偽陽性ゼロ ③属性順・改行差で誤検知なし。機械検証で完結。

### A2 — content-audit の coverage 拡張（旧 P3-1）
- **根拠**: `scripts/content-audit.mjs:155-314`（collectEntries は20アプリのみ）。未対応12アプリ（計~890件）: jitsuwa126 / iisen100 / ishin100 / word-wolf100 / ito72 / magire60 / ikutsu51 / pittari50 / uso50 / value30 / koedake12 / kyoumi142。

## 実バグ・要 sandbox 実測 → 確認後 Tier B（Codex の推奨着手順）

### B1（最優先）— hint-de-pinto: answer フェーズ離脱で進行不能（旧 P4-1）
- **根拠**: `apps/hint-de-pinto/index.html:1103-1138`（handleAnswer に回答者不在チェックなし）、`:356-384`（screen-answer にホスト救済ボタンなし）、`:989-1006`（clue-input には `hostCloseClueInput` 救済が有る）、`AGENTS.md:200-202`（離脱スキップはラウンド開始時判定のみ）。
- **Codex 較正**: 証明できているのは主に **answer 開始後**の離脱。「無限待機」ではなく**「通常UIで進行不能」**と表現。救済は回答強制でなく **再選択・スキップ・安全終了**。
- **受入条件**: authorized-sandbox で host/guest 実測（回答者を answer 中に切断→ホスト操作でパス扱い→次ラウンド/終了へ・盤面整合・二重遷移なし）。

### B2 — pittari-meter: goToTop の片付け漏れ（旧 P2-1）
- **根拠**: `apps/pittari-meter/index.html:1593-1612`（goToTop が `_hostDisconnectTimer`(L861) と切断オーバーレイを clear しない）。兄弟4本（iisen-show:1426 / kakure-number:1345 / tatoe-gp:1871 / uso-jisho:1674）は clear 済み。到達経路 `:1380`。

- **受入条件**: sandbox で、切断オーバーレイ表示中にホストがルーム削除→ゲストが TOP 復帰時にオーバーレイ消滅・カウントダウン停止・2分後の spurious alert が出ないこと。

### B3 — codenames: 購読エラーの生メッセージ露出（旧 P4-3）

- **アクション**: onError を stub して発火確認 → 固定の子ども向け文言に置換（技術詳細は console.error）。

### B4 — iisen-show: 切断カウントダウン初期値（旧 P4-2）

## 判断待ち（別レーン・P票①→②の順）

作戦会議のアプリ選択（観点7）を解くための停止ゲート。P8-1（sakusen 19カードが同一タグのみ）・P8-2（自己開示の交互運用の手がかり不足）は**独立 finding にせず、この2票の根拠に統合**（Codex 判定: 共通タグは現行仕様でありそれ自体は欠陥でない）。決定は Tier D だが、**承認後のポータル実装は通常 B**。

### P票①（先）— 非序列の支援機会語彙の確定
- **判断する一文**: ツール選択の語彙を、子どもの固定ラベルではなく「その日の本人の希望＋観察可能なセッション条件（所要/人数/発話量/自己開示の深さ）」で構成してよいか。
- **推奨案**: 語彙を最小の非序列セットに絞り、構造項目は P票②へ分離（承認面を小さくし部分承認を通しやすく）。
- **絶対条件**: 「不安が強い子」等の子ども属性ラベルを語彙に含めない。「話さなくてよい/弱い関心/パス」を灰色・末尾に置かず同格に。

### P票②（後）— ポータル選択メタデータ項目の確定
- **判断する一文**: `data-scenes`（場所）を残し、選択メタ属性（duration / party / voice / disclosure / record / opt_out）をスタッフ閲覧面に足すスキーマで確定してよいか。
- **Codex 較正**: **disclosure を3段階スコアにしない** → 観察可能な項目に分解（過去想起の要否 / 個人情報の要否 / 全体共有の要否 等）。`axis`（4軸）は人間のマッピング確定後のみ・値は AI が推定しない。
- 子ども向け画面には出さない。変更は `data-scenes` への追加のみ（後方互換）。
