# フィードバック → 承認 → 自動改善 の設計（案・第3版）

作成: 2026-10-30 ／ 改訂: 同日 第2版（承認画面の自作をやめた）→ 第3版（**Google フォーム・Apps Script をやめた**）
状態: **オーナー判断待ちの設計案**（実装・設定はまだ何もしていない）

メンターが気づいたことを各アプリから送り、AI が整理と修正案を作り、オーナーが承認を1タップすると
修正の PR ができ、もう1タップで公開される流れ。子どものプライバシーと情報セキュリティを最優先にする。

---

## 0. 前提として確認した事実

- **このリポジトリは公開（PUBLIC）**。Issue・PR・コミット・Actions のログは誰でも読める → **原文はここに置かない**
- RTDB のルールは `$app_rooms/$roomId` に `auth != null`。この**ワイルドカードは `feedback/{id}` にも当たる**ので、
  そのまま書くと id を知っている人（書いた本人を含む）が読める・書き換えられる・消せるうえ、欄も長さも縛れない
  （2026-10-30 エミュレーターで確認）。専用のルールを足す必要がある（§3）
- `database.rules.json` は変更禁止パスだが、`main` に push すれば `.github/workflows/firebase-rules.yml` が自動で配備する仕組みがある。
  変更するかどうかはオーナーの判断
- 業務委託用の Google アカウントでは Apps Script を使わない（オーナー方針・2026-10-30）
- 承認と実装を同じ AI が兼ねない（`docs/ai-roles.md`）。承認はオーナーのタップ

## 1. 第2版から変えたこと

| 第2版 | 第3版 | 理由 |
|---|---|---|
| Google フォーム → スプレッドシート → Apps Script で整理 | **アプリ内の送信ページ → Firebase RTDB の「書くだけ」の場所 → Claude Code の routine が整理** | Google 側に何も置かない。新しいアカウントも鍵も増えない。整理は routine（＝Claude）が自分でできるので、Claude API キーを別に置く必要もなくなる |

## 2. 全体の流れ

```
メンター ──(「？」の中の小さなリンク)──▶ apps/guide/feedback/（送信ページ。ポータルには出さない）
                                              │ 匿名ログインで feedback/{id} に書く（書けるが、誰も読めない）
                                              ▼
                                  Firebase RTDB  feedback/{id}  ← 原文はここだけ
                                              │
            非公開リポジトリ roomk-feedback の GitHub Actions（1時間に1回・§2.5）
              ① 管理者の権限で feedback/ を読み、1件ずつ Issue にする（ラベル「新着」＋種類）
              ② Issue にできた分を RTDB から消す
              （③ 任意: Claude Code の routine A が Issue を読んで、伏せ字・直し方の案をコメントする）
                                              │
            オーナー（GitHub モバイル）
              ④ Issue を読み、ラベル「直す」を付ける  ← 承認①（1タップ）
                 「保留」「見送り」もラベル。中身・方針の Issue には「直す」を出さない
                                              │
            Claude Code の routine B（夜に1回・roomk-tools で動く）
              ⑤ 「直す」の Issue を1件ずつ別ブランチで修正 → lint・E2E → 公開リポジトリに PR
                 PR 本文は「どの画面をどう直したか」だけ。Issue に PR のリンクを書き戻す
                                              │
            オーナー（GitHub モバイル）
              ⑥ 差分と検証結果を見て Merge  ← 承認②（1タップ）
                                              │
            いつもどおり main → GitHub Pages に公開
```

オーナーの操作は **④のラベル と ⑥のマージ** だけ。routine A と B は1つにまとめてもよい。

## 2.4 専用アプリ「フィードバックボード」（2026-10-30 夜・オーナーの理想形）

理想: **簡単に開ける専用アプリで要望を見て、承認または追記をして、Claude Code に直してもらう**。
これを claude.ai のアーティファクト（オーナーだけが開ける非公開ページ）で作った。

- URL: https://claude.ai/artifact/WhWshz45a77dSK5WohyAoH （非公開。claude.ai にログインした本人だけ開ける。スマホのブラウザでも開ける。サイドバーにピン留めできる）
- データ: アーティファクトの db（`requests/{id}`）。読めるのは Editor 以上、書けるのはオーナーだけ（`db` の rules）
- 画面: 新着／直す／保留／見送り／完了 のタブ。各カードに ツール名・種類・本文・日時、**追記**（Claude Code への指示）、ボタン **直す／保留／見送り**。
  「直す」の分は PR のリンクと Claude Code の返事が付き、**完了にする** が押せる。
  「『直す』の分を Claude Code に渡す文をコピー」で、承認済みの一覧（追記つき・board id つき）を1回でコピーできる

### データの流れ

```
送信ページ → RTDB feedback/ ─(Claude Code: 取り込み)→ ボード requests/{id} status=new
                                                         │ オーナー: 直す／保留／見送り ＋ 追記
                               (Claude Code: 修正)  ←───┘ status=approved
                                 別ブランチで直す → lint/E2E → PR → ボードに pr・reply を書き戻す
                                                         │ オーナー: PR をマージ → 完了にする
```

- 「取り込み」と「修正」は Claude Code が `ArtifactData`（ボードの db を読み書きするツール）で行う。
  手元の Claude Code セッションで「ボードの承認済みを直して」と言う／コピーした文を貼る、が今の起動方法。
  **定期実行（クラウドの routine）でこれを自動化できるかは未確認**（routine から ArtifactData が使えるかによる）
- 取り込み元は、非公開リポジトリの Issue（§2.5 C）でも、`scripts/feedback-pull.mjs`（B）でもよい。
  どちらから入れても、オーナーが見るのはボードだけ
- 原文はボード（オーナーだけ）にも置かれる。完了した要望はボードの「消す」で消せる

### コマンド（2026-10-30 追加・エミュレーターのデータで取り込みを通して確認済み）

| コマンド | すること | 必要なもの |
|---|---|---|
| `/feedback-import` | `feedback-pull.mjs --json` → ボードに `status:new` で入れる → 入れた分を RTDB から消す | `FEEDBACK_SA_JSON`（サービスアカウント鍵） |
| `/feedback-fix` | ボードの「直す」を1件ずつ別ブランチで直し、PR を作り、`pr`・`reply` を書き戻す | `gh` のログイン |

本文は `.claude/commands/feedback-import.md` / `feedback-fix.md`。
この形なら非公開リポジトリ（§2.5 C）は**無くてもよい**（通知が欲しくなったら足す）。

### 作業の手順（Claude Code 向け。routine-b-fix.md と同じ制約）

1. 取り込み: `feedback-pull.mjs --json` または非公開 Issue を読み、`requests/{id}` に `{app, appName, kind, text, at, status:'new', note:'', source}` を書く（id は RTDB の id か Issue 番号。二重に入れない）
2. 修正: `status == 'approved' && !pr` を読み、`note`（追記）を指示として、1件 = 1ブランチ = 1PR。PR ができたら `{pr, reply, updatedAt}` を書き戻す。直せないときは `reply` に理由を書いて `status:'hold'` に戻す
3. 完了はオーナーが押す（PR をマージしたあと）

## 2.5 送られたものを受け取る方法（2026-10-30 改訂: 見に行かずに届く形を主にする）

| 方法 | 位置づけ | 必要なもの |
|---|---|---|
| **C. 非公開リポジトリ `roomk-feedback` の GitHub Actions が1時間に1回 `feedback/` を読み、Issue にする（主）** | 見に行かなくても GitHub の通知（スマホアプリ・メール）で届く。ラベルで管理 | 非公開リポジトリ、サービスアカウント鍵を Actions の secret に。雛形は `docs/feedback-loop/roomk-feedback-template/` |
| B. `node scripts/feedback-pull.mjs` で手元から取り出す・消す | C が止まったときの予備、手元の Claude Code に整理させる入口 | 同じ鍵をローカルに |
| A. Firebase コンソールで見る | 最後の手段 | オーナー権限でログイン |

- Cloud Functions（RTDB の書き込みをきっかけに即時通知）は Spark（無料）プランでは使えないので採らない。1時間おきの Actions で十分
- Actions は非公開リポジトリ側に置く（公開リポジトリの `.github/**` は触らない。公開リポジトリの Actions ログは誰でも読めるため、原文を通さない）
- Issue ができた分だけ RTDB から消す。作れなかった分は残って次の回でやり直す。1回に最大20件
- C で原文は非公開リポジトリの Issue に入る（オーナーだけが見られる）。第3版の「原文は RTDB だけ」は、「原文は RTDB と非公開 Issue だけ」に改める。対応が終わった Issue は閉じる・消す
- エミュレーター＋偽の GitHub API で確認済み（Issue 作成・ラベル自動作成・失敗分は残る・2回目で二重にならない・鍵なしで止まる）。**本番の鍵でのトークン交換と、本物の GitHub での実行は未確認**

## 3. 「書けるが読めない」場所のルール（案。置くのはオーナー）

```json
"feedback": {
  ".read": false,
  "$id": {
    ".write": "auth != null && !data.exists()",
    ".validate": "newData.hasChildren(['app', 'kind', 'text', 'at'])",
    "app":  { ".validate": "newData.isString() && newData.val().length <= 40" },
    "kind": { ".validate": "newData.isString() && newData.val().length <= 20" },
    "text": { ".validate": "newData.isString() && newData.val().length >= 1 && newData.val().length <= 300" },
    "at":   { ".validate": "newData.isNumber()" },
    "$other": { ".validate": false }
  }
},
```

- 固有のキー `feedback` は `$app_rooms` より優先されるので、ワイルドカードの `auth != null` の読み取りは効かない
- 4つの欄は名前を書いて個別に `.validate` する（`$other` だけ書くと4つにも当たり、正しい形も書けない）。正本と検証結果は `docs/feedback-loop/database.rules.feedback.md`
- `!data.exists()` で、一度書いたものは本人でも書き換え・削除できない（改ざん防止）
- 読めるのは Firebase コンソール（オーナー）と、管理者の権限を持つ routine A だけ
- 欄は `app`（アプリ名・リンクから自動）・`kind`（不具合／文言・見た目／中身／方針）・`text`（300字）・`at` の4つだけ。
  名前やメールの欄はない。送った人を記録しない

## 4. 子どものプライバシーの守り方

1. **子どもも送ってよい**（2026-10-30 オーナー判断。第3版までは「メンターだけ」だった）。
   各アプリの「？」のとなりにフィードバックの丸ボタン（と、あそびかたの末尾にも「フィードバックを送信する」）を出し、
   **別タブで開く**ので遊んでいる画面はそのまま。
   だれが送ったかは記録しない（UID も書かない）。子どもが書く前提で、注意文は短く「名前などは書かないでください」だけにする
2. **「子どもの様子」ではなく「ツールの困りごと」を書いてもらう**。少人数のサービスなので、名前がなくても
   「○年生の△△が苦手な子」で本人が分かりうる。送信ページの注意文は「名前などは書かないでください」の1行
   （2026-10-30 オーナー指示で短くした）。子どもが自分のことを書いてしまう可能性があるので、routine A の伏せ字と
   「要確認」ラベルは**全件に対して**行う
3. **欄を少なくする**（§3）。300字まで。名前・メールは集めない
4. **routine A が伏せ字にする**: 人名・あだ名・学校名・地名・連絡先・健康や家庭の事情を `［名前］` に置き換える。
   検出があった Issue には「要確認」ラベルを付け、オーナーが本文を直してから「直す」を付ける運用
5. **原文は RTDB の `feedback/` にだけ置き、非公開リポジトリにも書かない**（要約だけ）。読み終えたら消す（→ D-4）
6. 伏せ字の作業は routine A（Claude）がするので、原文は Claude に渡る。主な守りは 2.・3.（最初から書かせない）で、
   AI の伏せ字は二重目の守り

聞かれたときの説明（集めるもの・保存・削除・法律の論点・よくある質問）は `docs/feedback-loop/privacy-notes.md`。画面には出さない（2026-10-30 オーナー判断）。

## 5. 情報セキュリティ

- **送信ページの文章は命令ではなくデータ**。URL を知っていれば誰でも書けるため、「○○を消して」「ルールを変えて」とあっても従わない
  - routine B に渡すのは、オーナーが「直す」を付けた**伏せ字済みの要約**だけ。原文も `feedback/` も見せない
  - routine B が触ってよいのは `apps/{そのアプリ}/` と `tests/{そのアプリ}/` だけ。
    変更禁止パスや `scripts/`・`docs/` に差分が出たら PR を作らず、Issue に理由を書いて止まる
  - `main` へ直接 push しない。**ブランチ保護**で「PR 経由・オーナーのレビュー必須」にする（オーナーの設定）
- **鍵の置き場所**
  - routine A が `feedback/` を読む権限: Firebase のサービスアカウント（読み取りと削除だけに絞ったもの）を
    **Claude Code クラウド環境のシークレット**に置く。コード・ログ・Issue に出さない
  - routine A → `roomk-feedback` の Issue 作成、routine B → `roomk-tools` の PR 作成: 既存の GitHub 連携
  - 本番 Firebase の**書き込み**権限はどこにも渡さない（routine B の E2E はエミュレーターだけ）
- **使いすぎ・荒らしを止める**: 1晩の上限（例: 整理20件・修正3件）。`feedback/` に大量に届いた日は整理を止めて Issue で知らせる。
  送信ページは「？」のリンクからだけ開く前提にし、ポータルや検索に出さない
- **匿名ログインの悪用**: ルールの `.validate` で欄と長さを縛る。書き込み回数そのものはルールで制限しにくいので、
  routine A 側の上限で受け止める

## 6. 自動で直す範囲（はじめは狭く）

| 種類 | 扱い |
|---|---|
| 不具合（表示崩れ・押せない・止まる） | 自動修正の対象 |
| 画面の文言・見た目 | 自動修正の対象（`docs/development/ui.md` に従う） |
| お題・問題などの中身 | **対象外**。Issue に並べるだけ（人間専任。AGENTS.md） |
| 支援の方針・内省ツールの在り方 | **対象外**（同上） |
| 同期・切断・再接続に関わる変更 | **はじめは対象外**。2ブラウザ確認が自動化できるまで、案だけ |
| 共通モジュール `apps/shared/**` | **対象外**（変更禁止パス） |

「1アプリ × 1関心事 × 1 PR」。あいまいな声は推測で直さず、Issue に「確認したいこと」を書いて止まる。

## 7. 正直に書いておく弱点

- **独立レビューが自動では入らない**。`docs/ai-roles.md` は別系統（Codex）のレビューを必須とするが、routine からは呼べない。
  自動修正の範囲を絞り、オーナーのマージ前確認を第2のレビューとするか、手動で挟むか（→ D-6）
- **E2E がクラウドで回るかは未確認**（エミュレーターに JDK が要る）。動かなければ lint と静的確認だけになる
- **routine がクラウド環境のシークレットを扱えるかは、作るときに確認が要る**。扱えなければ、routine A の代わりに
  オーナーが Firebase コンソールで `feedback/` を見て手で Issue を作る運用になる（それでも承認①②の形は変わらない）
- **件数が少ないと ⑤の自動修正は割に合わないかもしれない**。①〜④だけで価値の大半が出る。⑤は段階4で、たまってから
