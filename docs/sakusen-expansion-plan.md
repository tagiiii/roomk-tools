# 作戦会議コンテンツ拡充計画（第2期・2026-08）

2026-08-06 策定。作戦会議（週1回30分の1on1）のコンテンツ拡充と「悩まず選べる仕組み」の計画正本。

- 第1期の正本: [content-plan.html](./content-plan.html)（実装済み8本＋共通原則）
- 選び方の語彙・メタデータ確定案: [sakusen-selection-proposal.md](./sakusen-selection-proposal.md)（P-8/P-9・判断待ち）
- 参照した現場資料: 進行スライド（2026-07-02 版 PDF）。**room-K 公式の配布物ではなく、本計画の依頼者（ユーザー）の自作**。個人の予定内容はこの文書に転記しない

## 1. 背景と課題

現場でよく聞く声（この計画が解決対象とするもの）:

1. **準備に時間がかかる** — メンターが毎回、進行スライド（ジブンチェック・今日は何する？・予定表など）を自作している
2. **どのコンテンツを実施すればいいかわからない** — 選び方の指針がない
3. **そもそも何があるか知られていない** — ツールの発見性の問題
4. **子どもに合わせすぎてゲーム時間化する** — ねらいを決めてから選ぶ構造がない

## 2. セッションの型（実態）

| 枠 | 時間 | 現状 |
|---|---|---|
| 雑談（前回の振り返り） | 3分 | 口頭 |
| チェックイン | 5分 | talk-card 等を活用 |
| ジブンチェック | 1〜2分 | スライドで「心」の5段階を提示し番号で回答 |
| 今日は何する？ | — | スライドで6択提示: ①ゲーム ②おしゃべり ③学習する ④自分について知る ⑤おまかせ ⑥したいことがある |
| コンテンツ実施 | **15分** | 本計画の主戦場 |
| 予定の確認 | 5分 | スライドの週間表（午前/午後/するべきこと）を手入力 |
| お知らせ | — | 口頭・スライド |

**参加環境**: 子どもはカメラOFF・マイクONが基本。**チャットのみ参加の子どももいる。**
そのため選択肢を番号で提示し、数字だけで答えられる工夫が現場で定着している。

**注**: 上記の型と6択はユーザー自作の運用であり、公式標準ではない。他のメンターは各自ばらばらに準備している（＝準備時間問題の実態）。裏を返せば、進行ボードが事実上の共通型になり得るため、6択の設計品質がそのままレバレッジになる。6択の評価・再設計は 2026-08-06 に決着（5章 Phase 0・9章）。

- **リポジトリ**: 現リポジトリ（room-K tools）に追加する。作戦会議専用の分離はしない。発見性は Phase 0 の進行ボード＋`data-scenes` フィルタで解決する
- **優先順位**: 下記フェーズ順。ユーザーの一任を受けて計画側で決定（理由は各フェーズに記載）
- **役割分担**: [ai-roles.md](./ai-roles.md) に従う（司令塔が計画・実装プロンプト作成、実装モデルが実装。モデル固有名はあちらにのみ書く）
- **プログラムとの共用**: 既存ツールを作戦会議でも使う運用は継続する。`data-scenes` の複数シーン付与で表現する

## 4. 共通設計要件（作戦会議向け新規コンテンツすべてに適用）

1. **チャット番号回答で参加成立** — 選択肢は丸数字（既存共通規約「選択肢・カードの番号付け」）。音声で答えられない子がチャットに数字を打つだけで進行できることを、作戦会議系では明示的な受け入れ条件とする
2. **15分枠に収まる** — 所要10〜15分を上限に設計。超える構成は「2回に分ける」前提を AGENTS.md と早見表に明記する
3. **既存の哲学ガードを引き継ぐ**（content-plan.html:140-150）— 非序列・パス同格（「きょうは えらばない」を第1級の値に）・本人がその場で選ぶ・推定/保存/採点/推薦をしない・個人情報を入力させない
4. **受験系は対象宣言つきの意図的例外** — 面接・小論文は共通コンテンツガイドライン「学校・勉強を連想させる内容を使わない」の例外にあたる。kyapa-graph と同じく、アプリ自身の AGENTS.md に対象（受験を控えた本人が希望した場合に使う）を宣言し、ポータルでは `data-scenes="sakusen"` のみに置く
5. **共通規約一式** — stats.js / howto.js / `data-scenes` / updates.json / 早見表1行 / Material Symbols（絵文字不可）/ lint エラー0

## 5. フェーズ計画

### Phase 0: 作戦会議スライド（進行ツール）—【2026-08-06 見送り・破棄】

> **見送りの記録**: 実装・二重レビュー・検証まで完了したが、ユーザー実機確認で「進行の器としての使い勝手が悪い」と判断し、**未コミットのまま全部破棄**（同日）。
> **教訓**: 進行のオーケストレーションは、その場で順序を変える・1枚足す・文言を変えられる**スライドが構造的に勝つ**。アプリが勝つのは「双方向性・選択肢・リンク・組み立て」のあるコンテンツ側だけ。以後のアプリ化は進行の器ではなくコンテンツ（15分枠の中身など）に集中する。どのコンテンツをアプリ化するかは後日検討（10章）。
> 以下の設計記録は将来の参照用に残す（3択・予定の確認3ステップ・番号一意性の不変条件などの設計はスライド運用や他アプリに転用可）。

**名称決定（2026-08-06）**: 表示名「作戦会議スライド」・フォルダ名 `sakusen-slide`（各ゲームの説明用 `slides.html` とは別物なのでフォルダ名で区別）。

**ねらい**: メンターのスライド自作を丸ごと置き換える進行ツール。課題1〜4のすべてに同時に効く、最もレバレッジの高い1本。

- **形式**: オフラインパターン（DB なし・永続化ゼロ）。メンターが画面共有して進行する
- **見た目**: 現行スライド PDF の見せ方を踏襲する（1画面1メッセージ・大きな文字・画面を順に送る操作）。スライドの分かりやすさを設計として引き継ぐ
- **画面構成**（実スライドの流れをそのまま踏襲）:
  1. TOP（きょうの流れの一覧）
  2. チェックイン — talk-card へのリンク（または軽いお題を内蔵）
  3. ジブンチェック — 見出しは**「今日の調子はどのへん？」**（2026-08-06 ユーザー決定。「心」限定でなく体調も含む「調子」）。5段階を丸数字つきで表示し、チャットに数字を打てば回答完了。**記録しない**。5段階は現行のまま（「いまは いいたくない」は追加しない。2026-08-06 ユーザー判断）
  4. 今日は何する？ — **3択**を提示（2026-08-06 確定。6択→3択への圧縮はユーザー判断）:
     **①やりたいことがある ②メニューから選ぶ ③おまかせ**
     選択肢は「内容」ではなく「決め方」で切る。ゲーム・話す・自分について知る・学習するの4カテゴリは②で開くメニューの**見出し**に降格し、選ぶ負担を3択分に抑えつつ全体像は見えるようにする。文言は中学生向けでよい（共通の子ども向け文言ルールより上の学年設定。アプリ AGENTS.md に意図的逸脱として記載する）
  5. ツールメニュー — ②で開く画面。カテゴリ見出しの下にツールへのリンクを並べる（下記マッピング表）。**①（やりたいことがある）は子どもの当日の持ち込みを指す自由枠で、ツールを介さずそのまま実施する**（計画を立てることではない。必要ならメニューも開ける）。③はメンターがこのメニューか早見表から選ぶ
  6. 予定の確認 — **例外ベースの3ステップ**（2026-08-06 再設計。「7日ぶんを順に聞く」方式はテンポが悪いため廃止）:
     - (1) いつもの予定（毎週あるもの）の確認 — ①いつもどおり ②ちがう日がある ③いつもの予定はない。毎週同じ予定がある子（登校・塾・習い事など）は1往復で終わる。**いつもの予定の中身はメンターの手元メモが持ち、アプリは保存しない**。画面文言は「いつもの予定」で中立にし、学校等の固有の語を出さない
     - (2) ほかに予定がある日・かわる日 — 曜日チップ ①月〜⑦日＋**⑧とくにない**（同格）。選ばれた日だけ入力欄が開き、空欄は空欄のまま
     - (3) やることメモ — 日にちと紐づけない自由リスト
     - **保存しない**（DB・localStorage に個人の予定を残さない）。画面内の例文は架空の中立なものだけを使い、実在の個人の予定内容を例に使わない
  7. お知らせ — 先頭に**「つぎの作戦会議」の日時欄**を固定で置く（次回日程はお知らせで伝える。2026-08-06 ユーザー決定。予定の確認には置かない）。続けてフリーテキスト欄（その場入力・保存なし）
- **設計上の判断済み（2026-08-06 ユーザー判断）**:
  - ジブンチェックは現行の5段階のまま
  - 「今日は何する？」は3択（やりたいことがある／メニューから選ぶ／おまかせ）。コンテンツ4カテゴリはメニュー見出しへ
  - **メイン＋ミニ2枠制は v1 では採用しない**。メンター発のねらい（受験準備・SST 等）は、6択を黙って飛ばすのではなく「⑥おまかせ」への同意を取るか、次回のメインを子どもと合意して決める運用とし、この心得はアプリ AGENTS.md にのみ書く（画面には出さない）。実機の様子を見て2枠制は再検討
- **設計上の判断待ち（ユーザー承認が必要）**:
  - ツールメニューのマッピング表（下記ドラフト・4カテゴリ構成）の内容承認

**ツールメニュー マッピング表（ドラフト・承認待ち）**

3択の①（やりたいことがある）は当日の持ち込みの自由枠でツール不要。③（おまかせ）はメンターがメニュー全体か早見表から選ぶ。②で開くメニューは以下の**4カテゴリ**で構成する（2026-08-06 のアプリ整理を反映）。

| メニュー見出し | 対応ツール（1on1で成立するもの) |
|---|---|
| 話す | talk-card / kyoumi-sugoroku / docchi |
| ゲーム | quiz / pita-hame（ソロ）/ kanji-sagashi / machigai-sagashi など。早見表の1on1可のゲームへ誘導 |
| 自分について知る | kimochi-map / suki-type-check / tsuyomi-card（1枚ずつ3択方式に刷新済み）/ value-card |
| 学習する | quiz（難読地名等）/ e-board（外部リンク）。Phase 4 で拡充 |

- **チャレンジ（目標・計画）カテゴリは v1 では置かない**: challenge-tane・sakusen-kaigi が 2026-08-06 に削除されたため（使いづらさによる一旦削除。bamen-card・mirai-hikidashi・mienai-ganbari も同時削除）。子ども発のチャレンジは3択の①で受け、目標・計画ツールの再挑戦は後続フェーズで行う（Phase 1 の受験系が最初の再入居候補）
- ikutsu-ieru は掲載保留（チャットのみ参加の子がツール上で回答できないため。改修後に再検討）
- kotoba-asobo は掲載保留（1セッション45分設計。15分分割対応後に「学習する」へ）

このマッピングは**人間（ユーザー）が確定する**。アプリは子どもの選択を保存・学習・推薦に使わない（その場のリンク集を出すだけ）。

**優先理由**: 準備時間の主因（スライド自作）を直接除去でき、6択が「ねらいを決めてから選ぶ」順序を構造化するため課題4にも効く。実装リスクが低い（永続化ゼロ・静的中心）。

### Phase 1: 面接・小論文（受験対策）— 時間軸の制約あり

**ねらい**: 受験前の子どもとの面接対策・小論文対策をツール化する。推薦入試は秋に始まるため、**9月中の実機投入を目標**にする。

- **めんせつのじゅんび（仮名）**: 長所・短所・志望動機を「選択肢から選んで組み立てる」ツール
  - 長所は tsuyomi-card の42枚を素材に流用（「あるかも」の非断定から「面接で言い切る形」への変換を支援する、が中核価値）
  - 短所は「言い換えペア」（例: 慎重すぎる ↔ ていねいに確認できる）を選択式で
  - 志望動機はパーツ（きっかけ／やりたいこと／その学校でできること）を選択＋穴埋めで組み立て、完成文をコピー（チャット・メモ貼り付け用）
  - 永続化ゼロ＋JSON 書き出し（旧 sakusen-kaigi の方式。アプリ本体は 2026-08-06 削除済みだが方式は有効）
- **しょうろんぶんの したがき（仮名）**: お題に対する考えを「主張→理由→具体例」の型で組み立てる
  - 各パートを選択肢＋短い穴埋めで埋め、アウトラインをコピーして本文執筆（紙・ドキュメント）へ渡す
  - 「書き方の型を見せる」ことに限定し、本文の自動生成はしない
- 両方とも共通設計要件4（対象宣言つき例外）を適用

**優先理由**: 唯一、季節の締切がある領域。選択肢から組み立てる設計はチャットのみ参加の子にもそのまま機能する。

### Phase 2: ネットリテラシー — 低コストで先行投入可

**ねらい**: ネット利用に不安のある子どもに「こんなときどうする？」を伝える。

- **第1弾は quiz のパック追加**（最小コスト・実績ある形式）: シナリオ選択式「ネットのこんなとき」パック。怖がらせない・叱らないトーンで、「危ない！」ではなく「こうすると安心」の言い回しに統一
- 反応がよければ第2弾で専用アプリ（シナリオ分岐型）を検討
- Phase 1 と並行実装できる規模

### Phase 3: SST — 哲学の枠づけ確定が先

**ねらい**: 特性の強い子どもと「この場面ではどんなやり方があるか」を知る。

- **着手前にユーザー判断が必要**: SST は構造上「望ましい行動＝正解」を持ち、リポジトリの「正解を作らない」哲学と衝突する。ピタハメ（競争を意図的に残した例外）の前例に倣い、枠づけを先に決める
  - 案A: 「正解を教える」型をそのまま採用（例外として宣言）
  - 案B: 「いろんなやり方と起こりやすいことを眺めて、じぶんに合いそうなのを選ぶ」型（bamen-card の延長。優劣を付けず結果を並べる）— **計画側の推奨**
- 枠づけ確定後に具体設計へ進む

### Phase 4: 教科学習の補助 — スコープ定義から

- e-board 併用で埋まらない隙間（学習の入口・きっかけづくり）が何かを、メンターの実例を集めてから定義する。この計画では着手順の最後に置き、具体設計はしない

## 6. 選び方ガイドとの関係（P-8/P-9）

- スライドの6択は、P-8 で確定案としていた「その日の本人の希望」語彙と同じ役割を、ユーザー自作の運用としてすでに果たしていた実例（公式標準ではない）。2026-08-06 に「3択（やりたいことがある／メニューから選ぶ／おまかせ）＋メニュー見出し4カテゴリ」へ再設計済み。P-8 の再確認（2026-08-10 予定）では、この**3択＋見出し語彙**と突き合わせて統合することを推奨する
- P-9 のメタデータ9属性（所要・人数・発話量など）は、Phase 0 のマッピング表と早見表の裏付けとしてそのまま活きる。承認されれば「15分枠に収まるか」「チャット番号回答で参加できるか」をスタッフ閲覧面に出せる
- 停止ゲートの趣旨（子どもの固定ラベルを作らない・AI が適合判定しない）は本計画でも不変

## 7. 進め方・レビュー体制

1. 各フェーズの実装プロンプトは司令塔が作成し、この文書に追記してから実装モデルへ委任する（第1期 content-plan.html の方式）

3. メンター実機で一巡してから次フェーズの本格着手（問題時 revert の既存運用）
4. 新アプリはすべて共通設計要件（本文書 4章）を AGENTS.md 受け入れ条件に含める
