# 洗い出しプロンプト集（監査プロンプトのカタログ）

日々「するべきこと」を洗い出すための、観点別プロンプトの正本。
2026-07-13 策定（複数エージェント調査 ＋ 別系統モデル相談の合意内容。第2稿）。

「司令塔」「実装モデル」「別系統モデル」などの役割の定義は [ai-roles.md](./ai-roles.md) が正本。
本カタログのガードレールは大半が**権限由来**（誰が決めてよいかの線引き）であり、モデル世代が上がっても緩めない。

このカタログの目的は**発見（起票候補の生成）**であって、修正でも投入でもない。
各プロンプトは**静的な読み取り（`static-only`）を既定**として走り、結果は
[kaizen-backlog.md](./kaizen-backlog.md) の Tier / 判断待ち(P-番号) に**流し込める形の
起票候補**として返す。並行して別のToDo管理は作らない。

> このカタログはプロンプトを **9回複製した束ではない**。まず「共通契約(§0)」を読み、
> 各観点は「共通契約からの差分カード」として読む。実行時は
> 「共通契約 ＋ 該当カード ＋ 実行ヘッダ(§0.1)」をエージェントに渡す。

## 0. 共通契約（すべてのプロンプトが従う前提・出力形式・ガードレール）

### 0.1 実行ヘッダ（/loop・単発ともに毎回埋める）

呼び出し側が次を渡す。渡されない項目はエージェントが既定値で補い、補ったことを出力に明記する。

```text
監査ID:   P1〜P8（P9 は発見でなく承認後の書込み工程。この無人ヘッダの対象外）
モード:   change | weekly | monthly
対象:     app名 / 明示リスト（weekly は §0.7 の選定式で機械決定してもよい）
比較範囲: base SHA..HEAD（差分監査の基準。full なら "全体"）
観察:     static-only（既定） | authorized-sandbox（承認済み隔離環境でのみ動的確認可）
上限:     5（0〜5件。無理に埋めない。no-op はこの上限に数えない＝§0.2）
```

- **既定は `static-only`。** コードとドキュメントの読み取りのみ。**本番 Firebase へ書き込む操作（匿名Auth・ルーム作成/参加・データ投入）はしない。** 動的な挙動確認が要る finding は「未検証（要 authorized-sandbox）」として受入条件に記す。
- `authorized-sandbox` は、隔離された検証環境が用意され人間が明示承認した場合にのみ。ここでも本番データには触れない。

### 0.2 実行の前提

- **読み取り専用（発見のみ）。** バックログへ直接追記しない。返すのは「起票候補」だけ。反映（Tier A/B の修正・投入・P票起票）は別工程・別プロンプト・人間承認で行う。
- **先に機械チェックを走らせる。** 対象に応じて `bash scripts/lint.sh` / `node scripts/content-audit.mjs` を実行し、**同一根因を二重起票しない**。ただし lint の偽陰性・ルールの穴（機械化できていない規約）は起票してよい（「機械チェックの拡張」という起票になる）。実行できなかった場合は skip 理由を出力に記す。
- **既存資産と照合し、状態を分岐する（必須）。** `docs/kaizen-backlog.md` の Tier A/B/C/D と「判断待ち(P-番号)」、`docs/content-candidates/`、対象の `apps/{app}/AGENTS.md` を確認し、各 finding を次のいずれかに分類する:
  - `新規` … 既出でない
  - `既存票への追記` … 既存項目に新事実・別事例を足す
  - `再発` … 一度閉じた項目が再び観測された（＝起票する）
  - `no-op` … 既出かつ新事実なし（＝起票しない。**上限5件に数えず**、末尾の重複照合サマリーに件数だけ記す）
- **0件は正常な結果。** 無理に指摘をひねり出さない。「該当なし」と明示して終える。
- **最大5件（0〜5件）。** 最低数の要求ではない（`no-op` は含めない）。同一根因は複数アプリにまたがっても**1件の横断 finding に束ねる**。件数超過時は「深刻度 → 影響範囲 → 確信度」の順で上位を選び、落とした件数を明記する。
  - この上限は AI の発見能力の制約ではなく**人間の判断キューへの流入制御**。たくさん見つけられるモデルでも上限は上げない（落とした件数の明記がその代わり）。

### 0.3 finding の固定出力テンプレート

generic なベストプラクティスだけの指摘は捨てる。**room-K の仕様、または具体的な失敗場面**を示せない finding は起票しない。各 finding は次の項目をすべて埋める:

```text
finding_id:   {監査ID}-{連番}
dedupe_key:   {scope}:{一意な短い識別子}   # 再実行時の重複判定に使う
status:       新規 | 既存票への追記(#既存ID) | 再発(#既存ID) | no-op
scope:        app:{name} | shared | portal | 横断
基づく:       観測 | 推測                    # authorized-sandbox 実測なら「観測」
根拠:         {file:line}（複数可）
版:           base {SHA} .. HEAD {SHA}／作業ツリー {clean|dirty}
機械チェック: {lint.sh / content-audit の結果 or skip理由}
再現/観察:    役割(host/guest)・画面状態・手順・期待と実際（挙動系のみ）
利用者影響:   子ども / スタッフ / どちらに、どう
深刻度:       高 | 中 | 低
確信度:       高 | 中 | 低
変更リスク:   高 | 中 | 低                    # 直したときの副作用の大きさ
提案アクション: 何をどう直すと閉じるか
受入条件:     検証方法（機械チェックID / authorized-sandbox 実測 / 人間レビュー）
提案Tier:     A|B|C|D（§0.4・アクションに付ける。目安であり毎回再判定）
判断待ち:     不要 | 要P票（理由）
```

深刻度・確信度・変更リスクは**独立した別軸**として扱う（高深刻でも低確信、などがありうる）。尺度の目安 — 深刻度: 高=子どもの体験を壊す/安全に関わる、中=使いにくいが進行可、低=軽微。確信度: 高=コード/文書で直接裏取り、中=強い状況証拠、低=推測。変更リスク: 高=同期・データ・共有仕様に波及、中=1アプリの挙動変更、低=文言/局所。

### 0.4 Tier の付け方（提案アクション基準・毎回再判定）

Tier は「指摘」ではなく「提案アクション」に付ける。カード末尾の Tier 記述は**目安**であり、毎回アクション単位で判定し直す。

| Tier | 提案アクションがこれなら | 誰が反映 |
|---|---|---|
| **A** | 既存チェックID or 自動テストと明確な受入条件で閉じる、非可視・決定的な変更 | ループ自律 |
| **B** | 承認済み方針に沿う、子ども向けUI・文言・フロー・コンテンツの可視変更（AI確認後に反映、人間の体験レビューは事後） | ループ(AI確認後) |
| **C** | UX仮説・コンテンツ不足の解釈・観点6/7・利用観察が要る事項（調査/報告のみ） | — |
| **D** | 変更禁止パス（`firestore.rules` `database.rules.json` `firebase.json` `apps/shared/**` `.github/**`）、セキュリティルール、支援方針、新規コンテンツ本体投入(D-3) など人間専任 | 人間 |

- **Tier D は「監査対象外」ではない。** 問題は報告し、変更はせず人間へ回す。
- **挙動が変わりうる修正を自動で A にしない。** 例: RTDB の transaction 化・切断処理の変更は挙動が変わりうるので A とは限らない。受入条件と検証で裏取りできて初めて A。
- P票に回すときは、曖昧な指摘の置き場にしない。**「判断する一文」「2〜3案」「推奨案」「影響」「関連 finding」**を必ず揃える（新規起票は1回の実行につき3件まで）。

### 0.5 room-K 哲学ガード（誤検出を防ぐ絶対条件）

これらに反する「改善提案」は **finding にしない**。むしろ違反していれば起票する側。

1. **内省回答・成長評価に、評価・比較・採点・数値化・証拠化・保存を「足す」提案をしない。** 内省系ツール（`kimochi-map` `mienai-ganbari` `nurie-week` `kyapa-graph` `tsuyomi-card` `suki-type-check` `challenge-tane` `mirai-hikidashi` `bamen-card` ほか）の**永続化ゼロ・リロードで消える**は正しい仕様。「保存できないのは不便」は誤検出。
   - **この禁止は「内省の回答・成長の評価」に限る。** 娯楽ゲームの得点、RTDB のゲーム進行用の一時状態、再接続のための `sessionStorage` 保存は対象外（これらを消せという提案はしない）。
2. **既知の意図的例外を切り分ける:**
   - `kyapa-graph` … 数値化・グラフ・学校語は**意図的な例外**（対象は「登校を頑張りすぎている子」専用、不登校の子には別ツール、と AGENTS.md に理由付きで明記）。哲学違反として起票しない。むしろ「対象宣言が明記された良い例」。
   - `value-card` … 順位付け・RESULT画面・html2canvas の PNG保存を持つ**設計世代の古い外れ値**。「一律に非評価か」を問うと value-card だけ NO になる。**バグではなく設計時期の差**として「意図的例外か未更新か」を切り分ける finding にする（勝手に機能削除を提案しない）。
   - `kimochi-map` … ネガティブ感情語を**意図的に収録**（上限は「つらい・しんどい」まで）。「ダーク語があるから NG」と単純判定しない。
   - `suki-type-check` … タイプの断定・全軸のパーセント表示は**意図的な例外**（旧 `sukina-map` の「診断・タイプ分けをしない」を撤廃した経緯を AGENTS.md に明記）。数値が出ること自体を哲学違反として起票しない。残っているガードレールは「タイプ間に優劣をつけない・欠点を書かない」の2つで、**そちらの違反は起票する**。
   - ※ これは**恒久免責ではない**。「その特徴が存在するだけでは finding にしない」という意味であって、強制・保存・プライバシー侵害など**新たな実害**が観測されれば、意図的例外のアプリでも起票する。
3. **メンター向けの心得・声かけのコツを子ども向け画面 / `howto.js` に出す提案をしない。** 心得は `AGENTS.md` にのみ書く（強い規約）。スタッフ向けの選び方情報も、子ども向け画面には出さない（置き場は §P7・§P8 の注記に従う）。

### 0.6 アーキ型による観点の出し分け

チェック観点はバックエンド型で変わる。無関係な型に問わない。

| 型 | 該当アプリ例 | 固有に問う観点 |
|---|---|---|
| RTDB 単一ファイル | do-mannaka, word-wolf, jinro, tatoe-narabe, kaburazu-hint, tatoe-gp, magire-eshi, uso-jisho, pittari-meter, kakure-number, koedake-theater, ikutsu-ieru, nitaku-board, name-change | transaction 原子性・切断挙動・TTL/孤立ルーム掃除・再接続・リスナー/タイマー片付け・`maximum-scale=1` 必須（`rtdb-audit` スキルの領域） |
| Firestore 分割 | checkin, vote | 終了後削除・無料枠。※両者は**本体スタブ**（howto 未組込は正常） |
| オフライン | talk-card, docchi, 内省系の大半 | RTDB 固有観点は**問わない**。`maximum-scale=1` は付けたら WARN |

### 0.7 実行契機（毎日43アプリ全件監査をしない）

| 契機 | 何を走らせるか | 対象の決め方 |
|---|---|---|
| **change** | 触ったアプリ・共有ファイルに関係する観点カードだけ | `base..HEAD` の差分から機械決定 |
| **weekly** | 43アプリを数本ずつ回し、観点2〜5を深掘り | 呼び出し側が対象を渡す。省略時は「アプリ名を昇順ソートし、`(週番号 × N) mod 総数` を先頭に **N=5 本**」を機械決定し、選んだ対象を出力に明記。未コミットの作業ツリー変更は `dirty` として `base..HEAD` と別に扱う |
| **monthly** | 観点3（コンテンツ量）・観点8（横断選択導線）を全体俯瞰 | 全体 |

## 観点別カード

各カードは §0 に**加えて**適用する差分。実行時は「§0 ＋ 該当カード ＋ 実行ヘッダ」を渡す。

### P1. セキュリティ監査

- **目的**: `lint.sh` の SEC-*/DEP-* が拾えない、設計レベルのセキュリティ懸念を洗い出す。
- **先に実行**: `bash scripts/lint.sh`（SEC-1/2, DEP-1 の既出は除外）。
- **観点固有の問い**:
  1. `esc()` は掛かっているが、そもそもユーザー入力を `textContent` でなく `innerHTML` で描く**設計上の必然性**があるか（不要な innerHTML 経路はないか）。
  2. 外部スクリプト・CDN 依存は SRI ＋バージョン固定か（**固定 integrity 値を出せる実行依存に限る**。Google Fonts / Material Symbols のような可変配信は対象外）。`@latest` は DEP-1 が拾うが、SRI 欠落は目視。前例: value-card の html2canvas / sortablejs。
  3. 秘密情報（`isWolf` 等）の露出は**性善説の範囲内**か。DevTools で見える＝脆弱、と過剰指摘しない。逆に、性善説の前提を超えて**画面に**秘密が出ていないか。
  4. `firestore.rules` / `database.rules.json` に関わる懸念は **Tier D**。報告のみ・変更しない。
- **固有ガードレール**: 性善説（スタッフ監視下）を前提に、現実的な脅威モデルで起票する。理論上の脆弱性だけの指摘は捨てる。
- **Tier 目安**: A（SRI 追加など受入条件が明確なもの）／ D（rules 関連）。

### P2. RTDB 規約・保守性監査

- **目的**: lint の REF-* が個数・存在しか見ない領域で、**RTDB 規約の実質**を満たしているかを洗い出す。`rtdb-audit` スキルと連携。
- **先に実行**: `bash scripts/lint.sh`（REF-* 既出は除外）。RTDB アプリなら `rtdb-audit` スキルの手順を併用。
- **観点固有の問い**（RTDB 型のみ）:
  1. ルーム作成・参加・開始が read-then-write でなく `transaction()` で原子化されているか。
  2. 切断挙動: ホスト `hostConnected=false`＋`hostDisconnectedAt`、ゲスト `onDisconnect().remove()`。再接続ありアプリでホストに `onDisconnect().remove()` を使っていないか。
  3. TTL/孤立ルーム掃除が joinRoom / tryReconnect / ルーム監視の各所に入っているか（REF-4 は数値2分しか見ない）。
  4. `leaveGame()` / `goToTop()` でリスナー・`setInterval`・`setTimeout`・overlay を漏れなく片付けているか（REF-5 は個数差しか見ない）。
  5. 無料枠(Spark)を超えない購読設計か（多重リスナー・ポーリング濫用がないか）。
- **固有ガードレール**: オフライン型・Firestore 型にこれらを問わない（§0.6）。Firestore/オフライン型の保守性（重複ヘルパーの再定義=REF-3 相当、状態片付け）は軽く併せて見る程度でよい。
- **Tier 目安**: 多くは A だが、transaction 化・切断処理の変更は挙動が変わりうるので**自動 A にしない**（§0.4）。

### P3. コンテンツ量・偏り・重複の棚卸し

- **目的**: お題・問題・カードの**量／偏り／重複**を俯瞰し、拡充が要る箇所と機械検査の穴を洗い出す。**候補生成はしない**（それは P9）。
- **先に実行**: `node scripts/content-audit.mjs`（exact/structural/similar の既出増加は除外）。件数は**監査時に再カウントして確認**する（末尾スナップショットは時点値）。
- **観点固有の問い**:
  1. 対象アプリが `content-audit.mjs` の `collectEntries()` に**載っているか**。未対応なら**まず「抽出追加」を1件の finding として起票**し、量・偏りの判断はその**再計測後**に行う（抽出未対応と量不足は**別 finding・別 Tier**。未対象アプリは末尾スナップショット参照）。
  2. パック内・カテゴリ内の**偏り**はないか（例: quiz は難読地名系が約1/3、難易度が d3 偏重）。
  3. **反復利用で枯渇するか**（＝単に絶対数が少ないだけでは起票しない。「1セッションで何件消費し、どの頻度で使うアプリか」を添えて、実際に枯渇が起きる場合のみ）。
  4. 禁止題材（学校/成績/登校/恋愛/暴力/ホラー/死）の混入がないか（`validate-kotoba-asobo.mjs` の BAD_WORDS は kotoba-asobo 専用なので他アプリは手動照合）。
  5. 事実系（雑学・故事・方言・由来）に出典と参照日が付いているか。
  6. **均等・完結が設計意図のもの**（kimochi-map 12×6, kotoba-tantei 30×18, docchi 17×5）に水増しを提案していないか（哲学ガード）。
- **Tier 目安**: C（棚卸し・報告）。抽出追加は A/B、本体投入は **D-3（人間専任）**。

### P4. 機能品質・異常系・切断復帰のシナリオ監査

- **目的**: 「品質」を**正常系・異常系・復帰・レスポンシブ**に限定して壊れる場面を洗い出す。
- **観察モード**: 既定 `static-only`（コード読解で仮説を立てる）。実挙動の裏取りは `authorized-sandbox` のときのみ行い、環境がなければ finding を**「未検証（要 authorized-sandbox で host/guest 実測）」**として残す。**本番 Firebase にルームを作らない。**
- **観点固有の問い**:
  1. エラー時に子ども向けの平易な案内が出るか（技術用語・スタックトレースを見せていないか）。
  2. 認証失敗・通信断で無限リトライや操作ロックに陥らないか（B-20 系: authReady は一度 reject すると再試行で直らない → リロード導線が正しい）。
  3. RTDB: host/guest 間の同期・再接続・退出の設計に穴がないか（実測は sandbox 限定）。
  4. 最低/上限人数を満たさないと開始ボタンが disabled か。待機画面に「今なにを待っているか」の説明があるか。
  5. `600px` 以下のモバイルとPCで崩れる箇所がないか。
- **Tier 目安**: A（バグ修正で受入条件が明確）／ B（案内文言の追加・変更）。

### P5. セッションUX監査（スタッフ視点・子ども視点の二視点）

- **目的**: スタッフ用と子ども用を別々に監査すると同じ問題を二重報告しがち。**同一の利用シナリオ（開始→進行→終了→もう一度）を二視点で**評価する。
- **観点固有の問い**（各問いに**適用条件**を付け、当てはまらないアプリには問わない）:
  - *スタッフ視点*:
    1. 見た目・遊び方が変わる改修なのに `updates.json` への告知が漏れていないか（`base..HEAD` に該当コミットがある場合のみ）。
    2. 画面共有前提の導線が分かるか（ルームコードの大きな表示・コピー・最低人数明示）— **RTDB ゲームのみ**。
    3. ルール説明が要る複雑さなのに `slides.html` が無いか — **RTDB ゲーム等、進行が複雑なもののみ**。内省・オフライン型に slides 不在を起票しない（末尾に保有13本のリスト）。
    4. メンター向け注意書きが画面 / howto に漏れ出していないか（§0.5-3）。
  - *子ども視点*:
    5. 初見でボタンの意味が分かるか。比喩の派生語で操作名を濁していないか（比喩は導入1回、操作は素直な動詞。ルールは各アプリ AGENTS.md）。
    6. **手詰まりになる画面**で戻る導線が無いか（＝全画面に「戻る」を要求するのではなく、戻れないと詰む深い画面に限る）。
    7. 番号(①②③)が視認でき、コピー機能の表記と UI が一致しているか（番号付けが要る一覧画面のみ）。
    8. 「選ばない/わからない/答えない」が正式な選択肢として**同格**に置かれ、グレーアウト・強制がないか — **内省系のみ**（娯楽ゲームには N/A）。
- **固有ガードレール**: 「機能が多い＝良い」ではない（§0.5）。howto/slides の**存在**は HOWTO-1 が見るので重複しない。ここで見るのは**文言と実UIの一致**。
- **Tier 目安**: B（文言・導線の可視変更）。

### P6. 支援機会と倫理的安全性の監査（作戦会議・観点6）

- **目的**: 「発達的価値」そのものは AI では測れない。AI が扱えるのは**観察可能な仕組み**まで。回答は `YES / NO / 判定不能 / N/A`。**内省・支援系ツールにのみ適用**し、娯楽ゲームは `N/A` が正常。
- **観点固有の問い**（すべて仕組みの有無を問う）:
  1. AGENTS.md に「このアプリがスタッフに**提供する支援機会・体験**」が1文で書かれているか（＝効果を約束する「育てたい力」ではなく、機会の記述）。
  2. **回答・共有を強制されないか** — 安全な**非回答・非共有・離脱**の手段があるか（「パス/わからない/保留/撤回」の実装形は問わず、強制されない機能要件として。0件・無回答でも画面が成立するか）。
  3. 内省の成果物（JSON・画面）が子どもへの**評価物・証拠物に見えない**設計か（達成率・順位・バッジ・連続記録がないか。※ゲーム得点や一時状態は対象外＝§0.5-1）。
  4. メンター心得（例:「ふかぼりしない」）が画面に出さず AGENTS.md に書かれているか。
  5. 語彙・負荷がコンテンツガイドラインに適合するか（kimochi-map の意図的ネガ語は例外）。
- **AI は結論を出さない。** 具体的な根拠があるときだけ「**判定不能・人間レビュー候補**」として C で返す。実際の発達効果・個々の子どもへの適合・支援目標の分類・禁忌・目標間の重み付けは**人間専任**（**実装モデルと別系統モデルが一致してもこの根拠にはならない**）。
  - この線引きの理由は**能力ではなく権限**。モデルが強くなっても、自信が高くなっても変わらない。「今のモデルなら判定できる」は緩める理由にならない。
- **固有ガードレール**: 「役立つか」を達成度・効果測定で問わない（哲学と衝突）。問うのは「**文書化された意図と UI 機構が整合しているか**」（『本人が気づく余地』は静的には判定しない）。
- **Tier 目安**: C（大半）。AGENTS.md への1文追記は B。

### P7. アプリ選択情報の充足監査（アプリ単位・観点7）

- **目的**: スタッフが選ぶための**観察可能なメタ情報**が各アプリに揃っているかを洗い出す。**「向く子ども／向かない子ども」という個人適合の判断はしない**（それは P6 の人間専任、かつ固定ラベル禁止）。
- **前提**: このカードは §P8 の**語彙・メタデータ承認が済んでから**回す（未承認なら実行せず「§P8 の承認待ち」と返す）。
- **観点固有の問い**（`YES / NO / 判定不能`。すべて「アプリ自身のドキュメントに書かれているか」を問う）:
  1. **セッション条件**が読み取れるか — 所要時間の目安・想定人数・発話量（声/チャット/選ぶだけ）・自己開示の深さ。これらは観察可能で、固定ラベルにならない。
  2. アプリ自身が**利用場面・条件**を宣言しているか（例: `kyapa-graph` が想定場面を明示しているように）。見るのは**アプリ側に宣言があるか**であって、AI が個々の子どもへの割り当てを判断することではない。無くてもよいが、有れば選択の助けになる。
  3. 心理的負荷は**単一スコアにせず項目分解**して読めるか（自己開示の深さ・過去想起の要否・失敗が見える設計か 等）。現状これらは `docs/content-plan.html`（役割・負荷・「リスクと対策」）に散在。
  4. 似た役割のアプリとの分担が特定できるか（例: suki-type-check〈タイプ診断〉vs kyoumi-sugoroku〈会話のきっかけ〉）。
  5. 作戦会議の4軸（関係性/興味/自己理解/自己実現）について、**承認済みのマッピングがあればそれとの整合**を確認する（AI が新規に分類を推定しない。マッピング未確定なら『判定不能』）。
- **一次情報のありか**: `docs/content-plan.html`（共通原則・役割・負荷・リスク）が実質的に唯一の準・選択ガイド。統合ガイドは**未着手が公式見解**（MEMORY `project_session_flows.md`）。よってこのプロンプトは「既存ガイドの検証」ではなく「**ガイドを新規に組み立てる素材集め**」。
- **メタ情報の置き場**: 開発者・エージェント向けの記録は `AGENTS.md` でよい。ただし**スタッフが実際に見る選択ガイドは別**で、ポータル or スタッフ閲覧用の専用資料を正本にする（AGENTS.md をスタッフ導線にしない）。子ども向け画面には出さない。
- **Tier 目安**: C（素材集め）。AGENTS.md へのセッション条件追記は B。

### P8. ポータル・横断の選択導線監査（全43アプリ俯瞰・観点7の横断面）

- **目的**: アプリ単位では見えない**選択導線の設計欠陥**を横断で洗い出す。スコープは `portal` / `横断`。
- **停止ゲート（先に承認すべき2つのP票）**: 43アプリの個別監査（P7）に入る前に、次を**別々のP票**として人間承認する（部分承認できるよう2票に分ける）:
  - **P票①: 非序列の支援機会語彙** — 固定ラベル（「不安が強い子」等）ではなく、その日の本人の希望＋観察可能なセッション条件（所要時間/人数/発話量/自己開示の深さ）で絞る語彙。
  - **P票②: ポータルの選択メタデータ項目** — カードに載せる属性の集合（軸・負荷の項目・蓄積型か 等）。
  - **必要な2票が両方承認されるまで、P7・P8 のアプリ横断監査を停止する**（片方だけの承認では進めない）。停止中は「①②のP票候補」だけを返す。
- **観点固有の問い**（①②承認後。②〜④は**欠陥を前提にしない** — 承認済み基準への違反、または具体的なスタッフの選択失敗が示せる場合のみ finding 化する）:
  1. `data-scenes` が sakusen 二値に留まり、承認済みメタデータ項目がカードに反映されていないか。
  2. 承認済み基準に照らして、役割の**被り**（同じセッション条件に多数のアプリ）や**空白**（拾えていない条件）が具体的に指摘できるか。
  3. 「この状態にはこのアプリを避ける」に相当する**アンチパターン集**の不在が、実際のスタッフの選択失敗として示せるか。
  4. 週をまたいだ配列を判断できる手がかりの不足が、具体的な場面で問題になっているか。
- **固有ガードレール（絶対）**: 子どもの状態の**推定・保存・スコア化・自動推薦**を提案しない。絞り込みは**その日の本人の希望＋観察可能なセッション条件**に限る。
- **Tier 目安**: C（設計提案）／ 語彙・メタデータ確定は **D（人間専任・P票）**。

### P9.（承認後の別ワークフロー）コンテンツ候補の生成

> これは発見カタログ（read-only）の**外側**の工程。P3 の finding を**人間が承認した後**にのみ起動し、`docs/content-candidates/` に候補を書き出す（書き込みを伴うため §0 の read-only 前提に含めない）。

- **前提**: 承認された不足に対してのみ。新規コンテンツの**本体投入は D-3（人間専任）**で、このワークフローの成果物は候補ファイルまで。生成後は **`bash scripts/draft-lint.sh` 相当の検査**（または content-audit 再実行）を通す。
- **候補ファイルの必須要素**（`docs/content-candidates/quiz-duplicate-replacements.md` がテンプレ）:
  1. 冒頭に「**未承認・自動投入禁止**」。
  2. **事実系の候補**には独立した出典2件＋参照日、正答の一意性の自己検査（お題・トークテーマ等の非事実系には出典要求を課さない）。
  3. 年齢適合・既存重複ゼロの自己検査。
  4. 追加前に「重複が実害か」を再検証。
- **B+ シャドー運用**: 事実検証を伴う差し替えは、実装前に実装モデル＋別系統モデルの2系統独立判定を**記録だけ**する（適用は人間承認）。
- **Tier**: 候補生成は C。本体投入は D-3。
