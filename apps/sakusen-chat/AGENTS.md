# 作戦会議チャット — 仕様

共通の運用・品質基準はルートの [AGENTS.md](../../AGENTS.md)。ここにはこのアプリだけの仕様と、共通規約からの意図的な例外を書く。

## 目的・使用シーン

作戦会議（週1回30分の面談）で、マイクOFF・カメラOFFの子どもと文字と画像で話すためのチャット。
Zoom のチャットは話題が1本の流れに混ざり、1つの話題ずつしか進まずテンポが悪い。このアプリは話題ごとに会話が分かれ、いくつもの話題を同時に進められる。

- 入れるのはメンターと、参加する人2人まで（合計3人。2026-10-13 オーナー決定）
- 使えるのは、メンターがルームをひらいている間だけ
- メンターが「終わる」を押すと、会話と画像はすべて消える。履歴は持たない
- **ツール一覧（ポータル）・早見表・更新情報には載せない**（今のところ1人の子どもとだけ使うため。オーナー決定）。URL を直接ひらいて使う

経緯: 2026-10-13 オーナーの依頼 → 同日 `drafts/sakusen-chat/`（通信しないモック）で流れを確かめ → オーナーの指示で本体化。

## 技術スタック

- Realtime Database（`sakusenchat_rooms/{ルームのカギ}`）＋匿名認証。`index.html` + `app.js` + `style.css`
- 共通モジュール: `rtdb-utils.js`（初期化・時刻・トースト・コピー・切断時の予約の取り消し）、`stats.js`、`howto.js`
- 画像は Storage を使わない（Spark プランで使っていない）。ブラウザの中で JPEG に小さくして RTDB に置く

## 画面構成・フロー

| 画面 | 内容 |
|---|---|
| `screen-top` | リンクなしでひらいたとき。メンターの端末にだけ「ルームを作る」が出る。ほかの端末には「メンターから届いたリンクでひらいてね」だけ |
| `screen-join` | `?room=カギ` でひらいたとき。名前を入れて「参加する」 |
| `screen-chat` | 左に話題の一覧、右に選んだ話題の会話。幅 600px 以下では一覧と会話を切りかえる |
| `screen-end` | ルームが終わったとき。会話と画像が消えたことを伝える |

1. メンターが「ルームを作る」→「リンクをコピー」で参加用のリンクを Zoom のチャットに送る（スマホ・タブレットで入る人には「QRコードを出す」を読みとってもらう）
2. 参加する人はリンクをひらき、名前を入れて「参加する」
3. 話題を選んで書く。だれでも「話題をふやす」で話題をふやせる（20こまで）
4. メンターが「終わる」→ ルームごと消える

ルームを作ると、話題「チェックイン」「ジブンチェック」が最初から並ぶ。
ジブンチェックには「今日の調子はどのへん？」の5段階と「今日は答えない」のボタンがあり、押すと回答がその話題の会話に入る。

## メンターの端末（ルームを作れる人の限り方）

「作戦会議以外では使えないようにしたい」というオーナーの要望への対応。

- `?mentor=メンター用のカギ` でひらいた端末だけを「メンターの端末」としておぼえる（localStorage `sakusenchat_mentor`）。つぎからはリンクなしでもルームを作れる
- カギそのものはリポジトリに置かない。`app.js` の `MENTOR_KEY_HASH` に SHA-256 だけを置く
- **画面の上での制限（性善説の範囲）**。ルールでは止めていないので、DevTools を使えば回避できる。確実に止めるには `database.rules.json` の変更が要る（変更禁止パス。オーナー判断）
- カギを変えるとき: 新しいカギを決め、次で出した値に `MENTOR_KEY_HASH` を書きかえる（`?v=` も上げる）。メンターは新しいカギのリンクをひらき直す

  ```bash
  printf '%s' '新しいカギ' | shasum -a 256
  ```

## ルームのカギ（共通規約からの例外）

共通規約は「6文字のルームコード」「コードをコピー」「名前 → ルームコード → 参加する」だが、このアプリは次のとおり。

- ルームのカギは **20文字**（`RoomkRTDB` と同じ32文字から、`crypto.getRandomValues` で作る）。コードの手入力欄と「コードをコピー」は置かず、**リンクだけ**で参加する
- 理由: 現在のルールは、ルームの名前を知っていれば匿名認証だけで読める。子どもとの会話と画像を置くので、当てられない長さのカギにして「リンクを知っている人だけが読める」形にした。ルームの一覧は取れない（名前空間の直下は読めない）
- 「入れるのは3人まで」は画面の上での制限。リンクを知っている人が DevTools を使えば読める。ルールで「席のある人だけ読める」にするのは今後の候補（変更禁止パス。オーナー判断）
- つないだあとは `?room=` をアドレスから外す（共通規約どおり）。退出したときは参加の画面にもどし、`?room=` をアドレスに戻す
- **「QRコードを出す」**（`#btnShowQr`。「リンクをコピー」の隣で、同じくメンターだけに出す。2026-10-22）: スマホ・タブレットなど別の端末で入る人向けに、「リンクをコピー」と同じ参加用のリンクを QR コードにして画面の上に大きく出す。共通の `RoomkQR.show(カギ, リンク, { showCode: false })`（`apps/shared/js/room-qr.js`）。カギ（20文字）はふだん画面に出さないので、QR の下にも出さない（`showCode: false`）。せまい画面では、バーのボタンは文字を折り返さず、入りきらないボタンを次の行へ回す

## Firebase データ構造

```
sakusenchat_rooms/{カギ}/
  meta/                       小さい情報だけ。transaction はここ（とルーム作成の1回）にしか使わない
    status: 'open'
    createdAt, hostUid, hostName
    hostConnected, hostDisconnectedAt
    guests/{人の id}: { name, uid, joinedAt }     在室。切断で消える
  topics/{話題 id}: { title, kind: 'free'|'mood', mid, at }
  msgs/{メッセージ id}: { t: 話題 id, mid, name, kind: 'text'|'image'|'mood', text, at, w, h }
  imgs/{メッセージ id}: 'data:image/jpeg;base64,…'  画像の中身。表示するときだけ読む
  typing/{人の id}: { t: 話題 id, name, at }       入力中。切断で消える
```

- **人の id（`mid`）はタブごと**（sessionStorage `sakusenchat_mid`）。同じブラウザの別タブは匿名認証の uid が同じなので、自分のメッセージかどうかは uid ではなく `mid` で見る（メンターが同じブラウザの別ウィンドウで参加の側を試せる）
- 「タブを複製」は sessionStorage ごと写すので、同じ `mid` のタブが2つできる。起動時に BroadcastChannel でほかのタブに聞き、同じ `mid` が使われていたら、あとからひらいた側の `mid` を作り直して再接続の記録を使わない
- **画像を `msgs` と分けている理由**: メッセージの購読で画像まで何度も受け取らないため。画像は表示するときに1回だけ読み、手元に持つ
- 画像つきのメッセージは、`imgs/{id}` と `msgs/{id}` をルームへの1回の `update()` で置き、消すときも1回で両方を消す（片方だけが残らない）。`update()` が中止するのは書きかえた場所とその上下の transaction だけなので、`meta` の transaction は止まらない（SDK のソース `repoUpdate` で確認）
- **`meta` を分けている理由（共通規約からの例外）**: transaction は対象の値をまるごと送り直す。ルーム全体に transaction を使うと、画像を含む会話をまるごと送り直すことになる。そのため status・在室の確認と席の追加は `meta` の transaction で行う。ルーム全体の transaction は、空のルームを作る1回だけ
- 画像は長い辺 1280px・JPEG。70万文字（約500KB）を超えるときは順に小さくして作り直す。1ルーム40枚まで。受け取る側でも、JPEG の data URL であること・文字数・`w` `h` の範囲を確かめる（JPEG の中身の実寸までは見ない。直接データベースに書く人への備えは性善説の範囲）
- メッセージは 500文字まで、話題名は 30文字まで、名前は 8文字まで

## 切断時の挙動

| 役割 | 挙動 |
|---|---|
| メンター切断 | `meta.hostConnected=false`・`hostDisconnectedAt`。参加している人には4秒後から「メンターの戻りを待っています」を出す（メンターの再読み込みくらいでは出さない） |
| 参加している人の切断 | `meta/guests/{id}` と `typing/{id}` を `onDisconnect().remove()` |
| 自分の通信が切れた | 「接続が切れているよ」を出し、送信を止める（切れている間に書いたものを、ルームが消えたあとに送らないため） |

- **期限切れは10分**（`ORPHAN_TTL_CHAT_MS`。共通の2分からの例外）。メンターの通信が数分切れただけで会話が消えないようにするため。10分たつと、開いている端末がルームごと消す
- 席は自分の `mid` がキーなので、参加の transaction の前に切断時の予約を張ってよい（他の人の在室を消さない）。入れなかったときは予約を取り消す
- 作成・参加は、送信後の切断（`Error('disconnect')`）でやり直す。自分の書き込みがもう届いていれば成功として扱う
- ルームを作るときは「切断中」として作り、つないだあとの在室確認で接続中にする（切断時の予約がないルームを残さない）

## 削除（「毎回消える」の守り方）

1. メンターの「終わる」: 切断時の予約を取り消してから、ルームごと `remove()`。取り消しに失敗したら消さずにやめる。途中で打ち切らず、消えるまで待つ
   - ルームがなくなったのを知った端末は、それぞれもう一度ルームごと `remove()` を送る。終わる直前に送った書き込みが削除よりあとに届いても、同じ端末のこの削除がそのあとに届くので、残りかすにならない
   - 端末の記録（`sakusenchat_my_rooms`）からは、消せたのを確かめてから外す。消せなかったルームは、つぎにひらいたときにもう一度ためす
2. メンターが「終わる」を押さずに閉じた:
   - 参加している人の端末が開いていれば、10分後にその端末が消す
   - **メンターの端末がつぎにこのページをひらいたとき**に片付ける。端末は自分が入ったルームのカギをおぼえている（localStorage `sakusenchat_my_rooms`。会話の中身は保存しない）。期限切れなら何も聞かずに消し、期限の前なら「前のルームにもどる／前のルームを消す」を選ばせる（選ぶまで新しいルームは作れない）
   - 参加した人の端末も、つぎにこのページをひらいたときに期限切れのルームを消す
3. メンターが閉じるときは、ブラウザの確認（beforeunload）を出す

**残る限界**（サーバー側で時間で消すしくみは Spark プランでは持てない）:

- メンターが「終わる」を押さずに閉じ、そのあとだれもこのページをひらかなければ、会話と画像はデータベースに残る（読めるのはカギを知っている人だけ）
- 書き込みを送った直後に通信が切れ、そのまま閉じた端末の書き込みが、ルームの削除よりあとに届くと、その分だけが残る。その端末がつぎにこのページをひらいたときに消える
- メンターが同じルームを2つのタブでひらき、片方で終わったあと、もう片方が閉じるまでの間に切断時の予約が発火すると、`meta` のかけらが残ることがある（開いているタブが気づけば消す）

## 未読・入力中

- その話題を開いていて、ウィンドウが手前にある間に届いたものは未読にしない。別の話題を見ている間・ウィンドウが後ろにある間（Zoom を手前にしている間）に届いたものは未読
- 未読は、話題ごとの数・ブラウザのタブ名の件数で知らせる。ほかの人がふやした話題は「新しい」と出す
- **音は鳴らさない**（聴覚過敏のある子がいるかもしれないため。2026-10-13 オーナー決定。公開直後に、新着の音と切りかえボタンを外した）
- 未読のある話題をひらくと「ここから新しいメッセージ」の線を引く
- 入る前からあったメッセージは未読として出す（メンターが先に書いておいた質問に気づけるように）
- 「入力中…」は出す。**「既読」は出さない**（既読が見えると、返事をせかされるように感じるため。オーナー決定）
- 読んだところと見ていた話題は sessionStorage に置き、再読み込みで引きつぐ

## 入れない機能（意図的に未実装）

- 会話・画像の保存、書き出し、前回のつづき（毎回消すのがオーナー決定）
- 既読の表示
- 新着の音・通知音（切りかえ式でも置かない）
- ジブンチェックの記録・集計・前回との比較（回答はその場の会話の1通で、ルームと一緒に消える。ルートの哲学ガードのとおり、内省の回答を保存・採点・比較しない）
- 「なんで？」と理由を書かせる欄

## 利用回数

- `room-create`: ルームができたとき（作成を確定した1台だけ）。ほかの共通項目（`start`・`finish` など）は数えない（ゲームの回がないため）
- 数えるのは回数だけ。名前・会話の中身は記録しない

## 既存ガイドラインとの関係

- 画面の文言は通常表記（漢字まじり）。メンター向けの心得は画面・つかいかたに書かない
- 会話の中身はメンターと参加する人が書くもので、アプリは内容を持たない（`scripts/content-audit.mjs` は `NO_CONTENT_APPS`）
- ジブンチェックの5段階の文言は、オーナーが作戦会議で使っている進行スライドのもの（`docs/sakusen-expansion-plan.md`）。意味を変えない

## 検証

2026-10-13 隔離エミュレーター（本番には接続しない）＋ Playwright で確認。テスト一式と手順は [tests/sakusen-chat/](../../tests/sakusen-chat/README.md)。

- その1（97項目）: メンター用のリンク・作成・参加（名前の重なり・4人目の拒否）・会話・未読・線・ジブンチェック・話題をふやす・入力中・画像の縮小と別置き・消す・HTML が文字のまま出ること・幅 375px・話題20こ・同じブラウザの2タブ
- その2（62項目）: 再読み込みでの復帰（参加している人・メンター）・通信が切れている間の送信止め・タブの複製・退出・タブを閉じる・メンターの切断と「前のルームにもどる」・終わる・期限切れ・つぎにひらいたときの片付け・最後にデータベースに何も残らないこと
- その3（16項目）: 作成・参加の送信直後の切断でも、ルーム・席が1つだけできること。`meta` だけが消えて会話が残った形の残りかすを、開いている端末が消すこと

独立レビュー（別系統のモデル・2往復）: 1回目の7件のうち6件を反映（期限切れ削除の取りこぼし・打ち切り後の削除・削除後に届く書き込み・切断時の予約の取り消し・画像の2段書き込み・タブの複製・受け取る側の画像の検査）。2回目の4件のうち2件を反映（終わっているリンクの残りの片付け・「終わる」での取り消し失敗の検知）。「`update()` が `meta` の transaction を中止する」は SDK のソースで確認して不採用、JPEG の実寸の検査は性善説の範囲として見送り。

未確認: スマホ実機での表示・キーボードが出ているときの書く欄・画像の選択（カメラ・写真）、本番のデータベースでの動作。
