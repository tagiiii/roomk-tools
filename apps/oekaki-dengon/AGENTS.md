# お絵描き伝言ゲーム 仕様書

## 目的・使用シーン

書いた文を次の人が絵にし、その絵を次の人が文にし……と順番に回していく伝言ゲーム。
全員に回ったら、ホストの操作で1列ずつ最初のお題からめくって見せあい、お題がどう変わったかを楽しむ。

- **core value**: うまい・へたや正解がなく、「伝わり方がずれていくこと」そのものがおもしろい。書く・描く・見るだけで参加が成立し、話さなくても主役になれる。点数・勝ち負けは置かない。
- 対象: 小学校中学年〜中学生。ボドゲクラブ（`data-scenes="bodoge"`）。
- 描く側は **3〜8人**。ホスト（メンター）は既定で進行役。ロビーの「自分も描く側で参加する」で描く側に入れる（既定オフ）。
- マイク派とチャット派が混在しても遊べるよう、主な行動はすべてアプリ内（書く・描く・「完了」）で完結する。

> 着想元は『Gartic Phone（ガーティックフォン）』。遊びの一般名称「お絵描き伝言ゲーム」を表示名にする（伝統ゲームの一般名称の例外。オーナー決定 2026-09-28）。
> 原作の名称・見た目は使わない。紹介文・早見表では「『ガーティックフォン』から着想」と記述的に紹介し、「Web版」「オンライン版」「無料版」等の表現は使わない。

## ゲームルール（原作どおり。偶数人数の回数だけ変えている）

1. ホストが「始める」を押すと、描く側の並び順をシャッフルして固定する（`match/order`）。人数を N とする。
2. 全部で **R 回**（`match/rounds`）。N が奇数なら R = N、**N が偶数なら R = N + 1**。全員が同時に、それぞれ別の列（伝言の流れ）を1つずつ担当する。
   - 0回目（書く）: 自分の列の最初のお題を文で書く。
   - 奇数回目（描く）: 前の人の文を絵にする。N が偶数のときの1回目だけは、自分のお題を自分で絵にする。
   - 2以上の偶数回目（書く）: 前の人の絵だけを見て、何の絵かを文にする。
3. 全員が「完了」を押すか、制限時間になったら次の回へ。
4. R 回終わったら見せあい（`show`）。ホストが「つぎへ」で1つずつめくる。全部の列を見終わったら `end`（各自で好きな列を見返せる）。
5. ホストは「もう一回あそぶ」でロビーに戻り、同じルームで次のゲームを始められる（途中から来た子もロビーで参加できる）。

### 回し方

- 列 c（0〜N−1）は `order[c]` のお題から始まる。
- k 回目までに列を次の人へ渡した回数を p(k) とする。N が奇数なら p(k) = k。N が偶数なら p(0) = 0、k ≥ 1 で p(k) = k − 1（0回目と1回目を同じ人が担当し、2回目から渡す）。コードでは `passCount()`。
- 列 c の k 回目（エントリ (c, k)）を担当するのは `order[(c + p(k)) % N]`（`authorOf()`）。
- k 回目に `order[i]` が担当する列は `(i − p(k)) mod N`（`chainFor()`）。
- (c, k) で見せる材料は (c, k−1)。k が奇数なら文→絵、k が 2 以上の偶数なら絵→文。
- どの回も、全員がちがう列を1つずつ担当する。N が奇数なら全員が各列をちょうど1回ずつ担当する。N が偶数なら、お題を書いた人だけが自分の列を2回（お題と1枚目の絵）担当する。
- **どの列も、絵を見て書いた文で終わる**（R はいつも奇数）。

#### 偶数人数で1回足す理由（2026-10-05）

- 原作どおり N 回だと、N が偶数のとき列が絵で終わり、最後の絵に「何の絵か」の答えがつかない。メンターからの要望（「偶数で遊ぶときも、最後は絵に対する答えを書いて終われるようにしてほしい」）で変えた。
- 足し方は、市販の伝言お絵描きゲームの偶数人数ルールと同じ形（お題を書いた本人が1枚目を描いてから回す）。「1回減らす」「ロビーで選ぶ」も候補に出し、オーナーがこの形を選んだ。
- 最後の回を最初の人に戻す形（N 回のあとにもう1回）は採らない。お題を書いた本人が答えることになるため。
- 回数は開始時に `match/rounds` へ固定する。`rounds` を持たないゲーム（この変更の前に始めたもの）は N 回のまま進む（`roundsOf()`。`rounds` が N + 1 のときだけ足した形として扱い、それ以外の値は N 回）。
- 更新前の画面はこのルールを知らない（N 回で、1回目から次の人へ渡す）。新しい画面が始めた偶数人数のゲームに更新前の画面が混ざると、同じエントリに2人が書く・回数が食いちがう。濃さのときと同じく、公開（main への push）はセッションのない時間帯にし、公開のあとに開いたままのタブがあれば、ゲームを始める前に読み込みなおす。

### 制限時間（`textSec` / `drawSec`）

ロビーでホストが「書く時間」「描く時間」を分単位で選ぶ（1回ごとの時間）。開始時に `match/textSec`・`match/drawSec`（秒。0 は制限なし）へ固定する。

| 種類 | 選べる時間 | 既定 |
|---|---|---|
| 書く時間（0回目・絵を文にする回） | 1分・2分・3分・制限なし | 1分 |
| 描く時間（文を絵にする回） | 1分・2分・3分・4分・5分・制限なし | 3分 |

- 2026-09-28、メンターの要望（「分数で選びたい」「時間が足りないことがある」）で、ゆっくり（書く60秒・描く150秒。既定）・ふつう（40秒・90秒）・なしの3択から変えた。選べる幅はまぎれ絵師の手番タイマー（1〜5分・制限なし）とそろえている。既定の描く時間3分は、旧既定の2分30秒を分単位に切り上げたもの。
- 時間切れになったら、書きかけ・描きかけのまま次へ回る（原作どおり）。
- 全員が「完了」したら、時間前でも次へ進む。
- 制限なしの回は全員の「完了」を待つ。ホストは「しめきる」でいつでも次へ進められる（制限時間のある回も同じ）。
- 3択のころに作ったルーム・始めたゲーム（`settings/pace`・`match/pace`）も読める（公開の切り替えをまたいで続くゲームのため）。始めたゲームは当時の時間のまま進む。ロビーの設定は `pace: 'none'` なら両方とも制限なし、それ以外は既定の時間として扱う。

### room-K 向けに足したもの（遊び味は変えない）

- **下書きの復元**: 取れなかったら1秒おいて3回までやり直す。0回目のおまかせの自動補完は「サーバーに文が無いときだけ入れる」transaction で行うので、復元より先に回が閉じても、復元に失敗しても、子どもが書いた文を上書きしない。
- **「おまかせ」**: 0回目で思いつかない子は、用意したお題（`PROMPTS`・8テーマ×10件。2026-09-28 オーナー承認）をボタンで入れられる。入れたあと書き換えてもよい。お題は `match/seed` で並べかえた順に列ごとにずらして配るので、全員がおまかせを使っても同じゲームで列どうしのお題が重ならない（どの端末でも同じ結果）。`PROMPTS` の漢字は小学1〜4年で習う字にとどめる（回ってきた文は次の子が1人で読んで描き、メンターが読み上げると中身が伝わってしまうため）。0回目が空欄のまま閉じたとき（時間切れ・しめきり・途中で終わる）は、その子の端末がおまかせのお題を自動で入れる（`auto: true`。見せあいに「おまかせ」の札が付く）。
- **描きかけの保存**: 線は1本ごと、文は入力のたびに保存する。再読み込みや時間切れでも消えない。
- **空欄の扱い**: 回ってきた文が空（書いた子が抜けた等）なら「好きなものを描いてね」、回ってきた絵が白紙ならそのまま白紙を見せる。見せあいでは「（何も書かれなかったよ）」「（白紙）」と表示する。
- **途中で終わる**: ホストは遊んでいる途中でも「途中で終わる」で、そこまでの分（今の回を含む）の見せあいに進める。時間が足りない日でも見せあいで終われるようにするため。
- **入りなおし**: 遊んでいる途中にタブを閉じてしまった子は、「ルームに参加する」から同じニックネームで入りなおせる（描く側に入っていた名前で、いま接続していないときだけ）。同じタブの再読み込みは sessionStorage で自動復帰する。
- 「完了」のあとも、次の回に進むまでは「なおす」で直せる（原作どおり）。
- 文の回は、空欄のままでは「完了」できない（0回目は「おまかせ」がある）。絵の回は白紙でも「完了」できる。

### 描く道具

- 道具はペン・消しゴム・塗りつぶしの3つから選ぶ（`state.tool.mode`）。選んでいる消しゴム・塗りつぶしをもう一度押すと、ペンに戻る。色・濃さを押すと、消しゴムからはペンに戻り、塗りつぶしは塗りつぶしのまま（色を選んでから塗るため）。
- ペン: 13色。太さ3段階（細い・ふつう・太い）。消しゴム（白で塗る。太さ3段階）。
- 白（2026-10-05 追加。「白色も使えるようにしてほしい」という要望による）: 色の列のいちばん後ろ。塗った色の上に白で描きこめる（消しゴムより細く描ける）。濃さは選べない（濃さの列は押せなくなる）。色番号は線のデータに入るので、色を足すときは後ろに足し、並べかえない。
- 塗りつぶし（2026-10-05 追加。要望による）: 押したところとつながっている、ほぼ同じ色のところを、選んでいる色・濃さで塗る。
  - 線で囲まれていないところを押すと、つながっている全体（紙ぜんぶなど）が塗られる。「1つ戻す」で戻せる。
  - 押したところがもう同じ色なら、何も足さない（データも増えない）。
  - 「ほぼ同じ色」は、押したピクセルとの差が RGB それぞれ 24 以内（`FILL_TOLERANCE`）。線のふち（線の色と下の色がまざったピクセル）は、下の色の分だけを塗る色に置きかえるので、線のまわりに白いふちが残らない。
  - 1枚あたり 80回まで（`MAX_FILLS`）。読むときも 80回までで、それより多い塗りつぶしは描かない。絵を出すたびに保存した順に塗りなおすため（紙ぜんぶの塗りつぶし80回の塗りなおしで、開発機でおよそ0.5秒）。上限に達したら「塗りつぶしはここまでだよ。「1つ戻す」で消すと、また塗れるよ」と出す。
  - 自分のキャンバスは、最後の塗りつぶしまでを描いた写し（`state.play.paint`）を覚えておき、線を足すたびに全部を塗りなおさない。見せあいのアルバムは、めくっても同じ中身のキャンバス要素を使い回す。
- 濃さ: 色の下の列で、5段階（とても薄い・薄い・ふつう・濃い・とても濃い）から選べる（2026-09-28 追加。「色を薄めたり濃くしたりしたい」という要望による）。
  - 列には選んでいる色の5段階を並べ、両端に「薄い」「濃い」を出す。列は色の列と同じ幅に広げる。色の丸は、選んでいる色の丸だけを選んでいる濃さで見せる（どの丸も、押したら描ける色で見せる）。
  - ほかの色を選ぶと、濃さはふつうに戻る。濃さをほかの色へ持ち越さないため（色を位置で覚えて押す子が、前の色で選んだ濃さのまま描いてしまわないように）。同じ色を押し直したとき（消しゴムから戻るときなど）は濃さを保つ。その色をふつうに戻すときは、濃さの列の真ん中を押す。濃さを押すと、消しゴムからペンに戻る。
  - 選んでいる色・太さと同じく、濃さも次の回へ持ち越す（再読み込みではふつうに戻る）。道具は持ち越さず、描く回はいつもペンから始める（塗りつぶしのまま始めると、最初のひと押しで紙ぜんぶを塗ってしまうため）。
  - 各色の5段階は `COLORS[i].tones` の表で持つ。真ん中（ふつう）は濃さを足す前の色のまま。薄い側は白に寄せて彩度も少し下げ、濃い側は彩度を保ったまま暗くした（OKLCH の明るさで計算した値）。
  - 色の限界で、段の差が小さい色がある。黒の「濃い」「とても濃い」は、黒より暗い色がないためほぼ同じ黒に見える。うすだいだい・黄色・水色の薄い側は、もともと明るいので段の差が小さく、「とても薄い」は白い紙の上では見えにくい（どの段も列に実際の色で出しているので、子どもは見て選べる）。
- 「1つ戻す」（自分の最後の線または塗りつぶしを消す）、「全部消す」（2回押しで確かめる。1回目は「もう一度押すと消える」に変わり、3秒で戻る）。
  - 「全部消す」に `confirm()` を使わない理由: 確認ダイアログは画面を止めるので、その間に回が進むと、次の人に渡った絵を消してしまう（別エージェント監査の指摘）。
- キャンバスは論理サイズ 800×600（4:3）。画面幅に合わせて縮小表示する。
- 1枚の上限: 線 600本・点の合計 30,000（1枚およそ120KBまで）。上限に達したら「これ以上は描けないよ。「1つ戻す」で消すと描けるよ」と出す。

## 画面構成・フロー

```
TOP（screen-top）
 ├── 「ルームを作る」 → ニックネーム（screen-host-setup） → ロビー
 └── 「ルームに参加する」 → ニックネーム＋ルームコード（screen-guest-join） → ロビー
ロビー（screen-lobby / status: waiting）
   ホスト: ルームコード＋「コードをコピー」、「自分も描く側で参加する」、制限時間（書く時間・描く時間）、参加者、「始める」、「ルームを閉じる」
   ゲスト: 待機表示（制限時間の設定も見える）、「退出する」
        ↓「始める」（描く側 3〜8人）
あそぶ（screen-play / phase: play）
   描く側: 回の表示・残り時間・回ってきた文や絵・入力（文 or キャンバス）・「完了」/「なおす」・完了人数
   進行役のホスト: 回の表示・残り時間・全員の完了状況・「しめきる」・「途中で終わる」（中身は出さない）
   ホストが描く側のときは、描く画面の下に進行パネルを重ねる
        ↓ 全部の回（N が奇数なら N 回、偶数なら N+1 回）が終了 / ホストの「途中で終わる」
見せあい（screen-show / phase: show）
   全員: いまの列を最初のお題から、めくった分だけ縦に並べる（名前つき）
   ホスト: 「つぎへ」、「この列をまとめて見せる」、「見せあいを終える」
        ↓ 最後の列の最後まで / 「見せあいを終える」
おしまい（screen-end / phase: end）
   全員: 列を選んで見返せる（各自の画面で自由に）
   ホスト: 「もう一回あそぶ」（→ ロビー）、「ルームを閉じる」（ルーム削除）
   ゲスト: 「退出する」
```

- 遊んでいる途中の新規参加はできない（「もう始まっているよ」）。終わってホストが「もう一回あそぶ」を押すとロビーで参加できる。
- ボタン階層: 各画面の塗りつぶし主ボタンは1つ（ロビー「始める」、あそぶ「完了」、見せあい「つぎへ」、おしまい「もう一回あそぶ」）。

## status 遷移

ルート（`ctl`）の `status` はホストだけが変える。遊んでいる間の段階は `match/phase` で持つ。

```
waiting ──（ホスト「始める」）──→ playing
playing ──（ホスト「もう一回あそぶ」、phase が end のとき）──→ waiting
どこからでも ──（ホスト「ルームを閉じる」）──→ 削除

match/phase: play ──（最後の回が終わる / ホスト「途中で終わる」）──→ show ──（最後までめくる / ホスト「見せあいを終える」）──→ end
```

| status / phase | 説明 |
|---|---|
| `waiting` | ロビー。このときだけ新規参加できる。設定（hostPlays・textSec・drawSec）を変えられる |
| `playing` + `play` | 書く・描くを `match/rounds` 回。`match/step` が今の回 |
| `playing` + `show` | 見せあい。`match/show` がいまの列とめくった数 |
| `playing` + `end` | おしまい。各自で見返す。ホストが次を選ぶ |

- `play → show` は、最後の回の「完了」を押した人・時間切れを検知した人・ホストのいずれかの transaction が行う（全員同時に進むゲームのため。esadori の judge と同型の逸脱）。
- `show` のめくり・`show → end` はホストのみ。

## Firebase データ構造（Realtime Database）

パス: `oekaki_rooms/{roomCode}/`（共通命名規則。セキュリティルール変更不要）

```
oekaki_rooms/{roomCode}/
  ├── ctl/                                  # 進行データ（小さい）。リスナー・transaction はすべてここ
  │    ├── host:               string
  │    ├── hostConnected:      boolean
  │    ├── hostDisconnectedAt: number | null
  │    ├── status:             'waiting' | 'playing'
  │    ├── createdAt:          number          # ServerValue.TIMESTAMP
  │    ├── lastMatchId:        number          # 最後に始めたゲームの matchId（初期値 0）
  │    ├── settings: { hostPlays: boolean, textSec: number, drawSec: number }   # 制限時間は秒（0 は制限なし）
  │    ├── players/{nick}: { isHost: boolean, seat: number, sid: string }   # presence（ノードの有無＝接続中）。sid はその画面（タブ）の識別子
  │    └── match/                              # 「始める」で作成、「もう一回あそぶ」で削除
  │         ├── matchId:  number               # ルーム内の世代（始めるたびに +1）
  │         ├── order:    [nick, ...]           # 描く側の並び（開始時にシャッフルして固定）
  │         ├── rounds:   number               # 全部の回数（開始時に固定。N が奇数なら N、偶数なら N+1）。無ければ N 回
  │         ├── textSec:  number               # 書く回の制限時間（秒。0 は制限なし）。開始時に固定
  │         ├── drawSec:  number               # 描く回の制限時間（秒。0 は制限なし）。開始時に固定
  │         ├── phase:    'play' | 'show' | 'end'
  │         ├── step:     number               # play 中の今の回（0〜rounds−1）
  │         ├── seed:     number               # おまかせのお題を配る順番（開始時に作る）
  │         ├── deadline: number               # play 中の締め切り（サーバー時刻 ms）。制限なしの回は absent
  │         ├── done/{nick}: true              # 今の回で「完了」した人
  │         ├── steps:    number               # show / end で見せる回数（通常 rounds、途中で終わると step+1）
  │         └── show: { chain: number, upto: number }   # show 中の列と、めくった数（1〜steps）
  └── art/                                  # 書いた文・描いた絵（大きい）。transaction に含めない
       └── m{matchId}/c{chain}/s{step}/
            ├── t:    string                 # 文のエントリ（最大30文字）
            ├── auto: true                   # 0回目の時間切れで自動補完した印（無ければ absent）
            └── s/{pushKey}: { c: number, w: number, d?: number, p: string }   # 絵のエントリの線。塗りつぶしは { c, f: 1, d?, p }
```

### ctl と art を分ける理由

- 絵のデータは1ゲームで数百KBになりうる。ルーム全体への transaction は新しい値を丸ごと送るうえ、ほかの子の線の保存と衝突して再試行が続くため、描いている最中に使えない。
- そこで進行データを `ctl` にまとめ、作成・参加・開始・完了・回の進行・めくり・復帰の書き戻しはすべて **`ctl` への transaction** で行う。線と文は `art` の各エントリへ `set()` / `push()` / `remove()` で直接書く（エントリの持ち主は1人なので競合しない）。
- ホストの「ルームを閉じる」はルート（`oekaki_rooms/{roomCode}`）の `remove()` で ctl と art をまとめて消す。期限切れ・壊れルームの掃除は、ctl を transaction で消してから `art` を消す（ルートは消さない。同じコードで新しいルームが作られていても、始めるまで絵を持たないので巻き込まない）。
- 期限切れ・ゴースト判定は `ctl` の値で行う（`isRoomExpired(ctl)`、`status` の無い ctl は壊れルーム）。

### 線の形式

- `c`: 色番号（0〜12。12 が白）。消しゴムは `-1`（白で描く）。`w`: 太さ番号（0〜2）。
- `f`: 塗りつぶしの印（`1`）。塗りつぶしは `{ c, f: 1, d?, p }` で、`p` は押した1点、`w` は持たない。線と同じ並び（push キーの順）に入れ、見る側は保存した順に線と塗りつぶしを描きなおして同じ絵にする（塗った範囲そのものは保存しない）。
  - 塗る範囲は、その時点のキャンバスのピクセルから決まる。どのキャンバスも論理サイズ 800×600 のまま描くので、同じ種類のブラウザなら同じ範囲になる（E2E で、描いた画面・回ってきた画面・見せあいの画面のピクセルが一致することを確かめている）。ブラウザの種類がちがうと、線のふちのピクセルがわずかにちがうので、すき間がぎりぎりの囲みでは、片方では中だけ・もう片方では外まで塗られることがありうる（既知の制約。色の差の許容を小さくしてあるので、ふつうの囲みでは起きにくい）。
  - 手元のキャンバスと見る側の絵をそろえるため、手元の線もキーの順に持つ（キーが前後したら並べなおして描きなおす）。下書きの復元に3回失敗して白紙から描き始めたときは、その回は塗りつぶしを使えなくする（「前に描いた分を読みこめなかったので、塗りつぶしは使えないよ。ページを読み込みなおしてね」。サーバーに残っている前の線の上で塗りなおされ、見る側で塗る範囲が変わるため。別エージェント監査の指摘）。
  - Safari は、指紋対策でキャンバスの読み取り値に細かいゆらぎを入れることがある。色の差の許容（24）より小さいはずだが、実機では未確認（メンター実機で iPad の Safari を使う機会に、塗りつぶした絵がほかの画面と同じに見えるかを見る）。
  - 更新前の画面は `f` を読まずに、塗りつぶしを「押したところの点1つ」として描く。色番号12（白）は、更新前の画面では黒で描く。濃さと同じく、公開のあとに開いたままのタブは、ゲームを始める前に読み込みなおす。
- `d`: 濃さ（−2〜2 の整数。負が薄い・正が濃い）。ふつう（0）の線と消しゴムの線には付けない。`d` の無い線（濃さを足す前の線も）と、数でない値・範囲外の値は、ふつうで描く（型は変換しない。`"2"` や `true` もふつう）。
  - 更新前の画面は `d` を読まずに、どの濃さの線もふつうの色で描く。薄い黒・灰色は黒く、薄い色で広く塗ったところは濃く見えるので、その画面で絵を見て書く子には別の絵に見えうる。混在は、公開の時点で開いていた更新前の画面（遊んでいる途中に限らず、トップ・ロビー・おしまいの画面も）が、そのまま続けたり始めたりしたゲームで起きる（更新前の画面には版の確認や自動の読み込みなおしがない）。公開（main への push）はセッションのない時間帯にし、公開のあとに開いたままのタブがあれば、ゲームを始める前に読み込みなおす。
- `p`: 座標列。x・y を 0〜800 / 0〜600 の整数にして、それぞれ36進2桁で連結した文字列（1点4文字）。
- 3px 未満の移動は間引く。1本 400点を超えたら、そこで線を区切って続きを新しい線にする。1枚あたり 600本・点の合計 30,000 まで。
- 描画は点の中点を通る二次曲線でなめらかにする。

### art の読み方（リスナー）

- play: 回ってきた材料 `art/m{id}/c{c}/s{k−1}` を `on('value')`。自分のエントリは回が変わったときに1回 `get()` して下書きを復元し、以後は手元の状態を正とする。
- show: いまの列 `art/m{id}/c{c}` を `on('value')`。
- end: 見せあいで読んだ列は使い回し、足りない列だけ `art/m{id}/c{c}` を `get()` する（通信量を抑える）。
- 退出・画面の切り替えのたびに不要なリスナーを外す。

### 書き込みの流れ

- 線は描き終わった1本ごとに `push()` のキーで `set()`、文は入力のたびに（0.4秒まとめて）`set()` する。書き込みは待たずにすぐ送る（RTDB は同じ接続の書き込みを送った順に反映する）。「完了」の前だけ、それまでの書き込みの完了を待つ。
- 書き込み先のパスは、その回のエントリ（`m{id}/c{c}/s{k}`）で固定する。回が進んだあとに届いた書き込みも前の回のエントリに入るだけで、次の回に混ざらない。
- 回が進んだら、その端末が前の回の自分のエントリを仕上げる（最後の入力の保存、0回目が空欄ならおまかせ）。前の回のエントリの持ち主は自分だけなので、進んだあとに書いてもぶつからない。

### 容量の目安

- 1枚は現実的に数KB〜数十KB、上限で約120KB。1ゲーム（8人）で現実的に数百KB〜1.5MB 程度。
- 見せあいとおしまいで各端末が全部の絵を1回ずつ読む（おしまいは見せあいで読んだ分を使い回す）。Spark の転送 10GB/月に対して、週数回の利用なら十分に収まる。
- 放置されたルームは、作った端末の後片付け（下記「終了とデータ削除」）で消す。

### 秘匿情報の扱い（性善説）

- 遊んでいる間、ほかの列の中身は画面に出さない（画面は自分が担当する材料だけを読む）。DevTools での閲覧は共通のセキュリティ方針どおり許容する。
- 進行役のホストの画面は、遊んでいる間は完了状況だけを出す（画面共有しても中身が映らない）。

## transaction 設計

すべて `ctl` への `transaction()`。コールバックは複数回呼ばれうるため、乱数（並び順）は外で作る（その時点の参加者の名前ごとの並べ替えキー。transaction 内ではその時点の参加者から並びを組み立て、キーの無い名前は中央値で扱う）。押した時点の `matchId` / `phase` / `step`（見せあいは `chain` / `upto`）を捕捉し、transaction 内で一致を再検証する（ABA 対策）。ホストだけの操作は `ctl.host` が自分であることも確かめる。

| 操作 | 実行者 | 検証 → 書き込み |
|---|---|---|
| 作成 | ホスト | `ctl == null` → 初期 ctl。確定後に古い `art` を消す |
| 参加 | ゲスト | `waiting`・未期限切れ・ホスト接続中・名前未使用・9人未満 → `players/{nick}`。`playing` 中は、`order` に居て今は接続していない名前だけ入りなおせる |
| 設定変更 | ホスト | `waiting`・自分が host → `settings` |
| 開始 | ホスト | `waiting`・自分が host・描く側 3〜8人 → `status: playing`・`match`（matchId+1・order・rounds・textSec・drawSec・phase play・step 0・deadline） |
| 完了 | 描く側 | `playing`・phase play・matchId/step 一致・自分が order に居る → `done/{自分}`。全員そろったら同じ transaction で次の回へ |
| なおす | 描く側 | 同上 → `done/{自分}` を消す |
| 時間切れ | 描く側・進行役を含むホスト | phase play・matchId/step 一致＋締め切りがある（制限なしの回は `deadline` が無い）＋`now ≥ deadline + 1.5秒` → 次の回へ |
| しめきる | ホスト | phase play・matchId/step 一致 → 次の回へ |
| 途中で終わる | ホスト | phase play・matchId 一致（回が進んだ直後でも通す）→ `phase: show`・`steps: step+1`・`show: { chain: 0, upto: 1 }`・`done` と `deadline` を消す |
| つぎへ | ホスト | phase show・matchId/chain/upto 一致 → upto+1 / 次の列 / `phase: end` |
| まとめて見せる | ホスト | 同上 → `upto: steps` |
| 見せあいを終える | ホスト | phase show・matchId 一致 → `phase: end` |
| もう一回あそぶ | ホスト | phase end・matchId 一致 → `status: waiting`・`match: null`。確定後に終わったゲームの `art/m{id}` を消す |
| 復帰の書き戻し | 各自 | 下記「接続・切断・再接続」 |

- 次の回へ進む処理（共通）: 全部の回数を R（`roundsOf()`）として、`step + 1 < R` なら `step+1`・`done: null`・`deadline` を次の種類の時間で再計算（`RoomkRTDB.now()` 基準。その種類が制限なしなら `deadline` なし）。最後の回なら `phase: show`・`steps: R`・`show: { chain: 0, upto: 1 }`・`done` と `deadline` を消す。
- `matchId` はルームの `lastMatchId`（ctl 直下）から +1 して作る。「もう一回」で match を消しても世代が戻らないようにするため。
- ローカルキャッシュ null 対策: リスナー未接続から呼ぶ transaction（参加・復帰の書き戻し・期限切れ/壊れルーム削除）は、**先に ctl へ `on('value')` を張ってキャッシュを温め、最初の値が届いてから transaction する**（`withWarmCache()`）。oshitsuke-zukan・esadori の `const cur = room || preRoom` は、事前取得と transaction の間にルームが消えると古い値でルームを復活させうる（null キャッシュと null のサーバー値のハッシュが一致して確定する）ため、このアプリでは使わない（Codex 設計レビュー 2026-09-28 の指摘）。

### 締め切りの扱い

- `deadline` は回を進める transaction を実行した端末の `RoomkRTDB.now()`（サーバー時刻補正）＋時間で決める。
- 各端末は 250ms ごとに残り時間を表示する。締め切りを過ぎたら新しい線・入力を止める（描いている途中の1本は書き終えてから保存する）。0回目で文が空なら、その端末がおまかせのお題を入れる。
- 締め切り＋1.5秒（＋端末ごとに0〜0.8秒ずらす）を過ぎたら、描く側・ホストのどの端末も「時間切れ」transaction を試みる（先に確定した1回だけが通る。通らなければ2秒ごとにやり直す）。ホストのタブが裏にあってタイマーが遅れても進行が止まらないようにするため。
- 時間切れを試みるのは、その端末が一度 RTDB につながってから（サーバー時刻の補正値が届いてから）。時計のずれた端末が早すぎる時間切れを起こさないようにするため。
- 時間切れの transaction は手元に先に反映しない（`applyLocally: false`）。オフライン中に試したとき、画面に仮の次の回が出ないようにするため。

## 接続・切断・再接続

esadori と同じ **presence のノード有無方式**。

| 役割 | onDisconnect 予約 |
|---|---|
| ホスト | `ctl` に `update({ hostConnected: false, hostDisconnectedAt: TIMESTAMP, 'players/{host}': null })` |
| ゲスト | `ctl/players/{nick}` に `remove()`（全フェーズ共通） |

- 書いた文・描いた絵はすべて `art` 側にあるため、presence が消えてもデータは失われない。
- `.info/connected` が true になるたびに「復帰の書き戻し」transaction（`ctl` 対象・キャッシュを温めてから）を行う。検証: ctl がある・期限切れでない・ホストを名乗るのは host 本人だけ・ゲストは `playing` 中なら `match/order` に居る（進行役のホストは order に居なくてよい。waiting は再参加可・人数上限内）。書き込み: `players/{自分}`、ホストは `hostConnected: true` / `hostDisconnectedAt: null`。確定後に予約を張り直す。
- 再読み込み: sessionStorage `oekaki_session`（roomCode / nickname / isHost / matchId）から同じ書き戻しを行う。play 中なら自分のエントリを `get()` して下書きを復元する。再読み込みからの復帰中は、`.info/connected` 側の書き戻しを走らせない（同時に走ると、キャッシュが温まる前の判定でトップへ戻してしまうため。E2E で発見）。
- `playing` 中に order に居ない人（開始の瞬間に切れていた等）は「ゲームが始まっていたよ。終わったら入りなおしてね」でトップへ戻す。
- **画面の識別子（sid）**: 作成・参加のたびに画面ごとの `sid` を作り、presence と sessionStorage に入れる。書き戻しのとき、同じ名前の presence が別の `sid` なら（ほかの画面で入りなおした）書き戻さず「ほかの画面で同じ名前が入りなおしたので、この画面は終わるよ」でトップへ戻す。同じ名前で2つの画面が同じエントリに書くのを防ぐため。
  - 再読み込みのたびに新しい `sid` を作り、sessionStorage にあった前の `sid` を「引き継ぎの合言葉」にする（presence の `sid` が合言葉と同じなら、自分の続きとして新しい `sid` で上書きする）。「タブを複製」で sessionStorage が写されても、あとから開いた画面が引き継ぎ、古い画面は終わる（Codex 再確認の指摘）。
  - 書き戻しは、呼んだ時点の世代（epoch）と `sid` で固定する。待っている間に「トップへ戻る」などでやめたら、transaction の中で止める。すでに書けていたら取り消す（同じ `sid` の presence を消し、ホストなら `hostConnected:false` にして TTL を始める）。
- **つながらないときに待ち続けない**:
  - 参加・復帰は、ctl の最初の値が12秒届かなければあきらめる（最初の値が届く前なら transaction はまだ走っていないので、何も書き込まれていない）。参加は「つながらなかったよ。通信を確かめて、もう一度ためしてね」。復帰はセッションを残して「つながらなかったよ。通信が戻ったら、ページを読み込みなおしてね」。
  - 復帰に8秒以上かかると、つなぎ直し中の画面に「トップへ戻る」を出す。押したら、リスナー・タイマーを片付けて世代を進め（待ち中の書き戻しは止まる）、書けてしまっていた presence は取り消す。起動時の画面表示は、すでにほかの画面へ移っていたら上書きしない。
  - 退出・「ルームを閉じる」・トップへ戻る処理も、切断予約の取り消しは5秒までしか待たない（取り消しを送ってから削除する順は守る）。削除の返事は待たずに画面を戻す。
  - 切断予約（onDisconnect）の返事は5秒までしか待たない。送った直後に接続が切れると返事が来ないことがある（SDK が送信済みの要求の返事を待つのをやめ、再接続で送り直さない）ため。予約は次の接続のとき書き戻しと一緒に張り直す（Codex コードレビューの指摘）。
  - 作成・参加・復帰は、確定したらすぐ ctl のリスナーを張って画面を進め、切断予約はそのあとにする。
- **在室の書き戻し（つながっている間）**: つながっているのに自分の presence が消えている、またはホストなのに `hostConnected:false` になっているとき（古い接続の onDisconnect があとから発火した等）は、3秒に1回まで書き戻す（間引いた分は、あとで最新の状態でもう一度確かめる）。放っておくと、ホストが画面の前にいるのに2分でルームが消えてしまうため（別エージェント監査の指摘）。
- 切断中の描く側は、全員の完了状況に「通信が切れています」と出す。その子の「完了」は来ないので、時間切れかホストの「しめきる」で進める。空欄のまま回っても遊びは続けられる。
- ホスト切断中、ゲストには共通のオーバーレイ（2分のカウントダウン）を出す。ただし**遊んでいる途中（play）は画面を覆わない帯**で知らせ、描く・書くを続けられるようにする（回は時間切れで進み続けるため。Codex 設計レビューの指摘）。`ORPHAN_TTL_MS = 2 * 60 * 1000`。

## 終了とデータ削除

- 公認バリアント「**ふりかえり画面滞在中は削除しない**」を採用する。`end` では自動削除しない（見返し・もう一回のため）。
- 削除経路: ①ホストの「ルームを閉じる」（`cancelRoomOnDisconnect()` を await → ルート `remove()`） ②ホスト切断＋2分 TTL ③次回アクセス時（参加・復帰・ルーム監視）の期限切れ判定 ④**作った端末の後片付け**（下記）。
- 期限切れ削除: `ctl` への transaction で `isRoomExpired(ctl)` なら null を返す（生きていれば消さない）→ 確定したら `art` を消す。abort した（ルームが生きていた）ら自分の presence ノードだけ消す。
- **作った端末の後片付け**: みんながタブを閉じて終わると、ルームはだれにも開かれず残る（絵のデータが大きいので放置できない）。ルームを作った端末は localStorage `oekaki_my_rooms` にコードを覚え（最大20件）、次にこのページを開いたとき、期限切れのルーム、または作ってから12時間を過ぎたルームを上の手順で消す（12時間の条件は、切断予約の前にタブが落ちて `hostConnected:true` のまま残ったルームも回収するため）。ホストがルームにいる間は、1分ごとに localStorage `oekaki_my_rooms_alive` の「使っている」印を更新し、印が3分以内のルームには12時間の条件を使わない（12時間を過ぎても使い続けているルームを、同じブラウザのほかのタブの後片付けで消さないため）。コードは、次に開いたときの後片付けで ctl が無いことを確かめ、残った art を消してから外す（「ルームを閉じる」でもすぐには外さない。遅れて届いた書き込みで art が残っても回収するため）。別の端末・ブラウザで開いた場合は消えない（既知の制約）。
- ルーム作成は、確定したらすぐ切断予約とコードの記録をし、古い絵の掃除はそのあとにする。
- ゲスト・ホストとも、ctl が null になったら（ホストが閉じた）予約を解除してからトップへ（「ルームが閉じられたよ」）。
- 壊れルーム（`status` や `host` の無い ctl）は、参加・復帰で見つけたら ctl を消して `art` も消す。ctl が無く art だけ残ったものは、参加では探さない（JS SDK に浅い読み取りが無く、確かめるには絵を丸ごと読むことになるため）。作った端末の後片付けで消える。
- 「もう一回あそぶ」では終わったゲームの `art/m{id}` を消す（前のゲームの絵を残さない）。

### 既知の制約（v1）

- presence の書き込みのあとに onDisconnect を予約するため、その間（1往復）にタブが落ちると presence が残りうる（esadori と同じ）。ゲストは次の接続で直る。ホストは `hostConnected:true` のまま残りうるので、作った端末の後片付け（12時間）で回収する。
- 確認ダイアログ（しめきる・途中で終わる・見せあいを終える・ルームを閉じる・退出する）は画面を止める。進行の判定がずれないよう、押した時点の状態は確認の前に捕まえる。「途中で終わる」は確認中に回が進んでいたら、始まったばかりの回を見せあいに入れない。
- ルームが消されたのと同時に届いた線の書き込みは、消えたルームの下に `art` だけを作りうる（ほぼ起きない。作った端末の後片付けでは ctl が無ければ `art` を消す）。
- 締め切りは、回を進めた端末の時計（サーバー時刻補正後）で決まる。補正が届く前の端末は時間切れを起こさない。

## 文言・UX

- 通常表記（漢字まじり）。やわらかい語り口。導入（トップ・あそびかた）で一度だけ遊びを説明し、ボタンは素直な動詞にする（始める・完了・なおす・つぎへ）。
- 回ごとの見出し: 0回目「お題を書こう」、描く回「この文を絵にしよう」、書く回「この絵を文にしよう」。偶数人数の1回目だけ「自分のお題を絵にしよう」。回の表示「3回目 / 全5回」は見出しの上に置く。
- ロビーの「始める」の下に回数を出す（「5人で5回まわすよ」。偶数のときは「4人で5回まわすよ（偶数のときは、最初の絵は自分のお題を自分で描くよ）」）。
- 回ってきた文は「お題表示の定石」（白カード＋ティール枠・ラベル「お題」・文のお題サイズ）で出す。
- 見せあいのエントリは「◯◯さんが書いた」「◯◯さんが描いた」を添える。上手・下手の評価、いいね、投票は置かない。
- 時間切れは責めない（「時間になったよ。次に回すね」）。

## 原作とちがうところ

- **偶数人数のときは1回多く回し、お題を書いた本人が1枚目の絵も描く**（上記「偶数人数で1回足す理由」）。原作は人数と同じ回数で、偶数人数は絵で終わる。

## 共通規約からの逸脱の明文化

- **進行データを `ctl` 子ノードにまとめる**: 共通規約はルーム直下に `status` / `players` などを置くが、絵のデータを transaction から外すため `ctl` 配下に置く。`isRoomExpired` などの共通ヘルパーには ctl の値を渡す（上記「ctl と art を分ける理由」）。
- **回の進行・見せあいへの移行はホスト以外も行う**: 全員同時進行のため、最後の「完了」を押した人・時間切れを検知した人の transaction も進める（esadori の judge と同型）。ルートの `status` の変更はホストのみ。
- **presence はノードの有無方式**（esadori と同じ）。
- **終了後の自動削除なし**（公認バリアント「ふりかえり画面滞在中は削除しない」）。
- **ホストが描く側に入れる**（ロビーの選択。既定オフ。ピッタリメーターの hostPlays と同型）。
- **遊んでいる途中でも、描く側だった名前は入りなおせる**（他アプリは途中参加不可。タブを閉じやすい子ども端末で、その子の列が止まらないようにするため）。入りなおすと古い画面は終わる（sid）。
- **presence に画面の識別子（sid）を持たせ、つながっている間に消えた presence を書き戻す**（他アプリにはない。上記「接続・切断・再接続」）。
- **ホスト切断中の表示を、遊んでいる途中だけ帯にする**（共通はオーバーレイ）。
- **localStorage に自分が作ったルームのコードを覚える**（後片付け用。回答や絵は保存しない）。

## メンター向け進行のコツ

- 画面共有は、進行役（描く側に入らない）なら最初から最後まで共有してよい。遊んでいる間は完了状況しか映らない。**「自分も描く側で参加する」をオンにしたときは、遊んでいる間は共有を止め、見せあいから共有する**（自分に回ってきた文や絵が映るため）。
- 子どもが少ない日（2人など）は、メンターも描く側に入ると3人になって遊べる。
- 見せあいは、1枚めくるごとに「おー」「そうなる？」と一言添えるくらいがちょうどいい。描いた子の絵の上手・下手には触れず、「伝わり方のずれ」を一緒におもしろがる。
- 時間が足りなくなりそうなら「途中で終わる」で見せあいに進めてよい。見せあいまでたどり着くのがいちばん大事。
- 描く人が偶数のときは、1回多く回る（4人なら5回）。時間が気になる日は、描く時間を短めに選ぶか、メンターが描く側に入る・抜けるで奇数にする手もある。
- 自由に書ける欄なので、合わない言葉が出たときはその場でやさしく流す（スタッフの見守り前提。フィルタは置いていない）。
