# キャリアすごろく 仕様書

## 目的・使用シーン

まちをすごろくでめぐって「適性カード」と「職業カード」を集め、最後に持っている職業から1つを選ぶ、選択式のキャリアデザインすごろく。選んだ職業に合う適性が多いほどゲームの得点が高くなる。カードや得点はゲームの中のもので、本人の力や向き・不向きを表すものではない。

| 項目 | 内容 |
|---|---|
| 人数 | 1〜8人（ホストは「自分も参加する」か「進行だけする」を選ぶ）＋見学5人まで |
| 所要時間 | 推定で約18分（1人）〜約28分（8人）。説明・準備・終盤を含むモデルの値で、**45分以内の人による実測はまだ**（下の「試遊で確かめること」） |
| 利用シーン | ボドゲクラブ（2〜8人）・作戦会議（メンターと子ども1人でも成立。1人のときは架空の仕事仲間とコラボし、順位は出さない）。ポータルは `data-scenes="bodoge sakusen"` |
| 操作 | 各自の端末で押すことも、端末のない人の分をホストが代わりに押すこともできる（併用） |

2026-09-27〜28 に `drafts/` で試作し、2026-09-28 にオーナーの指示で移植した。試作の間の記録（決定・バランス・検証・独立レビュー）は [docs/reports/career-sugoroku-2026-09-28.md](../../docs/reports/career-sugoroku-2026-09-28.md)。

## ゲームルール

### 得点

- **職業の点**（最大19点）＝ 中心の適性の枚数×2 ＋ 関連の適性2種類の枚数 ＋ 3種類がそろうと＋3。適性は1種類4枚まで（`data.js` APT_CAP・`engine.js` MAX_SCORE）
- **仕上げのサイコロ**: 最後の職業を決めたあと、出目＋準備チップの合計で点を加える。合計1〜2は＋0、3〜4は＋1、5〜6は＋2、7〜8は＋3
- **準備チップ**（2枚まで）: イベント・コラボの判定でカードが取れなかったとき（別の適性を選ぶ前に手番が終わったときも）＋1。2人でコラボしてサイコロを振ったときは2人とも＋1
- 結果は同点同順位。職業を選ばなかった人は「結果なし（今回は途中まで）」で、最下位や0点にしない。プレイヤーが1人なら順位を出さない

### 流れ

```
入口 ─ ルームを作る（自分も参加／進行だけ）
     ├ ルームに参加する（ゲームに参加／見学）
     └ はじめてガイド・くわしいルール（モーダル）
待合室: ルームコード・参加者・見学者・端末なしの人の追加・設定（時間チップ・選ぶ時間・暮らし・進路）・目安の時間
準備（全員同時）: 理想の職業（まだ決めないも可）→ 最初の適性カード3枚 → 当面の目標（3枚から）
本編: 手番（時間チップ1枚 → サイコロ → 分かれ道 → 止まったマスで選ぶ → 結果 → 手番を終える）
      ＋ 進路のラウンド（全員同時に「進路 → そこでの体験」を選び、適性カード1枚）
最後の職業選び（全員同時）: 持っている職業から1つ → 仕上げのサイコロ
結果発表（職業の点＋仕上げの内訳）
```

- マス: 適性を伸ばす／新しい体験／職業との出会い／イベント（サイコロで判定）／コラボ（だれかをさそって判定。さそわれた人は時間チップ1枚）／暮らしのイベント
- 判定: 5〜6 なら狙った適性を2枚、3〜4 なら別の適性を1枚選ぶ、1〜2 なら今回はなし。持っている適性を狙うと出目＋1
- 進路のラウンド: 時間チップ6枚以上なら2回（2周目と、残りのまん中）、5枚以下なら1回（待合室で変更可）。進路の名前で点が増えたり、選べる職業が限られたりはしない。「今回は進路を決めない」をいつでも選べる
- 暮らしのイベント: 1人1回。ちがう場面のプラン3つ（適性もなるべくちがうもの）＋「どのプランも選ばない」から選ぶ。選んだプランの適性は、この先2回のイベントで＋1、ほかは−1。「選ばない」も1回に数える
- 時間チップ（1人の手番の回数）の推奨: 1〜3人 8枚、4〜5人 6枚、6人 5枚、7〜8人 4枚（待合室で 4/5/6/8/10 から変更可）
- 選ぶ時間: 既定は制限なし（30/45/60秒も選べる）。1手番に1回だけ「もう少し考える」で15秒のばせる。コラボの返事は10秒
- ホストの「進行」: 一時停止・代わりに操作・手番のスキップ・次の1周で終了・すぐに終了・各プレイヤーの見学/戻す/参加を終える・見学者の一覧・時間の計測・ルームを閉じる

## 技術スタック

- **分割ファイル**: `index.html`（骨組み）＋ `style.css` ＋ `data.js`（データ）＋ `engine.js`（ゲームエンジン）＋ `board.js`（盤面の SVG）＋ `net.js`（通信）＋ `ui.js`（画面）。下の「共通規約からの逸脱」1

- 共通モジュール: `design-system.css`（先に読み込み、`style.css` はアプリ固有の値だけを `body` に定義）・`rtdb-utils.js`（`initFirebase`・`now`・`initServerTime`・`generateRoomCode`・`cancelRoomOnDisconnect`・`copyRoomCode`・`esc`）・`howto.js`・`stats.js`

- テストは `tests/career-sugoroku/`（公開されない。README あり）

## Firebase データ構造（Realtime Database）

```
careersugoroku_rooms/{code} = {
  meta:       { v, createdAt, hostId, hostConnected, hostDisconnectedAt }
  game:       エンジンの状態（phase・settings・players・order・turn・career・final・results・log・metrics など）
  presence:   { id: true }            端末でつながっている人（切断で消える）
  spectators: { sid: { name, at } }   見学の人（切断で消える。5人まで）
  cursor:     { pid: { k, i } }       確定前の「選択中」の共有（画面共有で、選んでいる番号が全員に見える）
}
```

- ルームの状態は `status` ではなく `game.phase`（lobby → setup → main → final → results）
- ホストは `meta.hostId`・`game.host.id` で識別する（`players/{nick}/isHost` ではない）
- `meta` か `game` がないルームは、削除のあとに書き込みや予約だけが残った「ゴースト」。期限切れとして扱い、画面では待合室として描かずに退出し、掃除する
- RTDB を往復すると空の配列・null が消えるので、`engine.js` の `normalize()` で必ず形を戻してから使う

### transaction 設計

- **ルーム作成**: ルームルートの transaction で空きコードを確保する。ルームは「ホストの切断中」（`hostConnected: false`・`hostDisconnectedAt`）として作り、ホストの在室の登録で接続中にする（作った直後にホストの端末がいなくなっても、待合室の期限2分で片付く）。送信後に通信が切れても、自分の hostId のルームが届いていれば成功とする
- **参加・端末なしの人の追加・見学の入室・在室の登録**: ルーム全体の transaction（`net.js` transactRoom）で、ルームの有無・期限・人数・名前の重複を確かめることと書くことを同時に確定する。削除と重なっても一部だけのルームを作らない。名前の重複は見学の人も含めてルーム全体で見る
- **ゲームの操作**: `game` の transaction でエンジンに通す（削除済みなら中止し、`game` だけを書き戻さない）
- **SDK の性質**（@firebase/database のソースで確認）: 同じ端末がルームの配下に set/update/remove すると（選択中の共有・退出など）、送信前の祖先の transaction は `Error('set')` で中止される。送信後に通信が切れると `Error('disconnect')` で中止され、書き込みが届いたかは分からない。どちらも4回までやり直し、前の書き込みが届いていれば成功として扱う（期限切れを先に確かめ、ID・名前・操作方法が一致するときだけ）

## 接続・切断・再接続

| 役割 | 挙動 |
|---|---|
| ホスト | 切断時に `meta.hostConnected=false`・`hostDisconnectedAt` を予約。戻ったら true に戻し、不在の時間だけ締め切り（選ぶ時間・招待・進路）を延ばす。不在の間は時間切れを送らない |
| 参加者 | `presence/{id}` を切断時に削除 |
| 見学者 | `spectators/{sid}` を切断時に削除。見学の入室は、transaction の前に切断時の削除を予約する |

- 期限: 待合室は2分（`ORPHAN_TTL_MS`）、ゲーム中は15分（`ORPHAN_TTL_INGAME_MS`。下の逸脱2）。期限を過ぎると、参加者の画面が見つけた時点でルームを消し、「ホストが戻らなかったため、ルームは終了しました」と出してトップへ戻る。期限を過ぎたあとにホストが戻っても、ルームは復活させない（退出してから消す）
- 再接続: `sessionStorage` の `careersugoroku_session`。再読み込みで同じ人として戻る。見学の再登録で、自分の枠が消えていて人数の上限か名前の重複にかかったら退出する
- 在室の登録が例外で終わったとき（同じ端末の書き込みが続く・競合が続く）は、画面にエラーを出さず1・2・4・8・16秒あけて再試行する
- 匿名認証に失敗していたら、次の操作（ルームを作る・参加する など）のときに試し直す（ページを読み込み直さなくても回復できる）
- 時計（選ぶ時間・招待・進路の締め切りと、ホスト不在の表示）は、ルームに入っているあいだだけ動かす（退出・ルームを閉じるで止める）
- 退出・ルームが閉じられた・外されたときは、ガイドなどのモーダルを開いたままでも後ろの画面の `inert` を外す

## 終了とデータ削除

公認バリアント「ふりかえり画面滞在中は削除しない」に相当する。結果画面では自動削除しない（順位と内訳を見ながら話す時間を保つ）。削除は (1) ホストの「ルームを閉じる」（`cancelRoomOnDisconnect` のあと `remove`）(2) ホスト切断の期限 (3) 次回アクセス時の期限切れ掃除、の3経路。

## 負荷（2026-09-28 の見積もり。実測ではない）

- 無料プランの Realtime Database は同時接続100本まで（room-K の全アプリで共有・引き上げ不可）。コードを読む限り、利用回数カウンタ（`stats.js`）はページを開いているあいだ接続を1本持つので、1タブで2本（ゲーム用＋カウンタ用）になる見込み。見学を5人にしたので、最大の部屋（ホスト1＋端末の参加者8＋見学5＝14タブ）で約28本
- 転送量: 8人の回で状態（約6KB）を約150回書き直す → 1台あたり1回の遊びで約1MB。月10GBの枠では問題になりにくい
- カウンタの接続は room-K 全体の話として、別の作業で調査している（2026-09-28 起票）

## 共通規約からの逸脱の明文化

1. **分割ファイル**: Realtime Database アプリは単一ファイルが基本だが、規模（`ui.js` 約150KB・`engine.js` 約65KB）と、エンジンを Node でテストするために分割した。lint の XSS・esc の検査は `scripts/lint.sh` でこのアプリの `*.js` も対象に加えている
2. **ゲーム中の期限15分**（`ORPHAN_TTL_INGAME_MS`）: 45分の回で、ホストの一時的な切断（Zoom の切り替え・回線の不調）でゲームが終わらないようにする。待合室は共通の2分
3. **結果後の自動削除なし**: 上の「終了とデータ削除」
4. **ルームの状態は `game.phase`、ホストは `meta.hostId`**: エンジンが状態を一括で持つため
5. **`?emu=1`**: ローカルのエミュレーター（127.0.0.1）だけに接続する自動テスト用の入口。本番のデータには触れない
6. **`esc`**: `RoomkRTDB.esc` を使い、null / undefined を空文字にしてから通す
7. **見学の上限5人**・**名前の重複は見学の人も含めて禁止**（名前なしの見学は名前の重複の対象外。人数の上限5人には含む）
8. **在室は `presence/{id}` のノード有無**（プレイヤーの一覧 `game.players` とは別に持つ。端末なしの人は presence を持たず、ホストが操作する）

## 既存ガイドラインからの例外（コンテンツ）

ルートの [AGENTS.md](../../AGENTS.md) のコンテンツガイドラインでは、学校を連想させる内容と、恋愛・交際の内容を避けると定めている。このアプリは次の2つを**意図的に例外として扱う**（2026-09-28 オーナー決定）。元の依頼に、進路（高校入学・大学進学・専門学校・就職）と、ライフイベント（結婚・自動車や家の購入・子どもが生まれる）の明示の希望があった。

- **進路の学校名**（「高校・普通科」「高校・専門学科（工業系・商業系・農業系）」「高校・総合学科」「大学・短大」「専門学校（デザイン分野の例・調理分野の例）」「就職」）
  - 条件: 待合室で「進路のラウンド: なし」にできる／「今回は進路を決めない」をいつでも選べる／進路の名前で得点や選べる職業が決まらない／受験・成績の言葉を使わない／本人の志望を聞かない・保存しない
- **結婚・子どものカード**（暮らしのプラン「新しい暮らしを始める（結婚）」「子どもを迎える」）
  - 条件: ゲームが割り当てず、ちがう場面のプラン3つ＋「どのプランも選ばない」から本人が選ぶ／同じ強さの共同生活・カーシェア・賃貸・地域の活動と並べる／出会い・告白などの恋愛の場面はない／全員に見える記録（ログ）にはプラン名を出さない（結果の画面には出る）／待合室で「暮らしのイベント: なし」にできる
- 適用範囲はこのアプリだけ。ほかのアプリへは広げない

## 試遊で確かめること（未検証）

- 45分以内に収まるか（ホストの「進行」→「時間の計測」→「計測をコピー」。記録するのは時間だけ）。45分に収まる1手番の平均の上限は、5人で約96秒、6人・8人で約82秒、7人で約94秒
- はじめてガイド・ヒント・「目標の点＋N」が子どもに伝わるか、情報が多すぎないか
- 得点の差（上限4枚にした効果）。差がつきすぎて途中で「もう勝てない」と感じる子がいたら、上限を3枚に戻すか仕上げの段を見直す
- 進路・暮らし（学校名・結婚・子ども）の受け止め
- Zoom / Meet の画面共有での見え方。1280×720 で測ると、職業カードが並ぶ画面（準備の「理想の職業」・最後の職業選び）は文字の半分以上が11〜12px。読めなければ職業カードの文字を大きくする
- 実機のスマートフォン・タブレットでの操作、別々の端末からの参加、長い切断

## メンター向け進行のコツ

- はじめに「はじめてガイド」を画面共有で一緒に見る（上のバーの「ガイド」からいつでも開ける）
- 端末のない子は、待合室の「端末なしで参加する人を追加」で入れ、番号を言ってもらってホストが押す（数字キーでも選べる）
- 進路や暮らし（学校・結婚・子ども）の話題が気になる子がいる回は、待合室で「進路のラウンド」「暮らしのイベント」を「なし」にする
- 疲れた子には、自分の番の「今回はスキップ」「しばらく見学」をすすめる。カードはなくならない
- 「理想の職業」は点数と関係なく、なってみたいもので選んでよいことを伝える。「まだ決めない」でもよい
- 得点はゲームの中のもの。結果を本人の向き・不向きに結びつけて話さない
