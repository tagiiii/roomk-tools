# キャリアすごろく 仕様書

## 目的・使用シーン

- 子どものころから、おとなになるまでを、すごろくで進むボードゲーム。いろいろな体験で「適性」をため、しごとの道に進むときに、たまった適性に合う職業を選ぶ。適性に合う職業ほど、しごとマスでもらえるポイントが多い。ゴールしたとき、ポイントがいちばん多い人の勝ち（1番にゴールするとボーナスもある）
- 学びとしてのねらいは「適性から職業を選ぶ」こと（2026-09-29 オーナー）。適性から職業を選ぶことが、そのまま勝ち方になるように作っている
- 1〜6人。目安は4人で30分くらい。ボドゲクラブ・作戦会議の少人数の回など
- 経緯: 前の版（v1）は 2026-09-28 に公開し、同日ゲーム性の見直しのためいったん公開停止（最後の公開版 `e038b50`、仕様は `git show e038b50:apps/career-sugoroku/AGENTS.md`）。v2 は `drafts/career-sugoroku/` で作り直し、2026-09-29 にオーナーの試遊で了承（`049dfb1`）→ Codex の2回目の独立レビューを反映（`a2b1978`）→ オーナーの指示で `apps/` に移し、ルーム（各自の端末）に対応した。試作とレビューの記録は `docs/reports/career-sugoroku-v2-2026-09-29.md`

## 遊び方は2つ（2026-09-29 オーナーの決定）

- **ルーム（各自の端末）**: ホストが「ルームを作る」、ほかの人は「ルームに参加する」（名前 → ルームコードの順）。自分の番は自分の端末で押す。ホストは、端末のない人（待合室で「端末のない人を追加」）と、つながらなくなった人の番を代わりに押せる。ホストは遊んでも、進行だけでもよい（「ホストも遊ぶ」）
- **1台の画面であそぶ**: 試作のときと同じ。1台の画面をみんなで見て、メンターが代わりに押す。ゲームの通信はしない（利用回数カウンタだけ）。状態はそのタブの sessionStorage（`careersugoroku_local`）にだけ残る
- どちらも同じエンジン（engine.js）・同じ画面（ui.js）。ルームでは、表示する状態はルームから届いたものだけで、操作は通信（net.js）でエンジンに通す
- 見学（参加しないで見るだけの端末）は入れていない。画面共有で足りるため（v1 にはあった）

## Firebase データ構造（Realtime Database）

`careersugoroku_rooms/{code}`（ルールはワイルドカードのため変更なし。`database.rules.json` は変えていない）

| キー | 中身 |
|---|---|
| `meta` | `{ v: 2, createdAt, hostId, hostName, hostConnected, hostDisconnectedAt, dice, labels, gameNo, startedAt, seatSeq }`。`hostId` はホストの端末の ID（匿名認証の uid ではなく、端末ごとの乱数） |
| `status` | `'waiting'`（待合室）/ `'playing'`（ゲーム中）/ `'finished'`（結果） |
| `seats` | `{ sid: { name, dev, no, at } }`。参加する人。`dev` はその人の端末の ID（端末のない人は `''`）。`no` は入った順の番号（`meta.seatSeq` から） |
| `order` | ゲームを始めたときの席の順（エンジンのプレイヤー番号 i ＝ `order[i]`） |
| `game` | エンジンの状態を **JSON の文字列にしたもの**（下の「逸脱」） |
| `presence` | `{ dev: true }`。つながっている端末（切断で消える） |
| `answers` | `{ 'n'+番の番号: { 'p'+プレイヤー番号: 答え } }`。ミニゲームで各自が入れた答え。ミニゲームの結果を出したとき・ゲームが結果（`finished`）になったときに消す |

### status の遷移

`waiting` →（ホストの「はじめる」）→ `playing` →（全員ゴール・ホストの「ここで終えて結果を見る」）→ `finished` →（ホストの「同じメンバーでもう一度」）→ `playing`（`meta.gameNo` が1増える）

### だれが押せるか（room.js の `canAct`）

- 自分の番の端末と、ホスト（だれの番でも代わりに押せる）。ほかの端末のカードはボタンが止まり、「○○さんが選んでいるよ」と出る
- ホストだけ: 「ここで終えて結果を見る」（`end`）、ステージの表示（`labels`）
- ミニゲームの答え（`canAnswer`）は、自分の分。ホストは、端末のない人とつながっていない人の分だけ代わりに入れられる（つながっている人の分は本人が押す）。つながり方が変わると、ホストの画面の答えのボタンも出たり消えたりする。ほかの人の答えは結果まで見せず「答えた／まだ」だけ出す。「結果を見る」を押せるのは、止まった人の端末とホスト
- ミニゲームの結果は、その操作の transaction で読んだルームの `answers` で決める（画面が持っていた答えは使わない）
- 画面で見ていた状態のしるし（`stamp`: rev・phase・seq・turnNo・step の種類・記録の数）を操作に付け、ルームの状態と違えば `stale` で止める（二度押し・同時押し・古い画面からの操作）。`rev` は操作が1つ通るたびに net.js が1増やす数。道を選び直すと状態は前にもどるが、`rev` はもどらないので、選び直す前の画面からの操作も止まる。操作が1つ通るたびにしるしが変わることはテストで確かめている
- 「はじめる」「同じメンバーでもう一度」は、押しているあいだ二度目を受け付けない（`startGame` も待合室・結果のときだけ始めるので、ほかの端末と重なっても1回だけ）
- 性善説: ルールは「認証済みなら読み書きできる」なので、画面とトランザクションで守る（他アプリと同じ）
- 認証: 本番は共通の `RoomkRTDB.initFirebase`（匿名認証）。最初の匿名認証が失敗しても、次に通信するとき（作る・参加する・操作する）に `ensureAuth` がもう一度サインインを試す。席とホストは認証の uid ではなく端末の ID（`dev`）で見分けるので、再読み込みで匿名ユーザーが変わっても同じ席にもどれる

### transaction 設計

- 作成・参加・端末のない人の追加・席を外す・始める・ゲームの操作・ミニゲームの答え・在室の登録は、**ルーム全体の transaction**（確かめることと書くことを同時に確定する。削除と競合しても部分だけのルームを作らない。終わったミニゲームへの答えや、入れてよい人以外の答え・正しくない値も書かない）
- 同じ端末がルームの配下に書き込む（退出のときの在室の削除など）と、送信前の transaction は `Error('set')` で中止される。送信後に通信が切れると `Error('disconnect')` で中止される。どちらも4回まで読み直してやり直す（前の書き込みが届いていれば成功として扱う）
- transaction の最初の実行が空のキャッシュを「削除済み」と取り違えないよう、先に `on('value')` で読み込んでから行う（`withCache`）

## 接続・切断・再接続

- ルームは「ホストの切断中」（`hostConnected: false`・`hostDisconnectedAt`）として作り、ホストの在室の登録で接続中にする（作った直後にホストがいなくなっても、待合室の期限で片付く）
- ホスト: `meta` に `onDisconnect().update({ hostConnected: false, hostDisconnectedAt })`。ほかの人の画面の上に「ホストの接続が切れています（あとN分でルームが閉じます）。自分の番は続けられるよ」。つながりなおすと消える
- 全員: `presence/{dev}` に `onDisconnect().remove()`。つながっていない人は、プレイヤーの一覧に「つながっていない」。ゲームは止めない（ホストが代わりに押せる）
- 自分の通信が切れたら「通信が切れています。つながると自動でもどります」。`.info/connected` でつながったら在室を登録し直す
- 再読み込み: `sessionStorage['careersugoroku_session'] = { code, dev, role, name }` で同じ席にもどる。ルームがない・期限切れ・席がないと分かったときだけ情報を消してトップへ。通信の失敗でルームを読めない（8秒で打ち切り）ときは、情報を消さずに「ルームにもどっています…（通信を確かめています）」を出し、5秒ごと（つながったらすぐ）に約2分まで試し直す（試しは同時に1本だけ）。「トップへ戻る」でやめられる（読み込み中に押しても、あとから読めた結果は使わない）
- ルームから離れるとき（ルームが消えた・期限切れ・外された）は、在室の登録をやめ、切断時の予約（`onDisconnect`）を取り消してから片付ける（予約が残ると、あとで切れたときに `meta` だけのゴーストを作るため）。期限切れのルームを消すのも、取り消しが済んでから
- 在室の登録と、離れるときの予約の取り消しは、1本の列で順番に行う（net.js の `serial`）。同じ入室のあいだの登録は1本にまとめ（つながりなおしと画面の両方から呼ばれても重ねない。登録中に呼ばれたら、終わったあとにもう一度）、離れるときの取り消しは進行中の登録のあと、入り直したときの登録はその取り消しのあとに行う（取り消しはルーム以下のすべての予約に効くので、順番が逆だと新しい予約まで消える）。切断時の予約の片方だけが失敗したら、両方を取り消してから間隔をあけてやり直す。通信が止まっているあいだは列も進まないが、画面はすぐトップへもどる
- 退出: 待合室では席も外す。ゲーム中・結果では席は残し（ホストが代わりに押せる）、在室だけ消す。ホストは「ルームを閉じる」（全員トップへ）
- 期限: 待合室は2分（`ORPHAN_TTL_MS`）、ゲーム中・結果は15分（`ORPHAN_TTL_INGAME_MS`）。期限切れを見つけた端末が消す（ゴースト＝`meta` か `status` がないルームも期限切れとして扱う）

## 終了とデータの削除

公認バリアント「ふりかえり画面滞在中は削除しない」を採用する。結果の画面で自動削除はしない。削除は (1) ホストの「ルームを閉じる」 (2) ホストの切断の期限 (3) 次に見つけた端末の期限切れの掃除 の3経路。結果から「同じメンバーでもう一度」で続けて遊べるようにするため。

## 共通規約からの意図的な逸脱

1. **分割ファイル**（RTDB アプリは単一ファイルが標準）。ルール・文・ルームの決まりを Node でテストするため。lint は `SPLIT_JS_FILES`（`apps/career-sugoroku/*.js`）で XSS・TTL・タイマーの検査に含める
2. **ゲーム中の期限は15分**（待合室は共通の2分）。30〜45分の回で、ホストの一時的な切断（Zoom の切り替え・端末の再起動）を吸収する。name-change の `ORPHAN_TTL_INGAME_MS` と同じ考え方
3. **状態は `status`、ホストは `meta.hostId`**（`players/{nick}/isHost` ではない）。端末ごとの ID で、同じ名前の人がいても区別できる
4. **ゲームの状態は JSON の文字列で持つ**。Realtime Database は null・空の配列を消し、数字のキーを配列に変えるので、エンジンの状態の形をそのまま残すため。ミニゲームの答えのキーも `p0` のように文字列にする
5. **在室は `presence/{dev}` のノードの有無**（ゲストの切断で席を消さない。esadori の方式と同じ）。ゲーム中に席を消すと、その人の番が進められなくなるため
6. **結果の画面では自動削除しない**（上の「終了とデータの削除」）
7. ニックネームの重複は、端末のない人の名前とも確かめる（同じルームで名前が同じ人を作らない）

## 負荷の見積もり（実測ではない）

- 1タブの接続: 1台の画面は利用回数カウンタの1本だけ（localhost 以外）。ルームでは、通信の準備をしたあとはゲーム1本＋利用回数カウンタ＝最大2本。6人の部屋で約12本（無料枠は room-K 全体で100本）
- 1回の操作で書くのは、ルーム全体（ゲームの状態の文字列は6人で最大 約14KB。記録は300件まで）。1ゲームの操作は4人で約150回・6人で約270回（2026-09-29 にエンジンで測った値）

## ゲームの流れ

```
スタート（6さい）
 → 小学生（6〜12さい）
 → 中学生（13〜15さい）… 近道（3マス）／寄り道（5マス・体験マスが多い）
 → 15さいの節目: 学びの道（高校）か、しごとの道（ここで職業を選ぶ）
 → 16〜18さい
 → 18さいの節目: 学びの道（大学・専門学校）か、しごとの道（職業を選ぶ・続ける）
 → 19〜22さい
 → 22さいの節目: 職業がない人は選ぶ（ある人は続けても変えてもいい）
 → おとな（23〜35さい）… 近道／寄り道（成長マスとなかまマスがある）
 → ゴール（35さい）
```

- 1回の番: サイコロを押す → 進む → 止まったマスのカード → 「つぎへ」。押すのはサイコロと、選ぶところだけ
- 節目（15・18・22さい）は、サイコロの目が残っていても必ず止まる
- 節目で選んだ道は、その番のうちなら「もどって道を選び直す」で選び直せる（しごとを選んで職業のカードに進んだあとでも、道を選んだあとの結果のカードでも）。2026-09-29 オーナーの試遊で「就職を選ぶと、やっぱり進学するが選べない」→追加
- マス
  - 体験マス（6色＝6つの適性）: 止まると、その色の適性 +1
  - えらぶ体験マス（6色の輪）: 止まると、ランダムに出てきた3つの適性から1つ選んで +1（選んだ適性の体験の文が出る）。小学生の a3 と中学生の b4（どの道でも通る区間）
  - なかまマス: だれかをさそって一緒に体験。2人とも +1。休んでいる人をさそうと、その人の休みがなくなる
  - イベント: カードをめくる（いいこと・1回休み・もどる・進む・もう1回・みんなで決める・みんなでサイコロ）
  - しごとマス: 通るたびに、今の職業のポイント（+1〜+4。同じマスは1回だけ）
  - 成長マス: 今の職業に合う適性のうち、いちばん少ないもの +1
  - 転職チャンス: 職業を変えてもいい（今のままでもいい）
  - ミニゲームマス: 全員でミニゲーム（下の「ミニゲーム」）
- 学びの道から節目に着くと: 18さいは好きな適性 +1 と 1ポイント、22さいは好きな適性 +2
- しごとマスのポイント: 職業に合う3つの適性のうち、いちばん少ない数 +1（+4まで。3つそろって1以上で +2、2以上で +3、3以上で +4、どれか1つが0なら +1）。ほかの適性がいくら多くても、いちばん少ない適性で決まる。今の適性でいつも計算し直す（あとから育つ）。どの職業でも選べる
  - エンジンとデータの中では、この段階を「★」（stars・STAR_LEVELS・STAR_PAY）と呼ぶ。画面には★を出さず、ポイントで直接言う（下の「画面」）
  - 2026-09-29 オーナーの試遊「1つの特性が1でも、ほかの特性が5たされれば★が増えるのに違和感」で、合計（3・6・9で★2・★3・★4）から変えた。成長マス（今の職業に合う適性のうち、いちばん少ないもの +1）は、このルールにそのまま合う
- ゴールの順のボーナス: 1番目 +8、2番目 +5、3番目 +3、4番目 +2、5番目から +1
- 全員がゴールしたら結果。ポイントの合計が多い順（同点は同じ順位）。時間が来たら、メニューの「ここで終えて結果を見る」で終われる（まだの人は、ゴールに近い順に続きの順位のボーナス。ゴールまでのマス数が同じ人は同じ順位・同じボーナスで、次の順位はその人数だけとばす）
- ゴールした人は応援役になり、まだの人のサイコロに +1 できる（1回の番に1人）

## 作戦（戦略でポイントを増やす）

- えらぶ体験マス（2026-09-29 オーナーの「目標の職業に合う適性を選べるようにしてほしい。運の要素は大切なので、思いどおりに集まらなくてもいい」で追加）: 止まると、ランダムに出てきた3つの適性から1つ選ぶ。選ぶときは各適性の下に「その適性でしごとマスのポイントが上がる職業」が出る（適性→職業の向き）
- 経緯: 同じ依頼で「目標の職業」（しごと図鑑で決めると、選ぶ場面に「目標に合う」が出る。ボーナスはなし）も入れたが、試遊で「ポイントを上げるのが目標か、目標の職業になるのが目標かわかりづらい」。職業を先に決めて適性を集める向きは、ねらい（適性から職業を選ぶ）と逆なので、オーナーの判断でやめた（えらぶ体験マスは残した）。入っていたときの測り直しでは、目標をねらって選ぶ人はゴール時に目標の職業が★3以上になる割合が51%（ねらわない人13%）だった
- サイコロ: はじめの画面で「2つ振って、進む目を選ぶ（作戦あり・既定）」か「1つだけ振る（運まかせ）」を選ぶ
- 2つのときは、振ったあとに「どっちの目で進む？」のカードが出る。それぞれの止まる先（体験マスの色・イベント・分かれ道・節目・途中で通るしごとマスなど）をカードの文と盤面の①②で見比べて選ぶ。カードは駒と反対側に寄せて出し、盤面の目印を隠さない
- しごとマスにぴったり止まると、そのマスのポイントをもう1回（2倍）。2つの目から「急いで進むか、ポイントをねらうか」を選ぶ理由になる
- ぴったりのボーナスを入れたら、ねらってゆっくり進むほうが得になり、1番にゴールする意味が薄れた（4人で「1番にゴールした人が1位」が40%→29%。均等なら25%。同点1位は人数で分けて数えた値）。オーナーの方針3（醍醐味は1番にゴール）に合わせて、ゴールの順のボーナスを 5・3・2・1 から 8・5・3・2・1・1 に上げた（42%）
- 測った効き目（4人・各3000ゲーム。職業と適性とサイコロを考えて選ぶ人と、ランダムに選ぶ人を半々にし、席はゲームごとにランダム。同点1位は人数で分けて数える）: 考えて選ぶ人が平均7.3点多く、1位の割合は47%対3%（均等なら25%）。サイコロの選び方だけ（職業と適性はどちらも考える）の差は平均0.8点・1位28%対22%。いちばん効くのは職業と適性の選び方で、それを選びやすくするために「ポイントが上がる職業」（当時の名前は「★が上がる職業」）の表示としごと図鑑を入れた。★をいちばん低い適性で決める形にしてから、考えて選ぶ人の差は5.6点→6.9点に広がった（足りない適性をねらって育てるのが効く）
- はじめは「サイコロの選び方だけで1.0点」と測ったが、考えて選ぶ人がいつも先に振る席にいた偏りが入っていた（Codex のレビューで指摘。席をランダムにして測り直した）

## ミニゲーム

ミニゲームマスに止まると、全員で遊ぶ。3つを順番に（山札のように）出す。ルームでは各自の端末で自分の答えを押す（ほかの人の答えは結果まで「答えた／まだ」だけ。端末のない人・つながっていない人の分はホストが押す）。1台の画面では、みんなが口・チャット・手で出したものを、メンターが1人ずつ押して入れる。結果はアプリが決める。

| ミニゲーム | 遊び方 | ごほうび |
|---|---|---|
| 大きい？小さい？ | 画面の数（2〜5）より、つぎのサイコロが大きいか小さいかを全員で予想 | 当たった人 +1ポイント。同じ数なら全員 +1ポイント |
| じゃんけん | みんなでコンピューターとじゃんけん（チャットに書くか、手で出す） | 勝った人 +1ポイント |
| 合計ピッタリ | 相談しないで、せーので1〜3を出す。合計が目標と同じならピッタリ | ピッタリなら全員 +1ポイント |

- 勝ち負けは運か協力で決まるものだけにした（うまい子がいつも勝つ形にしない）
- 「大きい？小さい？」「じゃんけん」は、答えを入れなかった人がいても進める（今回は参加なし）。「合計ピッタリ」は全員の数が要る
- 合計ピッタリの目標は、全員1・全員3の端を除いた範囲（人数が n なら n+1〜3n−1）。1人のときは出さない
- ゴールした人・休みの人も参加する
- 答えを隠しておくゲーム（ジェスチャーでお題を当てる など）は、1台の画面だと全員に見えてしまうので入れていない（ルームなら隠せるが、1台の画面と同じ内容にそろえている）

## 画面

- いつも出すのは、盤面・コマ・「○○さんの番」・サイコロだけ
- 出来事は盤面の上のカードで大きく出す。選ぶものには①②③の番号（進行役は数字キーでも選べる。Enter で主なボタン）
- 適性・職業・ポイントは、プレイヤーの名前を押すと開く「手帳」で見る。途中の順位は出さない（コマの位置でレースは見える）
- 適性を選ぶカードでは、各適性の下に「ポイントが上がる職業」（上がる職業がなければ「合う職業」）を出す。今の職業に合う適性には「今の職業（○○）に合う・しごとマス +2→+3」のしるし（上がらないときは「気づく力を2にすると +3」）（2026-09-29 オーナーの試遊で「職業別の適性がわからず選びづらい」→追加）
- しごと図鑑: 全24職業の合う適性3つと、その人のいまのしごとマスのポイントを多い順（同じなら、つぎに上がるまでの不足が少ない順）に出す。適性でしぼれる。上のバー・適性を選ぶカード・手帳から開く
- しごとマスのポイントの見せ方（画面には★を出さない。エンジンの中の★の段階を、しごとマスのポイントで言う。文は `text.js`）
  - 職業を出すところ（職業のカード・しごと図鑑・手帳）は、合う適性3つと、その下の「↑ 工夫する力を1にすると +2」（2つなら「ものづくりと工夫する力を1にすると +2」、3つとも同じなら「3つとも2にすると +3」、いちばん上なら「いちばん上（+4）」）。行の右に「しごとマスで +1」
  - ポイントを決めている、いちばん少ない適性の札にふちをつける。いちばん上（+4）のときは上げる必要がないので、ふちは出さない
  - 説明は「しごとマスでもらえるポイントは、その職業に合う適性3つのうち、いちばん少ない数 +1（+4まで）」にそろえる（しごと図鑑とあそびかたでは「ほかの適性が多くても、いちばん少ない適性で決まる」も）。職業のカードは「たまった適性に合う職業ほど、しごとマスでもらえるポイントが多い。」から始める
  - 結果のカード: 番の人の職業に合う適性がふえたら「○○のしごとマスが +3 に上がった！」／「○○に合う適性がふえた（しごとマスは +2 のまま）」と、合う適性・つぎに上がるには。ほかの人は上がったときだけ1行（なかま・みんなで決める・みんなでサイコロ）。職業についた行と「できごと」の記録は「○○になった（しごとマスで +2）」
  - しごとマスのアイコンは仕事のかばん（前は★の形。職業の評価に見えないように変えた）。ぴったり止まった行はお祝いのアイコン
  - 手帳の適性の欄で、今の職業に合う3つに「○○に合う」のしるし
  - あそびかたの「適性・職業・ポイント」に、写真家の例（気づく力 4・ものづくり 2・工夫する力 1 → いちばん少ない工夫する力が1なので、しごとマスで +2。工夫する力を2にすると +3）
  - 職業のカードは横に広げ、職業の名前と説明を1行にした（行が長くなりすぎないように）。スマホ幅では「しごとマスで +N」を行の下に回す
  - 経緯（2026-09-29）: 「適性と職業や★の関係がわかりづらい」→★ゲージ（★ ■■■ ★ ■■■ ★ ■■■ ★）を入れた → 「★1の職業とは？」「誰が見てもわかりやすいか」→★とゲージをやめ、ポイントで直接言う形に作り直した（適性→★→ポイントの段階を1つ減らし、★が職業の評価に見えないようにした）
- 節目で選んだ道を選び直すと、「できごと」の記録も道を選ぶ前とまったく同じにもどる（選ぶ前の記録の写しを覚えておく。記録は300件で古い順に消えるが、その場合ももどる）
- 画面が切り替わったら、その画面の見出しに焦点を移す（見えなくなった画面に焦点を残さない。ルームを作る・参加するの画面は入力欄へ）。重ねて開く画面（しごと図鑑・手帳・メニューなど）のあいだは、後ろの画面をすべて止め（inert）、Tab はその中で回る
- できごと（記録）・あそびかた・メニューは上のボタンから。1台の画面のメニューは、表示の切り替え・遊んでいる時間・途中で終える・最初にもどる。ルームのメニューは、ルームコード（コードをコピー）・遊んでいる時間と、ホストは表示の切り替え・途中で終える・ルームを閉じる、ほかの人は退出する
- ルームでは、上のバーにルームコード、プレイヤーの一覧に「あなた」「ホストが押す」（端末のない人）「つながっていない」を出す。自分の番でないときは、手番の欄に「○○さんがサイコロをふるのをまっています」、カードに「○○さんが選んでいるよ」（ボタンは止まる。しごと図鑑などは開ける）。ホストがほかの人の番に押すときは「○○さんの代わりに押す」（本人がつながっていれば「○○さんの番。代わりに押すこともできる」）
- ルームで、イベントで「○マス進む・もどる」のカードは、その番の人の端末（とホストが代わりに押す人の分）だけ「OK」を待ち、ほかの端末は少し見せてから進む
- 1台の画面のときの状態はこのタブの `sessionStorage` にだけ残す（再読み込みしても「つづきから」で戻れる。タブを閉じると消える）。古い形で保存された状態は、読み込むときにそろえる（engine の migrate: 「目標の職業」と、その記録を消す。記録の「（★2）」を「（しごとマスで +2）」にする。道を選んでいる途中で保存した古い形は、選ぶ前の記録にもどせないので、その番の選び直しはできないことにする）

## つり合いのシミュレーション（`tests/career-sugoroku/sim.cjs`・各3000ゲーム）

コンピューターの選び方は「道はランダム・寄り道は半々・職業は★がいちばん多いもの・適性を選べるときは★につながるもの（今の職業のいちばん低い適性）・サイコロ2つは止まる先の価値と速さで選ぶ・ミニゲームの答えはランダム」。人の選び方とは違うので、目安として見る。
1位の割合は同点1位を人数で分けて数える（均等なら「1÷人数」）。± は 95% のおおよその幅。

| 人数・サイコロ | 1人あたりの手番 | 1番にゴールした人が1位 | 道ごとの1位の割合（しし／し学／学し／学学） | 平均点（同） |
|---|---|---|---|---|
| 2人・2つ | 12.3 | 56%±2（均等50%） | 49／53／50／48%（±3） | 24.0／24.4／24.5／24.3 |
| 4人・2つ | 12.2 | 41%±2（均等25%） | 22／27／25／25%（±2） | 22.0／22.7／22.5／22.4 |
| 6人・2つ | 12.1 | 33%±2（均等17%） | 15／18／18／16%（±1） | 21.2／21.9／21.7／21.5 |
| 4人・1つ | 12.3 | 42%±2（均等25%） | 21／27／26／26%（±2） | 21.5／22.5／22.2／22.2 |
| 6人・1つ | 12.2 | 35%±2（均等17%） | 14／18／17／18%（±1） | 20.9／21.9／21.8／21.7 |

（2026-09-29、★をいちばん低い適性で決める形にし、えらぶ体験マスを2つ入れたあとの測り直し。最後の★は4人・サイコロ2つで ★1 1%／★2 28%／★3 50%／★4 21%。合計のルールのときは ★2 15%／★3 52%／★4 32% で、平均点は約1.2点下がった。コンピューターは目標の職業を決めない）

「し学」は15さいでしごと・18さいで学びの道。言えるのは「この選び方のコンピューターでは、道ごとの平均点の差は約1点（最大1.0点）で、1位の割合も均等から数ポイントの範囲」まで。しごと→しごとがやや低めの傾向がある（15さいで職業を選ぶ時点では、合う適性3つがそろっていないことが多い。コンピューターでは約4割が★2の職業をまだ持たない）。寄り道と近道の平均点の差は1.0点以内（2人のときがいちばん大きい）。
しごと→しごとの差を縮める試し: 16〜18さいのしごとの道のイベントマスを成長マスにすると、4人・サイコロ2つでは差がほぼなくなるが、6人・サイコロ1つでは最大の差が1.2点→1.1点とほとんど縮まらず、会話のきっかけになるイベントマスが減るので入れていない。試遊で気になれば見直す。
経緯: 最初はしごと→しごとが圧勝 → しごとマスの数・★の段階・学びのボーナスで均した → ミニゲームでイベントマスが減り学びのボーナスが相対的に強まった → ぴったり2倍でレースが弱まり、ゴールのボーナスを上げた → Codex のレビューで数え方（同点・席の偏り）を直して測り直した → ★をいちばん低い適性で決める形にして測り直した → えらぶ体験マスを入れて測り直した（しごと→しごとの差は最大1.2点→1.0点）。

## ガイドラインとの関係

- 学校名: 前の版の決定10（進路の学校名は意図的な例外）を引き継ぐ。今回は盤面の骨組みになるため、はじめの画面とメニューで「年齢だけ」の表示に切り替えられるようにした
- ステージの出来事は、学校に通っていなくても経験できること（遊び・習いごと・家・地域・趣味・アルバイトなど）にした。運動会・修学旅行・部活・テストのような、通っていることが前提の出来事は入れていない
- 道の間に優劣をつけない（長さは同じ。平均点の差は約1点・最大1.0点）
- 職業は診断や推薦ではない。ゲームの中でたまった適性でしごとマスのポイントが決まり、その中から本人が選ぶ（どれでも選べる）。画面に★を出さないのは、職業そのものの評価や「向いていない」に見えないようにするため
- ポイント制は、オーナーの方針5による意図的な選択（遊ぶのは比較的エネルギーのある子の想定。苦手な子がいるのは承知のうえ）
- 結婚・子どものイベントは、まだ入れていない（入れるときは前の版の決定11の条件: 本人が選ぶ・オフにできる）

- 画面の★: エンジンの中の段階（★1〜★4）は、画面では「しごとマスで +1〜+4」と言う（★が職業の評価に見えないように）
- 暮らしのイベント（家・車・結婚・子どもなど）: まだ入れていない（v1 の決定11の条件: 本人が選ぶ・オフにできる）
- ふりかえり（結果のあとに問いに答える画面）: v1 の決定7のとおり入れない

## メンター向け進行のコツ

- ルームでは、ホスト（メンター）が画面共有しながら進めると、全員が同じ盤面を見られる。自分の番は各自の端末で押してもらう
- 端末のない子は、待合室の「端末のない人を追加」で入れ、選ぶものを言ってもらってホストが押す（数字キーでも選べる）。途中でつながらなくなった子の番も、ホストが代わりに押せる
- ホストは、本人がつながっている番でも押せてしまう。まず本人に押してもらい、止まっているときだけ代わりに押す
- ミニゲームは各自の端末で答えを押す。「合計ピッタリ」は、相談しないで出すことを先に伝える
- 学校名のステージが気になる子がいる回は、ルームを作るときに「年齢だけ」にする（あとからホストのメニューでも切り替えられる）
- ポイントはゲームの中のもの。結果を本人の向き・不向きに結びつけて話さない

## 試遊で確かめること（未検証）

- ルームでの1回の長さ（4人で30分前後の見込み）。自分の番以外に待つ時間の長さ
- 自分の番でないとき、カードの「○○さんが選んでいるよ」で待てるか。ホストが代わりに押す場面の分かりやすさ
- ミニゲームを各自の端末で押す流れ（答えがそろうまでの待ち）
- 1台の画面の遊び方との使い分け
