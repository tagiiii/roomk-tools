# エサドリ 仕様書

## 目的・使用シーン

「ハゲタカのえじき」（Hol's der Geier）に着想を得た、同時出し数字カードゲーム。
場に出たエサカード（+1〜+10 / −1〜−5）に対して、全員が手札 1〜15 から1枚を同時に伏せて出し、
プラスはいちばん大きい数字の人がゲット、マイナスはいちばん小さい数字の人が引き取り。
ただし**同じ数字を出した人どうしは無効（かぶり）**。15ラウンドの合計点がいちばん高い人の勝ち。

- **core value**: 「同時に伏せて出す → 一斉オープン」という実物では画面越しに再現しにくい部分だけをアプリが担い、読み合い・かけひき（ゲームの本体）は Metalife の声とチャットで盛り上げる。
- 対象: 小学校中学年〜中学生。ボドゲクラブ（`data-scenes="bodoge"`）。
- 2〜6人。**3人以上推奨**（ロビーに「3人以上がおすすめ」と表示。2人でも開始可）。
- **ホストもプレイヤーとして参加する**。
- **音声なしでチャット参加する子も完全に遊べること**が必須条件。全アクション（カード選択・確定・つぎへ）はアプリ内のボタン操作で完結する。

> 原典「ハゲタカのえじき」の名称・ハゲタカ/ネズミのアート・「えじき」等の固有表現は使わない。
> ルール構造のみ参照し、名称・見た目はすべてオリジナル（ピタハメ・おしつけずかんと同じ判断）。
> 紹介文・早見表では「『ハゲタカのえじき』から着想」と記述的に紹介する。
> 「Web版」「オンライン版」「無料版」等の表現は使わない（共通規約）。

## ゲームルール

### カード

- **じぶんのカード**: 各プレイヤー 1〜15 の15枚。1ゲームで各1回ずつ使い切る。
- **エサカード**: 15枚 = プラス +1〜+10（10枚）と マイナス −1〜−5（5枚）。ゲーム開始時にシャッフルし、毎ラウンド1枚ずつめくる。
  - プラスは「ごちそう」（ティール系の濃色）、マイナスは「くさったエサ」（茶系の濃色）として色分け。数値表記は `+7` / `−3` を大きく。イラスト・絵文字は使わない。

### ラウンドの流れ（15ラウンド）

1. エサカードを1枚めくって公開する（持ち越しがあれば横に並べて見せる）。
2. **picking**: 全員が手札から1枚選んで確定する。確定した人は他の人から「えらんだ！」とだけ見える（中身は非公開）。
3. 全員確定したら **reveal**: 全員のカードを一斉公開し、判定結果を表示する。
4. ホストが「つぎへ」を押して次のラウンドへ。15ラウンド終了で結果画面へ。

### 判定ルール — judge 純関数

judge は以下の入出力を持つ**純関数**として実装する（乱数なし・入力を破壊的変更しない・どの端末が実行しても同一結果）。

```
judge(plays, current, carry) → { taker, cards, canceled, newCarry }
  plays:   { [nickname]: number }   # このラウンド全員の出したカード
  current: number                   # 現在のエサカード（deck[round-1]）
  carry:   number[]                 # 既存の持ち越し（古い順。無ければ []）

  手順:
  1. 2人以上が出した数字（かぶり）をすべて無効にする → canceled（昇順の数値配列）
  2. 無効でない数字が1つ以上ある場合:
     - current > 0 → 無効でない数字の最大を出した人が taker
     - current < 0 → 無効でない数字の最小を出した人が taker
     - cards = [...carry, current]（taker が受け取る全カード）、newCarry = []
  3. 無効でない数字が1つもない（全員かぶり）場合:
     - taker = null、cards = []、newCarry = [...carry, current]
```

- 持ち越しは**符号に関係なく**次にエサカードを取った人がまとめて受け取る（例: +10 が持ち越された次のラウンドが −2 なら、−2 を引き取った人が +10 ももらう）。
- 最終ラウンド終了時に `carry` が残った場合、そのカードは誰のものにもならない。結果画面は `match/carry` を読んで「残ったエサはだれのものにもならなかったよ」と表示する。

### 勝敗

- 15ラウンド終了後、獲得したエサカードの合計点が最も高い人が1位。同点は**全員1位**（タイブレークなし）。
- 合計点はマイナスになりうる（そのまま表示する）。
- 順位は1位のみ強調し、2位以下の順位表は出さない（全員の合計点は一覧表示する。ゲーム中も公開情報のため）。

### 公開情報の設計（記憶負荷を下げる）

- 各プレイヤーの**使ったカード（1〜15 のどれを出し終えたか）**は全員に公開する（原作ではカードカウンティングが実力要素だが、子ども向けに記憶補助として開示する。意図的な逸脱）。
- 各プレイヤーの**獲得エサと合計点**も常時公開。
- **これまでのラウンド履歴**（第Nラウンド: +7 → ◯◯さん / もちこし）を一覧表示し、「どのエサがまだ出ていないか」を数えやすくする。
- 唯一の秘匿情報は「**いま選んでいる（確定した）カードの中身**」だけ。reveal で公開される。

## 画面構成・フロー

```
TOP（screen-top）
 ├── ルームを作る → ニックネーム入力 → ロビー（screen-lobby）
 ├── 入る → ニックネーム + コード入力 → ロビー（screen-lobby）
 └── 見るだけ → コード入力のみ → 共有ボード（screen-board）
                      ↓（ホストが「始める」/ 2人以上・6人まで）
            ゲーム画面（screen-game）
              picking ⇄ reveal をラウンドごとに繰り返す（画面遷移はしない）
                      ↓（15ラウンド終了 / ホストが「途中で終わる」）
            けっか（screen-result）
              status='result': 合計点一覧 + 1位表示
              status='aborted': 「途中で終わったよ。勝負はなし！」（合計点一覧は出さない）
              ホスト: 「もう一度」（result のみ。接続中メンバーで配り直し → screen-game）
                      「トップへ戻る」（ルーム削除）
              ゲスト: 「トップへ戻る」（自分の退出のみ）
```

- `aborted` からの「もういちど」は**無し**（おしつけずかん先行事例に合わせ、中断はトップへ戻る一択）。

### ゲーム画面の構成（全フェーズ共通レイアウト）

- **上部: 場のエサ**: 現在のエサカードを大きく表示（＋持ち越しカードを横に小さく並べる）。ラウンド表示「5 / 15」。
- **中央: フェーズUI**（下記）。
- **プレイヤー一覧**: `match/members` の seat 順で固定。各メンバーの 合計点・獲得エサ（値のチップを並べる）・「えらんだ！/かんがえちゅう…」状態・接続状態（`players/{nick}` ノードの有無で判定）。
- **じぶんの手札**: 1〜15 のカードグリッド。使用済みは打ち消し表示（グレー + 取り消し線）で残す（何を使ったか数えやすく）。
- **ラウンド履歴**: 「① +7 → ◯◯さん」「② −3 → もちこし」形式の一覧（スクロール可）。

### フェーズごとの操作 UI

| phase | 操作できる人 | UI |
|-------|--------------|-----|
| `picking` | 全メンバー（未確定の人） | 手札グリッドから1枚タップ → 選択強調 → 「このカードを出す」で確定。確定後は「みんなを待ってるよ」＋自分の出したカードだけ表示 |
| `reveal` | ホストのみ「次へ」 | 全員の出したカードを一覧表示（かぶった数字は打ち消し + 「かぶり！」）。結果バナー「+7は◯◯さんがゲット！」「みんなかぶった！次に持ち越し」。ホスト以外は見るだけ |

- 確定の取り消しは**できない**（全員確定と同時に判定が走るため。確定前に選び直しは自由）。
- reveal の結果パネルは自動で消さない。ホストが「つぎへ」を押すまで全員に表示する。
- タイマー・制限時間は置かない（時間圧をかけない方針）。効果音なし。

## status 遷移

```
waiting → playing → result（15ラウンド終了）
             └────→ aborted（ホストが「とちゅうでおわる」）
result →（もういちど）→ playing
```

| status | 説明 |
|--------|------|
| `waiting` | ロビー。このフェーズのみ新規入室可。2〜6人 |
| `playing` | ゲーム中。`match/phase` が picking / reveal を持つ |
| `result` | 15ラウンド終了。合計点と1位を表示。ホストは「もういちど」「トップへもどる」 |
| `aborted` | 途中終了。**勝敗なし**。ホストは「トップへもどる」のみ |

- `waiting → playing`（開始）、`result → playing`（もういちど）、`→ aborted` は**ホストのみ**。
- `playing → result` は最終ラウンドの「つぎへ」transaction 内で行う（ホスト操作なので共通規約どおり）。

### 「もういちど」（result のみ・ホストのみ）

- **そのとき `players` にノードがある（=接続中の）人だけ**で配り直す。seat を振り直し、`matchId` を +1 した新しい `match` を丸ごと書く（同一 transaction 内）。接続中が2人未満なら不可（ボタン無効化 + transaction でも拒否）。
- 外された人（切断中に再戦が始まった人）は、再接続時に「`status` が `playing`/`result` かつ `match/members` に自分が居ない」ことを検知したら、「メンバーからはずれたよ」を表示 → sessionStorage を消してトップへ戻る（復帰の書き込みは行わない）。
- result 画面の表示は `match/members` + `match/taken` から描く（result 中にゲストが退出して `players` から消えても、そのゲームの結果表示は変わらない）。
- **v1 の既知の制約**: result 中のゲスト退出と「もういちど」がほぼ同時に起きた場合、順序によっては退出者が新しい match の members に残り、その人の pick を待って進行が止まりうる。切断時と同型の状況であり、ホストの「とちゅうでおわる」で回復する（Codex レビューで議論の上、v1 では許容と判断）。

## Firebase データ構造（Realtime Database）

パス: `esadori_rooms/{roomCode}/`（共通命名規則。セキュリティルール変更不要）

```
esadori_rooms/{roomCode}/
  ├── host:                string          # ホストのニックネーム
  ├── hostConnected:       boolean
  ├── hostDisconnectedAt:  number | null
  ├── status:              'waiting' | 'playing' | 'result' | 'aborted'
  ├── createdAt:           number          # ServerValue.TIMESTAMP
  ├── players/                             # presence: 「いま接続している人」のみ（ノードの有無が接続状態）
  │    └── {nickname}/
  │         ├── isHost:    boolean
  │         └── seat:      number          # 参加順。ロビー表示順
  └── match/                               # 開始・「もういちど」で丸ごと上書き
       ├── matchId: number                 # ゲーム世代。開始=1、もういちどで +1（単調増加の整数）
       ├── members/                        # このゲームの対戦者集合（開始時に固定・不変）
       │    └── {nickname}: { seat: number }
       ├── deck:    [number × 15]          # シャッフル済みエサ。開始時に固定
       ├── round:   number                 # 1始まり（現在のエサ = deck[round - 1]）
       ├── phase:   'picking' | 'reveal'
       ├── carry:   [number, ...]          # 持ち越し中のエサ（古い順）。無ければ absent
       ├── picks/
       │    └── {nickname}: number         # このラウンドの確定カード（クライアント側で秘匿）
       ├── reveal: {                       # 最後の確定 transaction が書く。無ければ absent
       │      plays:    { [nickname]: number },  # 全員分
       │      taker:    string,            # 取った人。全員かぶりのときは absent
       │      cards:    [number, ...],     # taker が受け取った全カード。taker 無しなら absent
       │      canceled: [number, ...]      # かぶって無効になった数字（昇順）。無ければ absent
       │    }
       ├── taken/
       │    └── {nickname}: [number, ...]  # 獲得エサ（獲得順）。合計点は都度集計（重複保存しない）
       ├── used/
       │    └── {nickname}: { [value]: true } # 出し終えたカード（reveal 確定時に更新）
       └── history/
            └── {r001〜r015}: { card: number, taker?: string, carried: boolean }
                                            # taker は取った人が居るときのみ。carried=true は持ち越し
```

### presence 設計（ノードの有無方式）

- `players/{nick}` は「**いま接続している人**」を表す。切断＝ノード消滅、復帰＝ノード再作成。`connected` フラグは持たない。
- ゲーム中の手札・獲得エサ・確定済み pick はすべて `match/` 側にあるため、`players/{nick}` が消えてもゲームデータは失われない。
- 切断表示: `match/members` に居て `players` に居ない人を「◯◯さんの通信が切れています」と表示する。
- この方式を採る理由: 切断時の書き込みが常に `remove()` になるため、**ルーム削除後に onDisconnect 予約が発火してもゴーストデータが再生成されない**（`update()` 予約方式の根本的な穴を塞ぐ）。

### RTDB の配列・null の注意

- RTDB は**空配列・null 値のフィールドを保存しない**（absent になる）。`carry` / `canceled` / `cards` / `taken/{nick}` / `reveal` / `picks` は読み取り時に必ず `|| []` / `|| null` でデフォルトを補う。
- `reveal.taker` の「なし」は **absent** で表現し、判定は `taker == null` で行う。
- `history` のキーは `r` + ラウンド番号ゼロ埋め3桁（`r001`〜`r015`）。固定キーなので transaction リトライでも冪等。

### 秘匿情報の扱い（性善説）

- `picks` は RTDB に平文で入り全端末に届くが、表示は**クライアント側フィルタのみ**:
  - picking 中、`picks/{nickname}` の値は `nickname === 自分` のときだけ描画する。他人は「えらんだ！」のみ。
  - reveal になったら `reveal.plays` を全員分描画する。
- DevTools での閲覧は共通のセキュリティ方針（性善説・スタッフ監視下）どおり許容する。

### transaction 設計

ルーム作成・参加・開始・pick 確定・「つぎへ」・「もういちど」・中断・復帰の書き戻しは、すべて**ルームルートへの `transaction()`**。

**transaction コールバックの共通ルール**:
- コールバックは複数回呼ばれうる。**乱数（deck シャッフル）はコールバックの外で生成**し、コールバック内は入力 room に対する純粋な変換だけを行う。judge も入力を破壊的変更しない。
- **ローカルキャッシュ null 対策**: リスナー未接続の状態から実行しうる transaction（参加・復帰書き戻し・期限切れ/壊れルーム削除）は、コールバックが null で始まると abort だけしてサーバー照会せず終わるため、事前に `get()` したスナップショットを `const cur = room || preRoom` で代用してサーバー照会を強制する（oshitsuke-zukan の確立パターン）。ルーム監視リスナーが張られている間の操作（pick・つぎへ・開始・もういちど・中断）はキャッシュが温まっているため不要。
- クライアントは操作ボタンを押した時点の `matchId` / `round` / `phase` を捕捉し、transaction 内で**現在値と一致するか再検証**する。不一致なら abort（`undefined` を返す）。これにより、遅延・リトライした古い操作が次のラウンドや再戦後のゲームに適用されること（ABA 問題）を防ぐ。

| 操作 | 実行者 | transaction 内の検証 → 書き込み |
|------|--------|--------------------------------|
| 作成 | ホスト | `room == null` → 初期ルーム一式 |
| 参加 | ゲスト | `status === 'waiting'`・人数 < 6・ニックネーム未使用 → `players/{nick}` 追加 |
| 開始 | ホスト | `status === 'waiting'`・自分が `host` かつ `players[自分].isHost`・players が2〜6人 → `status:'playing'` + `match` 一式（matchId=1、members=現 players、deck=外で生成、round=1、phase:'picking'） |
| pick 確定 | 各メンバー | `status==='playing'`・`matchId` 一致・`round` 一致・`phase==='picking'`・自分が `members` に居る・`picks/自分` 未設定・カード未使用（`used/自分/値` 無し）→ `picks/自分 = 値`。書き込み後、**members 全員**（接続状態に関係なく）の picks が揃ったかを同 transaction 内で判定し、揃っていれば judge を実行して `phase:'reveal'`・`reveal`・`taken`・`used`・`carry`・`history/r{round}` を**同じ transaction で確定**（最後に確定した人の端末が判定を書く） |
| つぎへ | ホスト | `status==='playing'`・自分が `host`・`matchId` 一致・`round` 一致・`phase==='reveal'` → `round+1`・`picks: null`・`reveal: null`・`phase:'picking'`。`round === 15` なら代わりに `status:'result'`（match は残す。result 画面は members/taken/carry から集計） |
| もういちど | ホスト | `status==='result'`・自分が `host`・`players` ノード保持者が2人以上 → 上記「もういちど」のとおり |
| 中断 | ホスト | `status==='playing'`・自分が `host` → `status:'aborted'` |
| 復帰の書き戻し | 各自 | 下記「接続・切断・再接続」参照。**単純な `update()` は使わない**（削除済みルームの再生成防止） |

- 合計点・残り手札は `taken` / `used` から都度集計し、別フィールドに重複保存しない。
- 判定に乱数は使わない（タイブレークなし）ため、どの端末が judge を書いても結果は同一。

## 接続・切断・再接続

### onDisconnect 予約

| 役割 | 予約内容 |
|------|----------|
| ホスト | `roomRef.onDisconnect().update({ hostConnected: false, hostDisconnectedAt: TIMESTAMP, 'players/{host}': null })`（TTL 起点の記録と presence ノード削除を1予約で行う） |
| ゲスト | `players/{nick}` への `onDisconnect().remove()`（**全フェーズ共通**） |
| 観戦者 | **予約なし・presence 書き込みなし**（読み取り専用） |

- ゲストの予約は常に `remove()` のため、ルーム削除後に発火しても何も再生成しない。ホストの `update()` 予約が残るのは「ホスト接続中にルームが消える」場合だけだが、期限切れ削除は `hostConnected === false` が前提なのでこの競合は起きない（ホスト自身の「トップへもどる」は予約解除後に削除する）。

### `.info/connected` による自動再接続への追従

Firebase はページをリロードしなくても一時切断から自動再接続する。切断中に onDisconnect が発火して presence が消えたままになるのを防ぐため:

- ホスト・ゲストは `db.ref('.info/connected')` を購読し、`true` になるたびに**復帰の書き戻し transaction** を実行する:
  - 検証: `room != null`・`status` があり期限切れでない・（playing/result なら）`match/members` に自分が居る、または waiting なら再参加可能。
  - 書き込み: `players/{自分}` を再作成。ホストはさらに `hostConnected: true` / `hostDisconnectedAt: null`。
  - commit 成功後に onDisconnect 予約を張り直す。abort した場合はルーム消滅・除外として扱い、予約を張らずトップへ戻す（該当の案内文言を表示）。
- `hostConnected: true` を書くのは**ホストだけ**。観戦者はこの購読自体不要（表示のみ）。

### 切断中の進行

- 切断中プレイヤー（members に居て players に居ない人）には「◯◯さんの通信が切れています」を表示。picking 中は誰を待っているかを全員に表示する。
- 切断中の人の pick も**待つ**（進行が止まる）。ホストはいつでも「とちゅうでおわる」（確認ダイアログ付き）で `aborted` にできる。自動での途中終了・自動スキップ・個別プレイヤーの除外はしない（**v1 の既知の制約**。軽い通信切れは `.info/connected` 復帰で解消され、長い離脱はホスト判断で中断する）。

### 再接続（リロード復帰）

- sessionStorage キー **`esadori_session`**（roomCode / nickname / isHost / matchId）。`matchId` は match の変化を検知するたびに更新する。
- リロード時 `tryReconnect()` で上記「復帰の書き戻し transaction」と同じ検証・書き込みを行う。members に自分が居なければ「メンバーからはずれたよ」でトップへ（sessionStorage 消去）。
- 復帰後は RTDB の値から画面を完全再構築できる（確定済み pick・手札・履歴すべて `match` から導出可能）。
- TTL 判定は `RoomkRTDB.now()` / `isRoomExpired()`（サーバー時刻補正）。`ORPHAN_TTL_MS = 2 * 60 * 1000`。

## 終了とデータ削除

- `result` / `aborted` 画面ではルームを**自動削除しない**（振り返り・「もういちど」のため。jinro 方式）。
- クリーンアップ経路は3つ: ①ホストの「トップへもどる」で即時 `remove()` ②ホスト切断 onDisconnect + 2分 TTL ③次回アクセス時（`joinRoom` / `tryReconnect` / ルーム監視）の期限切れ判定。
- **すべての退出・削除経路で、`remove()` や画面遷移の前に必ず `cancelRoomOnDisconnect()` を await する**（ホストの「トップへもどる」・ゲストの自己退出・期限切れ削除・ルーム消滅検知、の全経路）。
- **期限切れ削除は transaction で行う**: `roomRef.transaction(room => { if (room == null) return; return isRoomExpired(room) ? null : undefined })`。判定と削除の間にホストが復帰しても、生きているルームを消さない。**abort した（ルームが生きていた）場合は、退出済みの自分の presence ノード（`players/{nick}`）を削除して残留を防ぐ**（期限切れ検知＝自分は必ず離脱する文脈のため、予約の張り直しではなくノード削除で整合を取る）。
- **ルーム消滅の検知**: ゲスト・観戦者はルーム値が `null` になったら（ホストが削除）、`cancelRoomOnDisconnect()` を await → sessionStorage を消す → 「ルームが閉じられたよ」でトップへ戻る。
- **壊れルームの扱い**: `joinRoom` / `tryReconnect` で `status` や `host` の無いルーム（万一の残骸）を見つけたら期限切れと同様に transaction で削除を試み、参加者には「そのルームはもうないみたい」と表示する。
- ゲスト側の「トップへもどる」は自分の退出のみ（`cancelRoomOnDisconnect()` → `players/{nick}` を `remove()` → sessionStorage 消去）。

## 共有ボード（screen-board）= 観戦モード

- TOP の「みるだけ」からコード入力のみで入る。ニックネーム不要・`players` に**書き込まない**・上限なし・読み取り専用（onDisconnect 予約も張らない）。
- 表示: 場のエサ（持ち越し込み）/ ラウンド表示 / members 全員の合計点・獲得エサ・「えらんだ！」状態 / reveal 時は全員の出したカードと結果バナー / ラウンド履歴 / result・aborted 相当の表示。
- **picking 中の picks の中身は一切描画しない**（「えらんだ！」のみ）。手札グリッドも出さない。
- 用途: ①メンターが画面共有するとき（自分の参加画面には選択中のカードが映るため、共有はこの画面で行う）、②観戦したい子。
- sessionStorage 復帰は不要（コードで入り直せばよい）。ルーム消滅時はトップへ戻る。

## 文言・UX ガイド

- 通常表記（漢字まじり。ルート AGENTS.md「表記トーン」参照）。導入（howto・ロビー）で一度だけ世界観を説明: 「エサをねらう鳥になって、1〜15のカードでエサを取り合うよ。同じ数を出した人同士は無効！」。以降のボタンは素直な動詞（出す・次へ・もう一度）。
- かぶりの表示は明るく（「かぶり！」）。責める演出はしない。
- マイナスを引き取る場面もユーモラスに（「−3は◯◯さんが引き取り…」）。
- 1位の表示はやわらかく祝う（「1位は◯◯さん！」）。2位以下の順位表・煽り文言は出さない。
- 数字カードは数値そのものが内容なので、丸数字（①②）の採番ルールは適用しない（ラウンド履歴の①②は装飾でなくラウンド番号）。

## 共通規約からの逸脱の明文化

- **競争要素（点数・1位）を意図的に残す**: 「比較を促さない」ガイドラインの例外案件（先行事例: ピタハメ、おしつけずかん）。読み合いの緊張感がこのゲームの核であるため。ただし順位表・敗者を責める演出は置かない。
- **match の更新はホスト以外も行う**: `status` の開始/再戦/中断/終了はホストのみだが、pick 確定と judge（reveal 書き込み）は各メンバーの transaction が行う（全員同時アクションのゲームであるため）。
- **presence はノードの有無方式**: 共通規約の「playing 以降は connected:false 方式（jinro）」ではなく、ゲスト切断は全フェーズ `onDisconnect().remove()` とし、接続状態を `players/{nick}` ノードの有無で判定する。ゲームデータを `match/members` ほか match 側に固定してあるため remove しても失われず、ルーム削除後の予約発火でゴーストが再生成されない利点を優先した（本リポジトリ初のパターン。Codex レビュー指摘による設計変更）。
- **result 後の自動削除なし**: 「もういちど」と振り返りのため（先行事例: jinro, word-wolf, tatoe-narabe）。
- **観戦（共有ボード）モード**: players に入らない読み取り専用ロール（先行事例: おしつけずかん、hint-de-pinto、codenames）。
- **使用済みカードの公開**: 原作はカードカウンティングが実力要素だが、記憶補助として全員の使用済みカードを開示する（子ども向けの意図的な設計）。
- **最小人数 2人**: 既存アプリは 3人以上が多いが、原作どおり2人でも成立する（かぶり=持ち越しが機能する）ため 2人から開始可とする。

## メンター向け進行のコツ

- このゲームの本体は**「みんな何を出すか」の読み合い**。最初のゲームは「+10 のとき、みんな 15 を出したくなるよね？ かぶったらどうなる？」と一言添えると駆け引きが立ち上がる。
- 画面共有は**必ず「みるだけ」（共有ボード）で行う**。自分の参加画面を共有すると選択中のカードが映る。
- 声の子とチャットの子が混ざっていても、進行はすべて画面に出るので置いていかれない。reveal のたびに「えー！」「かぶった！」の反応をチャットでも促すと盛り上がる。
- 強いカード（14・15）や小さいカード（1・2）を**どこで使うか**が悩みどころ。2ゲーム目から急に上手くなる子が多い。
- 1ゲームは10〜15分程度。持ち越しが起きたラウンドがいちばん盛り上がる。
- 途中で抜けたい子・接続が戻らない子が出たら「とちゅうでおわる」で仕切り直してよい（勝負なし表示になる）。
