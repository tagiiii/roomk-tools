# ドまんなか 仕様書

## 目的・使用シーン
数字で「いいセン」を狙うリアルタイム対戦パーティーゲーム。
メンターが画面共有しながら若者と一緒にプレイする。

## ファイル構成
```
apps/do-mannaka/
└── index.html   # 単一ファイルで完結（Firebase Realtime Database使用）
```

## 画面フロー
```
TOP
 ├── ホスト → ニックネーム入力 → ルーム作成・待機
 │             （答える人が3人以上でゲーム開始可。
 │              「自分もプレイヤーとして参加する」を選べる）
 ├── ゲスト → ニックネーム＋コード入力 → 参加待機
 └── 参加用のリンク ?room=CODE → 参加画面（コード入力済み・ニックネームだけ入れる） → 参加待機
                       ↓
              問題選択（ホストのみ操作 / ゲストは待機表示）
                       ↓
              回答入力（答える人全員 / 全員送信で自動進行）
                       ↓
              結果発表（ラウンドスコア表示）
                       ↓
              ホスト操作：次の問題 or ゲーム終了
                       ↓
              最終結果（順位表・優勝者表彰）
```

## 参加用のリンク（2026-10-05）
- 参加用のリンク `?room=CODE` と「リンクをコピー」（`#btnCopyLink`）。共通仕様は docs/development/rtdb.md「参加用のリンク」。このアプリの入口は index.html 末尾の初期化（`tryReconnect()` の直前で `?room=` を見る）、参加画面は `#screen-guest-join`（ヒント `#joinLinkHint`）。`?room=` は `startRoomListener()`（作成・参加・再接続の共通の通り道）でアドレスから外す
- ルームバーがないので、「リンクをコピー」はホストの待合室の「コードをコピー」の下に置く（参加者側にはコピーボタンがない。従来どおり）。コピーは共通の `RoomkRTDB.copyRoomLink`（`copyToClipboard` はコード専用の `copyRoomCode` なので使わない）
- リンクの検査は作られるコードの形 `/^[A-HJ-NP-Z2-9]{6}$/`（`ROOM_CODE_PATTERN`）。参加フォームの検査（`/^[A-Z0-9]{6}$/`）は変えていない。画面の欄名に合わせ、ヒントとあそびかたは「名前」でなく「ニックネーム」

## ホストの参加（2026-10-01）
- 待合室でホストだけに「自分もプレイヤーとして参加する」チェックを出す（初期値オン＝従来どおりホストも答える）
- 保存先は `settings/hostPlays`。ホストだけが `status === 'waiting'` の間に room transaction で書く。ゲーム開始後・結果画面では変えない（終了後は「もう一度遊ぶ」で TOP に戻るので、待合室に戻る経路はない）
- キーがない部屋（旧版のクライアントが作った部屋）は `hostPlays !== false` で「答える」扱い
- 答える人 = `hostPlays` なら `players` 全員、そうでなければホスト（`isHost` またはホスト名）以外。回答数（「N 人 / M 人が回答済み」・全員そろったら自動で結果）・採点・結果の一覧・現在のスコア・最終順位はすべて答える人だけで数える
- 最少3人は答える人で数える。待合室の人数表示は「答える人 N人」、足りないときは開始ボタンを無効にして「答える人があと N人必要です」を出す
- 進行だけのホスト: 待合室の一覧のバッジが「ホスト・進行役」になる。回答画面は回答欄を出さず、お題・回答数・「回答を締め切って結果へ」だけ。お題選び・次の問題へ・ゲーム終了は従来どおり
- ホストの `players/{host}` ノード（score・answer）は従来どおり作るが、進行だけのときは集計に入れない
- 答える人が全員抜けて進行役だけ残った場合: 回答数は 0 人 / 0 人のままで、自動の結果移行（回答1件以上が条件）も締め切りボタンも動かないので、書き込みは起きない。回答画面のホスト操作に「答える人がいなくなりました」と「ゲームを終了する」を出す（答える人が1人以上いる間は出さない。たとえグランプリと同じ扱い）。終了は結果画面の「ゲームを終了する」と同じ `hostEndGame()`（`status: 'finished'`・`deleteAt`・30秒後の自動削除）。最終結果は優勝の欄を出さず「遊んだ人はいませんでした」

## 得点ルール
| 条件 | 得点 |
|------|------|
| 中央値の回答者 | +50pt |
| 最大値 or 最小値の回答者 | -10pt |
| それ以外 | ±0pt |

- 偶数人数のとき: 真ん中の2つの回答者をどちらも中央値として +50pt（2026-10-01 オーナー判断。旧仕様は下側の中央値のみ）
- 人数は「そのラウンドで回答した人数」で数える（締め切りで未回答の人は含めない）
- 中央値が複数人いる場合: 全員 +50pt
- 最大値 or 最小値と同じ数字は中央値にしない（2026-10-01 オーナー判断。旧仕様は中央値判定を優先）
  - 偶数で真ん中の2つの片方だけが該当: もう片方だけ +50pt（例: 1・2・3・3 は 2 だけ +50pt、1 と 3 の2人は -10pt）
  - 中央値が残らない（例: 3・3・5、1・3・3、回答2人の 10・30、1・1・3・3、全員同じ数字）: その問題は全員 ±0pt（アウトも付けない）。結果画面に「この問題はいいセンなし。全員 ±0pt」と表示する

## Firebase データ構造（Realtime Database）
```
domannaka_rooms/{roomCode}/
  ├── host:             string        # ホストのニックネーム
  ├── hostConnected:    boolean       # ホスト接続状態
  ├── hostDisconnectedAt: number|null # ホスト切断時刻
  ├── status:           string        # waiting | selecting | answering | result | finished
  ├── currentQuestion:  string        # 現在の問題文
  ├── round:            number        # 現在のラウンド数
  ├── usedQuestions:    number[]      # 使用済み問題インデックス
  ├── pendingQuestions: {q, i}[]      # ホストが選ぶ候補問題（3問）
  ├── settings/
  │    └── hostPlays: boolean         # ホストも答えるか。ホストだけが waiting 中に書く。キーなし（旧版の部屋）は true 扱い
  └── players/
       └── {nickname}/
            ├── score:  number        # 累計スコア
            ├── isHost: boolean
            └── answer: number | null # 現ラウンドの回答
```

## 離脱時の挙動
- **ホスト離脱**: `onDisconnect().update()` で `hostConnected=false` と `hostDisconnectedAt=ServerValue.TIMESTAMP` を保存。ゲストにはオーバーレイを表示し、2分TTL（`ORPHAN_TTL_MS`）超過後に期限切れルームとして削除を試みる
- **ゲスト離脱**: `onDisconnect().remove()` でそのプレイヤーデータのみ削除
- 採点（結果へ進む）はルーム全体の transaction で、その時点の `players` にいる答える人だけで採点し、その人たちだけに書く（自動の結果移行・締め切りボタンの両方）。読み取ってから `update` すると、直前に退出した人のノードを score だけで作り直してしまう（2026-10-01 修正）。`status === 'answering'` のときだけ確定するので二重に加点しない
- ホストは `.info/connected` を監視し、ページを開いたままの通信回復でも `onDisconnect` を再登録してから `hostConnected=true` / `hostDisconnectedAt=null` に戻す（2026-09-06 B-25）。リロード時の `sessionStorage: domannaka_session` 復帰も同じ処理を使う
- 復元はルーム全体の transaction で存在・ホスト名・既知の status・2分TTL・終了後の削除期限を検証し、削除済み／期限切れルームを作り直さない。`finished` は削除期限前のみ復元する
- 退出・ルーム削除通知・終了後の自動削除では接続リスナーを解除し、進行中処理を無効化してから切断予約を取り消す。別接続との削除競合をクライアントだけで完全に防ぐものではなく、ホスト名や sessionStorage は認証境界ではない。ゲスト復帰方式は変更しない
- TTL 判定は `.info/serverTimeOffset` を使ったサーバー推定時刻で行う

## 特有のルール・制約
- ゲーム中の名前だけによる再参加は拒否し、復帰は同じタブの保存済みsessionによる `tryReconnect()` のみとする（2026-09-09 P-12）。sessionStorageは認証境界ではなく、別端末の本人確認を追加したものではない。待機中の通常参加・ホスト名の参加拒否・既存の保存復帰処理は維持する。
- ルームコードは6桁英数字（紛らわしい文字除外）
- ニックネームは1〜8文字・同ルーム内重複NG
- 答える人が3人以上でないとゲーム開始不可（進行だけのホストは数えない）
- 問題は重複しないようにトラッキング（全問使用後はリセット）
- ゲーム終了30秒後に Realtime Database のルームデータを自動削除。削除の transaction は `applyLocally:false`（確定前の null をルーム監視に通知すると、監視の `roomRef.off()` が transaction 自身の購読まで外して削除が届かない）
- Firebase compat SDK の初期化は `RoomkRTDB.initFirebase(firebase)` を使用する
  - **Realtime Database** を使用（Firestoreではない）
  - 匿名認証の完了は返り値の `authReady` を await してから読み書きする
