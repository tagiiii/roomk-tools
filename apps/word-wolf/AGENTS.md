# ワードウルフ 仕様書

## 目的・使用シーン
全員にお題が配られ、ひとりだけ違うお題を持つ「ウルフ」を会話から見つけ出す正体隠し系ゲーム。
メンターと若者が Zoom / Meet 等で画面共有しながら一緒にプレイする。

## ファイル構成
```
apps/word-wolf/
└── index.html   # 単一ファイルで完結（Firebase Realtime Database 使用）
```

## 画面フロー
```
TOP
 ├── ホスト → ニックネーム入力・設定（討論時間・ウルフ人数）→ 待機（ここで「自分もプレイヤーとして参加する」を選ぶ）
 ├── ゲスト → ニックネーム＋ルームコード入力 → 待機
 └── 参加用のリンク `?room=CODE` → 参加画面（ルームコード入力済み・ニックネームだけ入れる） → 待機
                     ↓
           お題確認（タップして自分のお題を見る・全員準備完了でホストが討論スタート）
                     ↓
           討論フェーズ（カウントダウンタイマー付き）
                     ↓
           投票フェーズ（ウルフだと思う人に投票）
                     ↓
           結果発表（ウルフ公開・投票集計・勝敗判定）
                     ↓
           ホスト → もう一度 or 終了
```

## 参加用のリンク（`?room=CODE`。2026-10-05）
- 待合室のホスト向けパネル（ルームコードの下）に「コードをコピー」と並べて「リンクをコピー」（`id="btnCopyLink"`）。ルームコードはホストにだけ出るので、このボタンもホストだけ。共通仕様は docs/development/rtdb.md「参加用のリンク」
- このアプリの入口は `<script>` 末尾の「初期化」（`?room=` → 保存した記録 `wordwolf_session` の順。`?watch=` はない）。参加画面は `screen-guest-join`、ヒントは `joinLinkHint`。`?room=` は `startRoomListener`（作成・参加・再接続の共通の接続処理）で外す
- 入力欄の名前が「ニックネーム」なので、ヒント・あそびかた・スライドのノートは「名前」でなく「ニックネームだけ入れる」と書く
- 同じコードの記録が残っているときの再接続は `tryReconnect()` の戻り値だけで判定する（このアプリの `tryReconnect` は途中で `state.roomRef` を入れてから失敗を返すことがあるため。kagi-awase の `|| state.roomRef` は使わない。失敗したら記録を消して参加画面へ）

## ホストの参加（2026-10-01 オーナー決定）
- 待合室のホスト専用の設定欄に「自分もプレイヤーとして参加する」（初期値: 参加）。変えられるのは待合室だけ（`status: 'waiting'` の transaction でだけ書く）。結果から「もう一度」で待合室に戻ったときも変えられ、変えなければ前の値を引き継ぐ
- 保存先は `settings/hostPlays`。作成時 `true`。キーがない旧ルームは参加扱い（`hostPlays !== false`）
- **遊ぶ人** = ホストが参加するなら全員、しないならホスト以外。お題・ウルフの割り当て、準備完了、投票（する側・される側）、票の集計、投票結果の一覧は遊ぶ人だけが対象
- 進行だけのホストには誰のお題も出さない（`word: ''`・`isWolf: false`。市民・ウルフどちらのお題も知らない進行役）。お題確認・討論・投票の画面では自分のお題・投票ボタンを出さず、「討論スタート！」「投票フェーズへ」「投票を締め切って結果へ」「もう一度」と全体の様子（準備状況・投票済み人数）だけを出す
- 待合室・お題確認・討論の参加者一覧で、進行だけのホストの行に「進行役」タグ
- 最少3人は遊ぶ人だけで数える（開始ボタン・案内文「あと N 人でスタートできます」も同じ）
- 遊ぶ人が全員抜けて進行だけのホストが残ったとき: お題確認では討論を始めず（準備待ちの案内と退出ボタン）、投票では自動で結果にしない（0/0 で結果を書き続けない）。ホストが退出してルームを作り直す
- 進行だけのホストも `players/{host}`（`isHost: true`）は残るので、リロード後もホストとして戻れる

## 勝敗ルール
- 最多票を獲得した人がウルフ → **市民の勝ち**
- 最多票が複数人いる（同票）or ウルフ以外が最多票 → **ウルフの勝ち**

## Firebase データ構造（Realtime Database）
```
wordwolf_rooms/{roomCode}/
  ├── host:             string          # ホストのニックネーム
  ├── hostConnected:    boolean         # 切断検知用
  ├── status:           string          # waiting | revealing | discussing | voting | result
  ├── citizenWord:      string          # 市民のお題
  ├── wolfWord:         string          # ウルフのお題
  ├── discussionSecs:   number          # 討論時間（秒）
  ├── wolfCount:        number          # ウルフの人数
  ├── discussionEndsAt: number          # 討論終了タイムスタンプ（ms）
  ├── citizenWin:       boolean         # 結果（市民が勝ったか）
  ├── voteCounts:       object          # {nickname: 票数}（遊ぶ人の票・遊ぶ人への票だけ）
  ├── settings/
  │    └── hostPlays:   boolean         # ホストも遊ぶか（作成時 true・キーなしは true 扱い・待合室でだけ変更）
  └── players/
       └── {nickname}/
            ├── isHost:  boolean
            ├── isWolf:  boolean        # 結果まで非表示（UIレベル）。進行だけのホストは常に false
            ├── word:    string         # 自分のお題のみ参照する。進行だけのホストは ''
            ├── ready:   boolean        # お題確認済みか
            ├── vote:    string | null  # 投票先ニックネーム
            ├── presenceVersion: 1     # 新方式のゲスト接続情報
            └── connections/{id}: true # 接続ごとの生存記録（ゲストのみ）
```

## セキュリティ注意事項
- Firebase Realtime Database はフィールドレベルの読み取り制御が難しいため、`isWolf` や他プレイヤーの `word` はDB上では見えてしまう
- UIレベルで自分の `word` のみを表示し、結果発表まで他人の情報を出さない
- DevTools でのカンニングは性善説で許容する（スタッフ監視下での使用のため）

## 特有のルール・制約
- ルームコードは6桁英数字（紛らわしい文字除外）
- ニックネームは1〜8文字・同ルーム内重複NG
- 遊ぶ人が3人以上でないとゲーム開始不可（進行だけのホストは数えない）
- ウルフは1人または2人（ホストが設定）。実際に配る人数は `min(設定値, 遊ぶ人数 − 1)`（人数は遊ぶ人で数える。ホストも遊ぶ3人ならウルフ2人もありうる）
- 討論時間は 3分 / 5分 / 7分 から選択
- ゲスト一時切断: 接続ごとの `connections/{id}` だけを `onDisconnect().remove()` し、player本体（役割・お題・準備・投票）を保持する。明示的な「退出する」ではplayerを削除する
- ホスト離脱: `hostConnected` を false にする。ゲストはオーバーレイ表示

## セッション削除の例外

### ゲスト保持の共通規約例外（2026-09-08 B-26 / P-11）

- waiting／resultを含む参加期間全体でゲストを保持する。待機からゲーム中に削除予約を切り替える競合を避けるため、待機中もplayer全体の削除予約は張らない。
- `.info/connected`の接続ごとに新しい識別子を作り、削除予約の受付後にroom transactionで存在・有効フェーズ・期限・既存guestを再検査して接続情報を追加する。旧接続の削除は新接続の記録を消さない。切断時はremoveのみなので削除済みroomを再生成しない。
- sessionStorageが残る同一タブ等からの復帰に限定する。消えたguestの再追加や、名前入力だけのゲーム中再入室はしない。保存情報は本人確認・別端末復帰の保証ではない。
- 接続確認完了前は準備・投票操作を止める。操作もroom transactionで存在・フェーズ・在籍を確認し、ready／voteだけの部分ノードを作らない。
- 待機・再戦後は切断者を表示し、在籍ゲスト全員の接続まで開始を待つ。旧方式データは互換上接続中扱い。お題確認は全員ready待ちを維持し、戻らない人がいる場合はホストが退出して新ルームを作る。自動除外・個別キック・役割再抽選はしない。
- 投票対象・役割・既投票は切断状況で除外しない。既存のホスト締切で未投票を票なしとして進められる。
- 退出・room消失・期限切れでは接続監視と処理世代を無効化し、遅れて完了した接続登録を回収する。ホストの接続方式・2分TTL・結果からの再戦は既存維持。
- 旧版の別接続が予約したplayer全体のremoveは新版から取り消せない。公開後は全員が新版を読み込んだ新規ルームで試す。稼働中の旧ルームの無停止移行は保証しない。

ルート規約ではゲーム終了後30秒でルームを削除するのが基本だが、ワードウルフでは `status: 'result'` 到達後に自動削除しない。

- 理由: 結果発表画面から「もう一度」で同じルーム・同じ参加者のまま再戦できるようにするため
- クリーンアップ: ホストが「退出する」場合は `leaveGame()` でルームを即時 `remove()`、ゲストは自分の `players/{nickname}` のみ削除
- 孤立ルーム対策: ホスト切断時は `hostConnected=false` / `hostDisconnectedAt` を保存し、ゲスト側の2分TTL（`ORPHAN_TTL_MS`）または次回アクセス時の期限切れ判定で削除を試みる

## お題ペアのガイドライン
- 近いけど微妙に違う2つのワードを選ぶ（例: カレー / シチュー）
- 学校・勉強・宿題を連想させる表現は使用しない
- 恋愛・暴力・ホラー系は使用しない
- 小学生〜中学生が知っているお題を選ぶ
