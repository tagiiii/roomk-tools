# ヒット&ブロー 仕様書

## 目的・使用シーン

かくれた色のならびを予想し、そのたびに出るヒント（ヒット＝色も場所もあっている数、ブロー＝色はあるけれど場所がちがう数）を手がかりに当てる推理ゲーム。

- **core value**: 1回ごとのヒントから「この色はない」「この色はここではない」と少しずつしぼりこむ手ごたえ。話さなくても、色を押すだけで遊べる
- 対象: 小学校中学年〜中学生。ボドゲクラブ・ひろば・作戦会議（`data-scenes="bodoge hiroba sakusen"`。メンターと子どもの1対1でも遊べる）
- 遊ぶ人は2人（2人で対戦）か2〜6人（みんなで対戦）。観戦はゲスト20人まで（＋端末なしの参加者4人まで）
- 所要時間 1回5〜15分

> 経緯: 2026-11-14「ヒット&ブローがほしい」という意見を受けて、オーナーが遊び方（2人で対戦できるモードと、複数人で対戦できるモード・隠すものは色としるし）を決め、`drafts/hit-blow/` に試作 → 同日オーナーが「この形で本体化」と承認。
> 名前「ヒット&ブロー」は、数や色のならびを当てる昔からある遊びの一般名称として使う（命名の例外。人狼・ブラックジャック・リバーシと同じ。`docs/development/app-registration.md`「アプリ名のつけかた」）。同じ名前のゲームが市販のゲーム集にも入っていることは、試作のときにオーナーへ伝えたうえで、名前はこのままと決まった（2026-11-14）。市販のゲーム集の名前・見た目は使わない。早見表では系統ラベル「定番の推理ゲーム」で紹介する。

## セッション条件（ツール一覧のカードと同じ）

スタッフがツールを選ぶときの条件。値はツール一覧（`apps/index.html`）のカードの札・`data-scenes`・`data-speech`・`data-self` と同じにする。変えるときはカードと一緒に変える。子ども向けの画面には出さない。

| 項目 | 値 |
|---|---|
| 人数 | 2〜6人 |
| 目安時間 | 5〜15分 |
| 利用シーン | ボドゲクラブ・ひろば・作戦会議 |
| 話す量 | 選ぶだけ・話さなくてよい（色を押すだけで進む。端末のない子はホストが代わりに押す） |
| 自分の話 | 外の題材で遊べる |

## ルール

| 項目 | 内容 |
|---|---|
| 答え | 色を、同じ色を使わずにならべたもの。むずかしさで決まる: やさしい（6色から3つ）・ふつう（6色から4つ）・むずかしい（8色から4つ） |
| 色としるし | 赤（ハート）・青（しずく）・黄（星）・緑（葉っぱ）・紫（ダイヤ）・オレンジ（まる）・ピンク（花）・茶（四角）。色ごとに玉の中のしるしの形がちがい、色だけで見分けなくてよい |
| ヒント | 予想ごとに「ヒット◯・ブロー◯」と、塗った点（ヒット）・輪の点（ブロー）を出す。点は数だけで、どの場所かは出さない |
| 2人で対戦 | はじめに2人がそれぞれ、相手に当ててもらう答えを決める（「おまかせ」でくじにもできる）。相手の答えを交互に当て、先に当てた人の勝ち。**先の番の人が当てたら、後の人にもう1回だけ番がある**（同じ回数で比べるため）。後の人も当てたら引き分け |
| みんなで対戦 | コンピューターがかくした1つの答えを、順番に1つずつ予想する。みんなの予想とヒントは全員に見える（ほかの人のヒントも手がかりになる）。最初に当てた人の勝ち |
| 先の番 | 「もう一回」のたびに1人ずつずらす（いつも同じ人が先にならないように） |

ルールは `engine.js`（画面と通信に触らない。node でも読める）。保存先から読んだ値は `normalize` で形をそろえる（Realtime Database は空の配列や null を保存せず、配列を番号つきのオブジェクトで返すことがあるため）。

- むずかしさの3段階・みんなで対戦の上限6人・「後の人にもう1回」は、試作のときに AI が決めて、オーナーが試作をそのまま本体化と承認したもの

## 画面構成・フロー

```
TOP（screen-top）
 ├── 「ルームを作る」 → 名前（screen-create） → 待合室
 ├── 「ルームに参加する」 → 名前＋ルームコード（screen-join） → 待合室（ゲーム中なら見るだけでゲームの画面）
 ├── 参加用のリンク `?room=CODE` → 参加画面（コード入力済み）
 ├── 「1台の画面であそぶ」 → あそびかた・むずかしさ・人数（screen-local） → ゲーム（通信しない）
 └── 「みんなにみせる画面をひらく」 → ルームコード（screen-watch-join） → 見るだけの画面
待合室（screen-waiting）: あそびかた・むずかしさ（ホストが選ぶ）・参加している人（遊ぶ／見るだけ）・端末なしの参加者・「はじめる」
  ↓「はじめる」（遊ぶ人の数があそびかたに合っている）
ゲーム（screen-game）: 遊ぶ人の札・番の表示・ヒントの見かた・（自分の答え）・答えを決める／予想をならべる・予想の一覧
  ↓ だれかが当てる（2人で対戦は、もう1回の番のあと）
結果（同じ画面）: 答え（2人で対戦は2人分）。ホストは「もう一回」「遊ぶ人・あそびかたを変える」（→ 待合室）
```

- ルームバー: ルームコード・「コードをコピー」・「リンクをコピー」・「QRコードを出す」・「みんなにみせる画面」（ホストだけ）・「退出する」（ホストは「ルームを閉じる」）。1台の画面では出さない
- 遊ぶ人: 待合室では、入った順に「遊ぶ」で入る（あそびかたの上限まで。それより後は「見るだけ」）。**ホストもはじめは「遊ぶ」**（メンターと子どもの1対1で遊ぶことが多いため）。ホストは一覧の「見るだけにする」「遊ぶにする」でだれでも切りかえられる（自分も）。共通規約の `hostPlays` は、この「遊ぶ」の切りかえで受け持つ（`seated/{ホストの名前}`）
- 予想のならべ方: 色を押すと左の空いた場所から入る。ならべた色を押すとけせる（使った色は押せない）。「ぜんぶけす」「これで聞く」
- 一覧: 2人で対戦は、2人それぞれの「当てる」一覧を左右に（せまい画面では上下に）。自分が遊ぶ人なら「あなたが当てる」を先に出す。みんなで対戦は、1つの一覧に「だれが・何回め」
- そのほかの操作（ホスト）: 「通信が切れた人の答えをおまかせで決める」（2人で対戦の答えを決める間、通信が切れた人がいるときだけ）・「この人の番をとばす」（みんなで対戦。確認あり）・「このゲームをやめる」（確認あり。待合室へ）
- 1台の画面: 「最初からやりなおす」「トップへ戻る」
- ボタン階層: 塗りつぶしの主ボタンは各画面1つ（トップ「ルームを作る」、待合室「はじめる」、答え「これにする」、予想「これで聞く」、結果「もう一回」）

## 秘密の扱い（だれの画面に何を出すか）

| 情報 | 出す画面 |
|---|---|
| 2人で対戦の自分の答え | 本人の画面だけ（「あなたの答え（相手が当てる）」）。結果で2人分を全員に出す。**ホストが遊ぶときは、ホストの答えをはじめ折りたたみ**、「見る」「かくす」で出し入れする（ゲームが変わると折りたたみにもどる）。答えを決めるところには、ホストにだけ「見ないでおまかせで決める」（くじの答えを画面に出さずにそのまま送る）を出す |
| 2人で対戦の端末なしの人の答え | だれにも出さない（コンピューターがくじで決める。ホストも知らない）。結果で出す |
| みんなで対戦の答え | だれにも出さない（コンピューターがくじで決める）。結果で出す |
| 予想とヒント | 全員（観戦・みんなにみせる画面もふくむ） |

- ホストが遊ばないときは、ホストの画面に答えは出ないので、ホストの画面をそのまま共有してもよい
- ホストが2人で対戦で遊ぶときは、ホストの画面に自分の答え（並べている途中の答え・「あなたの答え」）が出うる。折りたたみと「見ないでおまかせで決める」で出さずに遊べるが、確実なのは、みんなにみせる画面を共有して、ホストは自分のタブで遊ぶ形（rtdb.md「ホストも遊ぶかを選ぶ」と同じ）。2026-11-14 の独立レビューの指摘で足した
- みんなで対戦は、ホストが遊んでもホストの画面に答えは出ない
- 答えはルームに保存しているので、DevTools では見える（共通方針の性善説。スタッフの見守りの中で使う）

## 端末なしの参加者（ホストが代わりに押す）

- 待合室でホストが「端末なしの参加者を足す」で名前を足す（はじめる前だけ。4人まで。ほかの人・ホストと同じ名前は不可。「外す」で外せる）。`proxies/{name}` に置き、在室（`players`）には入れない（切断しない扱い）。遊ぶ人に空きがあれば「遊ぶ」で入る
- その人の番は、ホストの画面に「○○の番。代わりにならべてね」の欄が出て、ホストがならべる
- 2人で対戦では、その人の答えは「はじめる」のときにコンピューターが決める（ホストが決めると、ホストが遊ぶときに答えを知ってしまうため）
- 「端末なし」の印は、ホストの画面にだけ出す（子どもどうしの画面で区別しない）

## status 遷移

```
waiting ─はじめる→ play（game.phase: setup〈2人で対戦〉→ play → end）
play ─もう一回（ホスト・おわったあと）→ play（新しいゲーム。先の番をずらす）
play ─遊ぶ人・あそびかたを変える／このゲームをやめる（ホスト）→ waiting
どこからでも ─ルームを閉じる（ホスト）→ 削除
```

## Firebase データ構造（Realtime Database）

```
hitblow_rooms/{roomCode}/
  ├── status:             'waiting' | 'play'
  ├── host / hostUid:     ホストの名前と匿名ID
  ├── hostConnected / hostDisconnectedAt / createdAt
  ├── lastGameId:         number
  ├── mode:               'duel' | 'party'      # 待合室で変更
  ├── level:              'easy' | 'normal' | 'hard'
  ├── seated/{name}:      true                   # 待合室で「遊ぶ」の人
  ├── players/{name}:     { isHost, uid, joinedAt }   # 在室。ゲストは切断で消え、戻ると同じ joinedAt で戻る
  ├── proxies/{name}:     { joinedAt }                # 端末なしの参加者
  └── game/                          # 「はじめる」で作り、待合室にもどると消す
       ├── v: 1, mode, level, n（遊ぶ人数）, round（先の番を決める回の番号）
       ├── id, names: [名前...]（番の順）, uids: [匿名ID | ''（端末なし）], proxy: [bool...]
       ├── phase: 'setup' | 'play' | 'end', turn: 番の人の番号
       ├── secrets: [答え...]   # 2人で対戦は2つ（決めていない人はなし）、みんなで対戦は1つ
       ├── log: [{ by, target, guess: [色...], hit, blow }...]
       ├── solved, winners: [番号...], lastChance: もう1回の番の人, draw: 引き分け
       ├── rev: ゲームが変わるたびに増える番号（予想・答え・番をとばす）。古い画面からの操作の照合
       └── ended: 一度でもおわった（finish を1ゲームに1回だけ数える）
```

- 読み込むときは壊れた値を読み飛ばす（`gameOf` → `engine.normalize`）

## transaction 設計

すべてルーム全体への `transaction()`。ホストの操作は `hostUid` を確かめる（`hostTransaction`）。
あそびかた・むずかしさ・遊ぶ人の変更は、続けて変えても取りこぼさないよう二度押しよけのロックを使わない（中で今の値から作りなおす）。

| 操作 | 実行者 | 検証 → 書き込み |
|---|---|---|
| 作成 | ホスト | 空のコード → 初期ルーム（`transactRetry`。送信後の切断のやり直しで、自分が作ったルームならそのまま使う） |
| 参加 | ゲスト | 名前が空いている（ホスト・端末なしの子と同じ名前は不可）・ゲスト20人未満（ゲームの席の人が戻るときは上限を見ない）・ゲームの席の名前は同じ匿名IDの人だけ → `players/{name}`。待合室で遊ぶ人に空きがあれば `seated` にも入る（`transactRetry`。自分の在室が残っていれば入りなおし） |
| あそびかた・むずかしさ・遊ぶ人・端末なしの参加者 | ホスト | `waiting` |
| はじめる | ホスト | `waiting`・遊ぶ人の数が合っている・全員いる → `game` を作る（端末なしの人の答えはくじ） |
| 答えを決める | 席の本人 | `play`・押した時点の game.id が一致・`setup`・まだ決めていない → `secrets`（自分の欄だけを書くので `rev` は見ない。2人がほぼ同時に決めても両方通す） |
| 予想を出す | 番の席の人（端末なしの人・通信が切れた人の番はホスト） | `play`・game.id と `rev` が一致・その人の番 → `log`・番・勝ち負け、`rev` を1増やす。おわったら `ended` |
| おまかせで決める | ホスト | `setup`・通信が切れていて答えがない席 → くじの答え |
| 番をとばす | ホスト | みんなで対戦・`play`・game.id と `rev` が一致 → 次の人の番 |
| もう一回 | ホスト | おわったゲーム・game.id 一致・遊んだ人がまだいる → 先の番をずらして新しいゲーム |
| 待合室へ | ホスト | game.id 一致 → `waiting`。そのゲームの遊ぶ人（いまいる人）を `seated` に残す |
| 退出 | ゲスト | 自分の在室を消す。待合室なら `seated` からも外す（ゲーム中の席は残し、ホストが代わりに押せる） |

## 接続・切断・再接続

リバーシと同じ作り。

| 役割 | onDisconnect 予約 |
|---|---|
| ホスト | ルームに `update({ hostConnected: false, hostDisconnectedAt: TIMESTAMP })` |
| ゲスト | `players/{name}` を `remove()` |

- `.info/connected` が true になるたびに切断予約を張り直し、在室を書き戻す（3秒に1回まで）
- 席の人が切れると、全員の札に「通信が切れた」。その人の番はホストが代わりにならべられる。2人で対戦の答えを決める前に切れたときは、ホストが「おまかせで決める」で進められる。戻ると（同じタブの読み込み直し・同じ名前と同じ匿名ID）続きから
- ゲームの席の名前は、ほかの人（別の匿名ID）は使えない（「その名前は使われているよ」）
- ゲーム中に入った人は見るだけ（席には入らない）
- ホスト切断中、ゲストと見る画面には共通のオーバーレイ（2分）。`ORPHAN_TTL_MS = 2 * 60 * 1000`。期限のタイマーは、切れた時刻が変わったら仕掛けなおす

## 終了とデータ削除

- 公認バリアント「**ふりかえり画面滞在中は削除しない**」を採用する。ゲームがおわっても自動削除しない（「もう一回」のため）
- 削除経路: ①ホストの「ルームを閉じる」（`cancelRoomOnDisconnect()` を await → `remove()`） ②ホスト切断＋2分 TTL ③次回アクセス時（参加・再接続・ルーム監視）の期限切れ掃除（status の無いゴーストも対象、`applyLocally: false`）
- 待合室にもどると `game` を消す

## みんなにみせる画面（画面共有用・見るだけ）

- **入口**: ①ルームバーの「みんなにみせる画面」（ホストだけ）②トップの「みんなにみせる画面をひらく」③アドレスの `?watch=CODE`
- **ルームへの書き込みゼロ**: `state.role === 'spectator'`。players に入らない・切断予約をしない・期限切れのルームも消さない
- 待合室では「参加のしかた」とルームコードを大きく出す。ゲームでは、予想の一覧を高さの制限なしで出す。答えは結果まで出さない

## 1台の画面（メンターが操作する）

- 通信しない（Firebase に書き込まない）。あそびかた・むずかしさ・人数（みんなで対戦）を選んで「はじめる」。遊ぶ人は「1人目」「2人目」…
- 2人で対戦では、2人の答えをコンピューターが決める（1つの画面では、おたがいにかくせないため）
- ゲームは sessionStorage（`hitblow_local`）に置き、読み込み直すと続きから。「トップへ戻る」で消す
- 結果のあと「もう一回」（先の番をずらす）・「あそびかたを変える」（準備の画面へ）

## 利用回数（stats.js）

「1回」は1ゲーム。

| 項目 | 数えるとき・端末 |
|---|---|
| `room-create` | ルームができた（ホスト） |
| `start`・`players-{N}` | ゲームが始まった（「はじめる」「もう一回」。ホスト。N は遊ぶ人数） |
| `finish` | ゲームがおわった（最後の予想を確定させた端末） |
| `again` | おわったあと「もう一回」「遊ぶ人・あそびかたを変える」（ホスト）。途中でやめたときは数えない |
| `local-start` | 1台の画面でゲームを始めた（「はじめる」「最初からやりなおす」「もう一回」） |
| `local-finish` | 1台の画面のゲームがおわった |

## 意図的な逸脱

- **分割構成の RTDB アプリ**: lint の REF-4（TTL 定数）と REF-5（タイマー解放）は RTDB_HTML_FILES のとなりの app.js も見る。engine.js は DOM に触らない
- **ホスト以外も進行の一部を行う**: 席の人が答え・予想を書く・最後の予想を確定させた端末が `finish` を数える
- **観戦は参加者として players に入る**（席に入らない人）。見るだけの画面（書き込みゼロ）は別にある
- **終了後の自動削除なし**（公認バリアント「ふりかえり画面滞在中は削除しない」）
- **端末なしの参加者は在室を持たない**（`proxies`。切断しない。ホストが代わりに押す）
- **勝ち負けを出す**（定番の対戦ゲームの結果。当てた人に印を付けるだけで、回数の比較・順位・記録はしない）
- **`hostPlays` を `seated` で受け持つ**（ホストもほかの人と同じ「遊ぶ／見るだけ」の切りかえ。はじめは「遊ぶ」）

## 入れない機能

- 音（予想・当たりの音もなし）
- 制限時間（考えこむ子を急かさないため。必要になったら足す）
- 同じ色を2回使う答え（はじめての子にむずかしくなりすぎるため）
- 消した色に印を付けるメモ・CPU と1人で対戦するモード（試作のときに「入れていない」とオーナーに伝えたもの）
- 勝ち数・対戦成績の記録、順位
- ゲーム中の新しい遊ぶ人（途中から入った人は見るだけ）

## 既知の制約（v1）

- 同じ名前・同じ匿名IDのタブが2つ開いていると、両方が同じ `players/{name}` に切断予約を張る（ほかのルーム型ゲームと共通）
- 待合室で遊ぶ人が一時的に切れている間（`players` から消える）は、一覧に出ず、遊ぶ人の数にも数えない（その間に入った人が空きに入れる）。戻ったときに遊ぶ人がもう上限なら、戻った人は「見るだけ」になる（ホストが切りかえられる）。この戻りの扱いは E2E では確かめていない（コードを読んで確かめた）
- 確定の応答が届く前に通信が切れると、`start`・`finish` などを数え漏れることがある（共通方針どおり、少なめに出る側の誤差として扱う）

## メンター向けの心得（画面には出さない）

- はじめての子には「やさしい」で、メンターと「みんなで対戦」をすると、ヒントの読み方をいっしょに考えられる（「ブローが2つだから、この中の2色は入っているね」）
- 1台の画面で遊ぶときは、子どもに色やしるしの名前で言ってもらう（「ハートを1番目」など）。言いにくい子には、チャットで送ってもらうでもよい
- 当てられなかった子には、しぼりこめた予想をほめる（「この回で赤が入っていないとわかったね」）
